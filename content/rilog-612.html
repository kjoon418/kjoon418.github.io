주문이 하나 생기면 여러 서비스에게 알려야 한다고 가정해보자.
주문이 생겼다는 사실을 어떻게 전달해야 할까?

간단하게 구현해보자

주문이 완료된 후에 다음 작업들도 해야 한다고 가정해보자.

  • 사장님에게 새 주문이 들어왔다고 알린다.
  • 주문을 정산한다.
  • 쿠폰을 사용 처리한다.

주문이 끝나면 하나씩 호출하면 되지 않을까?
이러면 2개의 문제가 생긴다.

한 기능이 멈추면 다 같이 멈춘다

주문이 바로 정산됐는지 아닌지는 주문 입장에서 중요한 내용이 아닌데도, 주문 정산 기능이 잠깐 멈추니 주문 기능까지 멈춘다.

기능이 추가될 때 마다 주문 서비스를 수정해야 한다

주문이 끝나면 매출 대시보드에도 반영해야 한다는 요구사항이 추가되었다고 가정하자.
이렇게 주문 이후 할 일이 늘어날 때 마다, 주문 서비스를 수정하고 다시 배포해야 한다.

Pub/Sub을 사용하자

Pub/Sub을 사용하면, 주문 서비스가 이후 작업들을 직접 호출하지 않아도 된다.
주문 서비스는 주문이 생겼다는 이벤트만 전달하고, 그 이벤트는 Pub/Sub을 통해 다른 서비스에게 보내진다.

이 과정을 단계별로 표현하면 다음과 같다.

  1. 주문 이벤트가 주문을 생성하고 저장한다.
  2. 주문 서비스가 ‘주문 이벤트 토픽’에 ‘주문 생성 이벤트’를 발행한다.
  3. Pub/Sub이 해당 이벤트를 다른 서비스에게 전달한다.
  4. 각 서비스가 주문 이벤트를 받아 처리한다.

이 과정을 일반적인 용어로 표현하면 다음과 같다.

  1. 발행자(Publisher)가 토픽(Topic)에 이벤트를 발행(Publish)한다.
  2. Pub/Sub 시스템이, 해당 토픽을 구독(Subscribe)한 구독자(Subscriber)들에게 이벤트를 전달한다.
  3. 각 구독자는 전달받은 이벤트를 처리한다.

작업 큐와 Pub/Sub는 뭐가 다를까?

작업 큐와 Pub/Sub은 둘 다 메시지를 넘기는 역할을 하지만, 조금 다르다.

작업 큐는 이벤트 하나를 한 소비자에게만 전달하고, Pub/Sub은 이벤트 하나를 여러 구독자에게 전달한다.

Kafka 같은 요즘 브로커 제품은, 다음과 같이 작업 큐와 Pub/Sub을 함께 제공한다.

  • 소비자 그룹들에게 이벤트를 전달할 때는 Pub/Sub 방식 사용
    → 이벤트를 여러 소비자 그룹에게 전달
  • 한 소비자 그룹 내에서는 작업 큐 방식 사용
    → 같은 소비자 그룹 안에서는 한 소비자만 이벤트 처리

이벤트에 어떤 정보를 담아야 할까?

알림형 vs 상태 전달형

이벤트에 정보를 담는 방식은, 크게 알림형과 상태 전달형으로 나뉜다.
각각의 장단점을 살펴보자.

받는 쪽에 필요한 필드까지 담는다

이벤트 크기가 작다

받는 쪽이 추가 정보를 따로 조회하지 않아도 된다

어떤 단점이 있는가?

받는 쪽에서 조회 요청을 별도로 보내야 한다

이벤트 크기가 커진다
이벤트를 받는 쪽에서 이벤트 형식에 강결합한다

알림형을 사용할 경우, 이벤트를 받는 쪽에서 매번 추가 조회 요청을 보내야 한다.
알림형을 사용해 생기는 추가 요청이 감당 가능할지 과할지 고민해보자.

별개로, 상태 전달형을 사용하더라도 개인정보(이름, 연락처 등)는 포함하지 말자.
이벤트는 구독자 모두에게 전달되니 민감한 정보를 담기 부적절하다.

이벤트의 정보는 어떻게 수정해야 할까?

이벤트는 여러 곳에서 구독하기 때문에, 기존에 존재하던 필드를 수정하거나 제거하면 다른 서비스에서 문제가 발생할 수 있다.

때문에, 가능하다면 기존 필드를 수정하지 말고 새로운 필드만 추가하자

연결이 끊기면 어떻게 할까?

연결이 끊기면 어떻게 될까?

Pub/Sub은 메시지가 온 순간의 구독자에게만 이벤트를 보낸다.
또한, 뒤늦게 구독하더라도 그 이전에 발행된 이벤트를 전달하진 않는다.

그러므로, 클라이언트는 연결이 끊긴 사이에 발행된 이벤트를 받을 수 없다.

놓친 주문을 알려주자 → 변경분 조회

연결이 잠시 끊긴 클라이언트는, 그 사이에 생긴 주문을 조회할 수 있어야 한다.
이를 위해, 마지막으로 주문을 받은 이후에 바뀐 주문들을 따로 조회할 수 있게 해주어야 한다.

이런 조회를 변경분 조회라고 한다.
변경분 조회를 위해, 서버는 주문 정보를 이벤트 뿐 아니라 데이터베이스에도 저장해야 한다.

메시지를 보관해야 할까?

제품마다 한 번 전송한 메시지를 다시 읽을 수 있게 보관하는지 아닌지 다르다.
Redis Pub/Sub 같은 제품은 보관하지 않고, Kafka 같은 제품은 보관한다.

여기서 어떤 제품을 사용해야 할지는 메시지마다 다르다.

‘매출 합계’처럼 금방 다음 메시지로 대체되는 메시지는 보관하지 않아도 되니, Redis Pub/Sub 같은 제품이 적절하다.

‘정산 이벤트’처럼 멈추면 나중에라도 재처리해야 하는 메시지는 보관해야 하니, Kafka 같은 제품이 적절하다.

이벤트를 서버가 먼저 알려주려면?

폴링 vs 롱폴링 vs 웹소캣

새 주문이 생겼다는걸 클라이언트에게 어떻게 알릴 수 있을까?
크게 폴링, 롱폴링, 웹소캣 중 하나를 선택할 수 있다.

방법

장점

단점

폴링

구현이 가장 간단하다

폴링 간격이 짧을수록 많은 요청-응답을 주고받아야 한다
폴링 간격이 길수록 이벤트가 늦게 전달된다

롱폴링

HTTP 환경을 그대로 사용할 수 있다.
요청-응답을 필요한 만큼만 주고받는다.

응답할 때마다 클라이언트가 새로운 요청을 보내야 한다.

웹소캣

한 번 연결하면 이후 요청 없이 데이터를 전달할 수 있다

웹소캣 통신 정책을 별도로 구축/관리해야 한다.

각각의 장단점은 위와 같으니, 현재 상황에 맞는 방법을 선택하자.

앱이 꺼져 있어도 알려줘야 해 → 푸시 알림

폴링, 롱폴링, 웹소캣은 모두 클라이언트와 연결되어 있어야 한다.
클라이언트 앱이 꺼져 있더라도 이벤트를 전달하고 싶다면, 푸시 알림을 사용하자.

하지만, 푸시 알림은 잘 전송되는지 서버에서 알아낼 수 없다.
따라서, 푸시 알림은 앱이 꺼져 있어도 알려주는 용도로만 사용하고, 데이터는 서버에서 따로 조회하게 만드는게 안전하다.

요약

정할 것

정하는 방법

작업 큐 vs Pub/Sub

메시지 하나를 한 곳(소비자)에서만 처리하면 작업 큐
메시지 하나를 여러 곳(구독자)에서 처리하면 Pub/Sub

이벤트에 담을 정보

받는 쪽에 필요한 최소 필드만 담는다.
개인정보는 담지 않는다.
가능하면 기존 필드를 수정하지 않는다.

메시지를 보관할지 여부

새 값으로 금방 대체되는 메시지는 보관하지 않아도 된다. (Pub/Sub)
나중에라도 재처리해야 해서 잃으면 안 되는 메시지는 보관한다. (브로커)

클라이언트에 알리는 방법

HTTP 인프라를 재사용하고 싶다면 롱폴링
최소한의 요청/응답으로 해결하고 싶다면 웹소캣
앱이 꺼져 있어도 알리려면 푸시 알림
앱이 꺼져서 놓친 메시지는 별도로 조회할 수 있게 만든다.
