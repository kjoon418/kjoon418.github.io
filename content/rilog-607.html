준비된 재고 만큼의 주문만 성공시키는 시스템을 설계해보자.
우리가 사용할 수 있는 방법은 다음과 같다.
  1. 조건부 UPDATE
  2. 분산 캐시
  3. 샤디드 카운터
  4. 예약 단위 행 풀

대충 만들면 어떻게 될까?

상품 주문 기능을 구현해야 한다.
우선 간단하게 구현해보자.

1. 남은 재고를 조회한다.
2. 주문할 수 있는지(재고가 남아 있는지) 판단한다.
3. 재고를 차감한다.

논리에 딱히 문제가 보이진 않는다.
이대로 배포해도 잘 돌아갈까?

여러 사용자가 동시에 주문 요청을 보내면, 재고보다 더 많은 수의 주문이 승인될 수 있다.
서버가 주문을 재고 만큼만 승인하도록 만들어보자.

동시성 방어 → 조건부 UPDATE

이전엔 재고 검사와 차감 사이에 간격이 있었기 때문에 다른 요청이 비집고 들어올 수 있어서 문제가 됐다.
두 동작을 원자적으로 수행해, 여러 요청이 동시에 들어오더라도 순서대로 처리하게 만들자.

UPDATE 상품_테이블
SET 재고 = 재고 - 1
WHERE 재고 >= 1

이렇게, “재고가 있으면 차감한다”라는 동작을 한 쿼리로 수행하자.

DB 부하 완화 → 분산 캐시

조건부 UPDATE를 쓰더라도, 행에 Lock을 걸어야 한다는 한계는 그대로다.
때문에, 인기 상품 하나에 요청이 몰릴 경우, 락 때문에 뒤에 온 요청들이 모두 오래 대기하게 된다.

이 때 분산 캐시를 데이터베이스 앞에 두면 재고보다 많이 온 요청을 빠르게 거절할 수 있다.
Lua 스크립트를 사용하면 여러 동작을 원자적으로 처리해주니, 동시성을 걱정할 필요도 없다.

재고를 확인과 차감을 처리하는 Lua 스크립트 예시

-- 재고 키(KEYS[1])를 통해 재고 조회
local stock = redis.call('GET', KEYS[1])

-- 키가 없으면 -1 응답
if not stock then
    return -1
end

-- 재고가 없으면 0 응답
if tonumber(stock) < 1 then
    return 0
end

-- 재고가 있으면 1 응답
redis.call('DECR', KEYS[1])
return 1

분산 캐시의 한계

캐시와 데이터베이스는 서로 다른 저장소라서, 하나의 트랜잭션으로 묶을 수 없다.
즉, 캐시와 데이터베이스의 값이 서로 어긋날 수 있다.

따라서, 캐시만 믿고 주문을 승인하면 안된다.
캐시는 재고보다 많은 주문을 빠르게 거절하는 용도로만 사용하고, 실제 주문은 데이터베이스를 통해 처리하자.

또한, 캐시와 DB의 값이 어긋나 있으면 재고가 있는데도 주문을 거절하는 상황도 생길 수 있다.
주기적으로 캐시 값을 데이터베이스에 맞춰주자.

처리량 개선

1. 샤디드 카운터

분산 캐시로 DB 부하를 완화했다고는 하나, 여전히 행 하나에 모든 주문 요청이 몰리는건 똑같다.
이 문제를 해결하기 위해, 하나의 재고를 여러 키로 나눌 수 있다.

키를 10개로 나누면 요청이 10개의 행으로 분산된다.
이런 식으로, 키를 필요한 만큼 나눠 처리량을 증가시키는걸 샤디드 카운터라고 한다.

주의할 점

샤디드 카운터를 사용하면, 재고가 얼마 남지 않았을 때 위처럼 다른 키까지 찾아야 한다.
심지어는, 재고가 남아 있는데도 찾지 못해 재고가 없다고 응답할 수도 있다.

이런 문제를 방지하기 위해, 재고 합계가 일정 이하가 되면 분산한 키를 합쳐야 한다.

2. 재고 풀 + SKIP LOCKED

이번엔 SKIP LOCKED을 활용한 해결법도 알아보자.
샤디드 카운터와 유사하지만 조금 다르다.

이 방식은, 재고 하나를 행 하나로 만들어 구매자마다 서로 다른 행을 사용하게 만든다.
구매자마다 사용하는 행이 다르니, 락을 걸더라도 다른 사용자가 대기하지 않아도 된다.

주의할 점

만들어진 행이 없으면 재고가 없다고 판단한다.
이 때문에, 실제로는 재고가 있어도 주문에 실패할 수 있다.

이런 문제가 발생하지 않게, 행을 채워 넣는 보충 작업을 따로 운영해줘야 한다.

요약

지금까지 재고 관리 시스템을 설계할 때 활용할 수 있는 방법들을 알아보았다.
이 방법들을 요약하면 다음과 같다.

방법

이점

한계

조건부 UPDATE

정확성
주문이 재고보다 많이 처리되지 않게 막는다.

여러 요청이 한 행의 Lock을 두고 경합한다.

분산 캐시

속도
데이터베이스 앞단에서 재고 이상의 요청을 거절한다.

데이터베이스와 한 트랜잭션으로 묶을 수 없어서, 값이 어긋날 수 있다.

샤디드 카운터

처리량
경합이 여러 행으로 분산된다.

재고가 남아 있는데도 주문에 실패할 수 있다.
→ 재고가 적어지면 키를 합쳐야 한다.

재고 풀 + SKIP LOCKED

처리량
경합이 발생하지 않는다.

재고가 남아 있는데도 주문에 실패할 수 있다.
→ 행을 채워 넣는 보충 작업을 따로 운영해주어야 한다.
