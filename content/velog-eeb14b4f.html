1. ShedLock, 왜 도입할까요?

결론부터 정리해볼게요.
ShedLock은, 서버를 여러 대 띄우더라도 하나의 스케줄러만 실행하기 위해 사용해요.

구체적으로 어떤 상황에 필요하고, 어떻게 구현하는지 살펴볼게요.

2. 언제 필요할까요?

요구사항이 생겼어요

"매일 오전 9시에, 모든 사용자에게 푸쉬 알림을 보내야 한다"라는 요구사항이 생겼어요.
이 요구사항을 만족할 스케줄러를 구현해볼까요?

스케줄러를 만들었어요

@Component
@RequiredArgsConstructor
public class DailyNotificationScheduler {

    private final NotificationRepository repository;
    private final NotificationSender sender;

	// 매일 오전 9시에 실행한다
    @Scheduled(cron = "0 0 9 * * *")
    public void sendDailyNotifications() {
    	// 전송해야 할 알림을 찾는다
        List<Notification> notifications = repository.findSendableNotifications();
        for (Notification notification : notifications) {
        	// 알림을 사용자에게 전송한다
        	sender.sendToAllUsers(notification);
            // 알림을 전송 완료했다고 표시한다
            repository.markAsSent(notification);
        }
    }
}

스케줄러를 위와 같이 짜면 되겠죠?
잘 동작할 것 같아요.
Shedlock을 사용할 이유가 있을까요?

왜 문제가 될까요?

서비스의 인기가 많아져서, 서버 인스턴스를 여러 대 띄워야 한다고 해볼게요.
스케줄러는 인스턴스별로 동작할테니, 위 그림처럼 여러 개의 스케줄러가 동작할거에요.

그러면 어떻게 될까요?
"전송해야 할 알림을 찾고, 그 알림을 전송한다"라는 동작이 동시에 여러 곳에서 이루어져요.
결과적으로, 사용자가 같은 알림을 여러 번 받게 돼요.

해결법은 간단해요.
인스턴스가 여러 개 있어도, 하나의 스케줄러만 동작하게 만들면 돼요.

3. 해결해봅시다

락 저장용 테이블을 만들어요

CREATE TABLE shedlock (
    name VARCHAR(64) NOT NULL,
    lock_until TIMESTAMP(3) NOT NULL,
    locked_at TIMESTAMP(3) NOT NULL,
    locked_by VARCHAR(255) NOT NULL,
    -- 같은 이름(name)의 락은 하나만 존재할 수 있게 막아요
    PRIMARY KEY (name)
);

여러 인스턴스가 공유할 락 상태를 DB 테이블에 기록할거에요.

여기서, name을 PK로 지정해요.
이 덕에, '같은 이름의 락은 하나만 존재하도록' 막아요.

ShedLock을 설정해요

@Configuration
// ShedLock의 AOP 프록시를 활성화하고, 락의 기본 최대 점유 시간을 지정해요 (여기서는 10분)
@EnableSchedulerLock(defaultLockAtMostFor = "PT10M")
public class SchedulerLockConfig {

    @Bean
    public LockProvider lockProvider(DataSource dataSource) {
        return new JdbcTemplateLockProvider(
                JdbcTemplateLockProvider.Configuration.builder()
                        .withJdbcTemplate(new JdbcTemplate(dataSource))
                        .usingDbTime() // DB 서버 시각을 기준으로 락을 판정하게 지정해요
                        // .withTableName("테이블명") DB 테이블명을 지정할 수도 있어요
                        .build()
        );
    }
}

위와 같이 LockProvider 빈을 등록해요.
이 빈은, "ShedLock에서 락을 어디에서 어떻게 저장/획득/해제할지"를 담당할거에요.

이 코드의 핵심 부분은 각각 다음과 같아요.

@EnableSchedulerLock

  • ShedLock의 AOP 프록시를 활성화해요.
  • 이 덕에, @SchedulerLock이 붙은 메서드를 실행을 가로채서, 락을 획득하고 나서 실행하게 만들어요.

defaultLockAtMostFor = "PT10M"

  • 락의 기본 최대 점유 시간을 지정해요. (여기서는 10분)
  • 작업 중 인스턴스가 죽는 일이 생기더라도, 일정 시간 뒤에 락이 자동 해제되도록 만들어서, 데드락을 방지해요. (최후의 안전장치에요)
  • 여기서 시간은 ISO-8601 Duration 표기법을 따라 작성해요. PT10M이 왜 10분인지가 궁금하다면, 표기법을 학습해보세요.

.usingDbTime()

  • 애플리케이션 시각이 아닌, DB 시각을 기준으로 락을 판정하게 만들어요.
  • 서버 인스턴스마다 시간에 오차가 있을 수 있는데, 이로 인한 문제를 방지할 수 있어요.
  • 즉, ShedLock이 서버 시간에 의존하지 않게 만들 수 있어요.

.withTableName(...)

  • 만일 락 테이블 이름이 shedlock이 아니라면, 테이블 이름을 지정해줘야 해요.
  • 생략한다면, 기본값으로 shedlock을 사용해요.

이 예시에서는 RDBMS(JdbcTemplateLockProvider)를 사용하지만, Redis나 MongoDB를 사용할 수도 있어요.

스케줄러에 적용해요

public class DailyNotificationScheduler {

    // ...

    @Scheduled(cron = "0 0 9 * * *")
    @Transactional
    @SchedulerLock(name = "dailyNotification", lockAtLeastFor = "PT30S", lockAtMostFor = "PT10M")
    public void sendDailyNotifications() {
    	// ... 로직은 수정하지 않아도 돼요 ...
    }
}

스케줄러의 다른 코드는 일절 수정할 필요 없이, @SchedulerLock 애노테이션 하나만 붙여주면 돼요.

애노테이션 속성별 역할은 다음과 같아요.

name

  • 락의 이름을 의미해요. (shedlock 테이블의 name 컬럼 값으로 사용돼요)
  • @SchedulerLock을 적용할 스케줄러가 여럿일 수도 있겠죠? 이 작업들을 서로 구분하는 용도로 사용돼요.

lockAtMostFor

  • 이 작업 락의 최대 점유 시간을 지정해요. (위 예시에서는 10분)
  • LockProvider을 등록할 때도 봤죠? 데드락을 방지하는 역할이에요.

lockAtLeastFor

  • 락을 유지할 최소 시간이에요.
  • 작업이 아무리 빨리 끝나더라도, 지정된 시간 동안은 락을 풀지 않게 만들어요.
  • 이 값이 없다면, 작업이 끝나자마자 락을 풀겠죠? 서버 인스턴스마다 시간 오차가 있다면, 뒤늦게 실행된 스케줄러가 "락이 안 걸렸으니 실행해야겠네!"라고 생각할 수 있어요.
  • 이를 방지하기 위해, 일정 시간동안 락을 들고 있게 강제해요.

어떻게 막는거에요?

ShedLock을 적용한 스케줄러는, 다음과 같이 동작해요.

  1. 실행 시간이 되면 실행하려고 시도해요.
  2. 가장 먼저 DB에 접근한 인스턴스는 Lock을 획득하고 작업을 수행해요.
  3. Lock을 획득하지 못한 인스턴스는, 작업을 조용히 건너뛰어요.

작업을 건너뛴다는 점이 일반 락과의 큰 차이점이죠?
일반적인 락과 ShedLock은 같은 락이지만, 목적이 달라요.

다른 락은 '여러 작업을 동시에 실행할 때 문제가 생기지 않게 막는다'라면, ShedLock은 '여러 번 실행할 필요 없는 작업을 한 번만 실행하게 만든다'에 가까워요.

4. 언제 써야 할까요?

예시로 든 상황을 해결할 수 있는 방법은 ShedLock 하나가 아니에요.
DB 데이터 락, Spring Batch 등으로도 동일한 결과를 만들어낼 수 있어요.

그렇기에, 우리는 항상 "왜 이 기술을 사용해 해결했는가"에 대한 근거를 지녀야 해요.
ShedLock의 이점과 한계에 대해서 살펴봅시다.

이점이 무엇일까요?

단순함과 가벼움

이전에, ShedLock을 도입하기 위해 스케줄러를 어떻게 수정했는지 기억하시나요?
기존 스케줄러 코드를 그대로 유지하면서, @SchedulerLock 하나만 추가하면 돼요.

또한, 데이터 스키마 변경과 LockProvider 설정도 비교적 단순해요.
학습 곡선이 낮고 구현이 단순하니, 다른 개발자도 쉽게 이해할 수 있고, 실수가 발생할 확률이 낮겠죠?

비즈니스 로직과 락의 분리

ShedLock은 비즈니스 테이블(이 예시에서는 notification)에 락을 걸지 않아요.
오직 shedlock이라는 별도의 관리 테이블을 이용해 락을 관리해요.

이 덕분에, 스케줄러 로직이 핵심 비즈니스 로직의 트랜잭션을 방해하지 않아요.

자원 낭비 최소화

다른 락 방식은, 락을 획득하지 못하면 대기(Blocking)해요.
반면, ShedLock은 락을 획득하지 못하면 "다른 인스턴스가 실행 중이니까 나는 필요 없구나"라고 생각하고 스킵해요.

즉, 스레드 및 DB 커넥션 반환이 빨라요.

어떤 한계가 있을까요?

관리 기능의 부재

ShedLock은, 단순히 "Lock을 획득한 인스턴스만 실행한다"라는 기능만 제공해요.
즉, 다음 기능들은 제공하지 않아요.

  1. 작업이 실패했을 때 자동으로 재시도(Retry)하는 기능
  2. 작업 A가 끝나면 작업 B를 실행하는(Chaining) 기능
  3. 누가 언제 성공/실패했는지를 보는 관리자 모니터링 기능

이런 기능들이 중요하다면, 다른 선택지를 고려하는게 나을 수 있어요.
(물론, ShedLock을 사용하면서 직접 구현해도 되죠!)

좀비 락

'관리 기능의 부재'와 연결되는 이야기에요.
작업을 수행하던 서버가 락을 해제하지 못하고 죽으면 어떻게 될까요?
(ex_ 메모리 부족, 강제 종료 등)
DB에는 락이 남아 있으니, 다른 서버들은 "다른 인스턴스에서 처리 중이구나" 하고 스킵해버려요.

결국, lockAtMostFor로 지정된 시간 동안, 아무 스케줄러도 동작하지 않을 수 있어요.
(앞서 설명했듯이, lockAtMostFor는 이 경우를 위한 안전장치에요)

5. 주의점) 서버 시간 오차가 크면?

ShedLock은, 단순히 "스케줄러를 지금 실행해도 되나?"를 알려줘요.
즉, "스케줄러를 언제 실행해야 할까?"를 알려주진 않아요.
(이건 ShedLock의 책임이 아니라, 서버 시간과 스케줄러의 책임이에요)

서버 인스턴스마다의 시간 오차가 크다면, ShedLock으로도 중복 실행을 막을 수 없어요.
물론, 약간의 오차는 lockAtLeastFor가 해결해줘요.

6. 결론

ShedLock은 다음과 같은 상황에 유리한 도구에요.
1. 실패해도 다음 주기에 다시 실행하면 되는 경우
2. 모니터링 및 관리가 복잡하지 않아도 되는 경우
3. 중복 실행을 막아야 하는 경우

특히, ShedLock의 본래 목표인 중복 실행 방지에 초점을 두면 좋겠어요.
여러분의 프로젝트에서는 ShedLock이 최선의 선택지인가요?
