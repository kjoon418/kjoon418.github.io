검증 로직의 위치 및 분배

일반적인 Spring MVC는 Controller - Service - Repository로 구성되어 있고, 계층과 별개로 Domain이 존재한다.

이렇게나 다양한 역할의 객체들이 존재하는데, 검증 로직은 어디에 두어야 하는 걸까?

Controller 계층의 검증
@GetMapping("users")
public ResponseEntity<List<User>> findUsers(
    @RequestParam int limit // 필수 파라미터를 정의한다
) {
	// ...
}

컨트롤러는 API의 스펙을 표현한다.
즉, 어느 값이 필수인지를 표현해야 한다.
그러므로, null 체크를 통해, 필수 값이 누락되지 않았는지 검증할 책임이 있다.

별도의 목적이 없다면, Service나 Domain은 null을 체크하지 않는다.
null일 수 없는 값을 null로 보내주는 것은 계약 위반으로 합의한다.

Domain(VO, Entity 등)
public record UserName(
	String value
) {
	public UserName {
    	if (value.isBlank() || value.length() > 20) {
        	throw new IllegalStateException("이름은 비어 있거나 20자 초과일 수 없습니다.");
        }
    }
    
    public UserName copy() {
    	if ("관리자".equals(value)) {
        	throw new IllegalStateException("관리자
}

Domain은 애플리케이션 전역에서 사용된다.
그러므로, 애플리케이션에 어디에서든 항상 적용될 요구사항을 검증해야 한다.

단, 검증을 위해 외부 인프라(데이터베이스 등)를 의존할 순 없다.
외부 인프라에 의존하지 않는 선에서 검증한다.

Service 계층의 검증
public void createUser(UserName userName) {
	User user = new User(userName);
	
    // 데이터베이스에 의존해야 검증할 수 있는 요구사항
    if (userRepository.existsByName(userName)) {
    	throw new IllegalArgumentException("이미 사용중인 이름입니다.");
    }
    userRepository.save(userName);
}

Controller와 Domain이 검증하지 않는 요구사항은 모두 Service로 넘어온다.
즉, Service는 "외부 인프라에 의존해야 검증할 수 있는 요구사항"을 검증한다.

또한, 상황에 따라 다음 요구사항을 검증할 수 있다.

  • 일부 유스케이스에서만 적용되는 요구사항(ex_ 관리자의 회원 삭제)
  • 여러 도메인에 걸쳐 있는 요구사항

위에 해당하는 검증 로직은 서비스가 지닐 수도, 도메인이 지닐 수도 있다.
어느 쪽에 두는게 더 바람직할지는 트레이드 오프를 고려하도록 하자.

테스트 로직의 책임 분배

애플리케이션을 구현하다 보면, 테스트해야 할 내용은 차고 넘친다.
테스트에 대한 명확한 기준이 없다면, 필수적인 테스트 케이스가 누락될 수도 있고, 같은 기능을 여러 곳에서 중복해서 테스트할 수도 있다.

따라서, 상황별로 어떤 테스트가 필요한지 목표를 명확히 하고, 그에 맞는 도구를 선택하자.
이를 통해, 각 테스트의 목적을 명확히 분리하고 관리해야 한다.

Controller 계층 테스트
@WebMvcTest(UserController.class)
class UserControllerTest {
	
    @Nested
    class 회원_조회 {
    	
        @Test
        void 모든_회원_목록을_조회한다() {
        	// ...
        }
        
        @Test
        void limit_파라미터가_누락되었다면_4xx를_응답한다() {
        	// ...
        }
    }
}

Controller 계층에 대한 테스트는 왜 작성하는걸까?
Controller가 본인의 책임을 다하는지 검증하기 위함이다.

'Controller의 책임'을 조금 더 구체화해보자.

  • 필수 파라미터가 누락되었는지 검증한다.
  • 의도된 형태로 응답한다.
  • 의도된 상태 코드로 응답한다.
  • 의도된 엔드포인트 + HTTP 메서드의 요청을 처리한다.

Controller 계층에 대한 테스트는 위 내용들만 검증하면 충분하다.
따라서, MockMvc를 이용한 슬라이드 테스트로 작성하길 권장한다.

Service 계층 테스트
@ExtendWith(MockitoExtension.class)
class FruitServiceTest {
	
    @Test
    void 과일의_상태를_판매_불가로_만든다() {
    	// given
        Fruit fruit = new Fruit(1L, Status.ON_SALE);
        Fruit updatedFruit = new Fruit(1L, Status.NOT_FOR_SALE);
        
        when(fruitRepository.findById(1L))
        	.thenReturn(fruit);
        when(fruitRepository.updateStatus(fruit, Status.NOT_FOR_SALE))
        	.thenReturn(updatedFruit);
            
        // ...
    }

Service 계층에 대한 테스트의 목적도 유사하다.
Service가 본인의 책임을 다하는지 검증하기 위함이다.

Service는 비즈니스 로직을 다룬다.
즉, 비즈니스 요구사항대로 적절히 동작하는지를 테스트해야 한다.

나는 여기서도 Repository를 모킹할 것을 권장한다.
반드시 모킹해야하는건 아니지만, 다음과 같은 이점이 있다.

  • DB를 띄우지 않아도 되므로, 테스트 실행 속도가 빨라진다.
  • 테스트 실패 원인이 오직 서비스 혹은 테스트 코드에만 있다. (Repository 구현체에 의해 실패하지 않는다)

위와 같은 이점이 덕에, "Service 계층의 책임을 테스트한다"라는 의도가 명확해진다.

통합 테스트
class FruitServiceIntegrationTest {

	@Nested
    class 과일_판매는_원자적으로_동작한다 {
    	
        @Test
        void 회원_잔고_수정에_실패하면_과일_재고도_수정되지_않는다() {
        	// ...
        }
        
        @Test
        void 모든_작업이_성공하면_모두_반영된다() {
        	// ...
        }
    }
}

모킹 기반 단위 테스트만으로는 검증할 수 없는 책임도 있다.
대표적인 예시로, Spring AOP 기능이 있다.

트랜잭션 경계(@Transactional), 재시도(@Retryable) 등의 기능은, 객체가 지닌 책임임에도 단위 테스트로는 검증할 수 없다.

이런 기능에 한해 통합 테스트로 구현하도록 하자.
단위 테스트와 통합 테스트의 역할을 다음과 같이 구분할 수 있다.

  • 단위 테스트: 순수한 객체의 동작을 테스트한다
  • 통합 테스트: 외부 환경(Spring 등)에 의존하는 동작을 테스트한다
Repository 계층 테스트
@JdbcTest
class UserRepositoryTest {
	
    @Test
    void 회원_정보를_저장한다() {
    	// given
        User user = new User("Watson");
        
        // when
        User savedUser = userRepository.save(user);

		// then
        String findSql = """
        		SELECT *
                FROM user
                WHERE id = ?
                """;
        User foundUser =jdbcTemplate.query(findSql, userRowMapper(), savedUser.id()); 
        
        assertThat(foundUser).isEqualTo(savedUser);
    }
}

Repository 계층에 대한 테스트는 개념적으로 간단하다.
데이터베이스 로직이 제대로 구현되었는지 검증하면 된다.
Repository는 비즈니스 로직도 모르므로, 검증해야 할 케이스도 훨씬 간단하다.

또한, DB에 실제로 반영되었는지 검증하길 권고한다.
단, 운영 환경과 똑같은 DB를 사용할 필요는 없다.
특이 케이스(특정 DB 기능을 사용한다거나)가 아니라면, 인메모리 DB를 사용해 테스트 속도를 높이길 권장한다.

E2E 테스트
class UserE2eTest extends IntegrationTestBase {

    @Test
    void 회원가입_후_로그인한다() {
		// 1. 회원가입
        given()
            .contentType(ContentType.JSON)
            .body(new SignUpRequest("아이디", "비밀번호"))
        	.when()
            .post("/api/authorizations/users")
        	.then()
            .statusCode(200);
            
        // 2. 로그인 및 JWT 발급 검증
        String jwtToken = given()
            .contentType(ContentType.JSON)
            .body(new LoginRequest("아이디", "비밀번호")) 
        	.when()
            .post("/api/authorizations/users/login") 
        	.then()
            .statusCode(200)
            .body("accessToken", notNullValue());
    }
}

통합 테스트와 단위 테스트를 통해 대부분을 검증할 수 있지만, 하나 부족한게 있다.
애플리케이션이 실제 환경에서도 잘 동작하는지 검증하려면, 결국 E2E 테스트가 필요해진다.

E2E 테스트의 목적을 생각하면, 실제 운영 환경과 최대한 똑같은 환경에서 테스트를 수행해야 한다.
이를 위해서 Testcontainers 사용을 고려해보자.

E2E 테스트는 Spring 컨테이너를 띄워야 하며, Testcontainers를 사용하면 도커 컨테이너를 띄우는 시간도 필요해진다.
따라서, 세세한 엣지 케이스까지 E2E로 작성하기보단, 사용자가 실제로 이 API를 호출했을 때도 정상 동작하는지 테스트하는걸 목표로 두고 작성하자.

트랜잭션 분리 기준

트랜잭션은 작업의 원자성을 보장하고 싶을 때 사용할 수 있는 아주 좋은 도구다.

그렇다면, 모든 작업을 하나의 트랜잭션에 묶는게 항상 좋은걸까?
이 고정관념을 벗어던지면, 트랜잭션을 어떨 때 분리해야 하는지 기준을 잡을 수 있어진다.

크게 다음과 같은 관점을 고려해보자.

  • 데이터 정합성 관점: 깨지면 즉시 문제가 되는가?
  • 동작의 개념 관점: 개념적으로 하나의 동작인가?
  • 동작의 실패 가능성 관점: 부가 동작이 실패할 확률이 높은가?
  • 유지보수 관점: 분리하려면 구현이 많이 복잡해지는가?
  • 트랜잭션 비용 관점: 묶으면 롱 트랜잭션이 되는가?

이 중 몇가지는 예시까지 같이 확인해보자.

데이터 정합성 관점
물건 재고를 차감한다
	  ↓ 
주문 정보를 생성한다
	  ↓ 
회원의 잔고를 줄인다

위와 같은 주문 기능이 있다고 가정해보자.
중간에 실패했을 때, 하나의 트랜잭션으로 묶이지 않았다면 어떻게 될까?

물건 재고를 차감한다
	  ↓ 
주문 정보를 생성한다
	  ↓ 
회원의 잔고를 줄인다 ⬅ 실패!

위와 같이, 물건의 재고는 줄어들고 주문 정보는 생겼으나, 회원의 잔고가 줄어들지 않았다.
데이터 정합성이 깨졌으며, 즉시 문제가 될 수 있는 케이스다.

예약을 취소한다
	  ↓ 
1순위 대기를 예약으로 승격한다

반면, 위와 같은 작업도 있다.
이 작업도, 중간에 실패하면 데이터 정합성이 깨진다.
하지만, 즉시 문제가 되진 않으니, 추후에 해결해도 괜찮다.

새로운 회원을 생성한다
	  ↓ 
회원가입 성공 이메일을 발송한다

반면, 이처럼 데이터 정합성과 관련 없는 작업도 있다.
이렇게 데이터 정합성이 문제가 되지 않을수록, 별도 트랜잭션으로 분리하는걸 고려해볼만 하다.

동작의 개념 관점
물건 재고를 차감한다
	  ↓ 
주문 정보를 생성한다

앞서 사용한 예시를 다시 보자.
주문을 생성하고 물건 재고를 차감하는건, 개념적으로 하나의 동작이다.
따라서, 데이터 정합성 문제가 발생하지 않는다 하더라도, 하나의 동작으로 묶는게 자연스럽다.

주문을 취소한다
	  ↓ 
주문 취소 히스토리를 생성한다

반면, 이렇게 '메인 동작'과 '부가 동작'으로 구분할 수 있는 기능도 있다.
이 경우엔, 하나의 트랜잭션으로 묶는게 오히려 부적절할 수 있다.

'주문 취소 히스토리를 생성한다'가 실패하면 '주문을 취소한다'까지 롤백되어야 하는가?
도메인 관점에서 생각해보자.
사용자는 "히스토리 생성에 실패해서 주문이 취소되지 않았습니다"라는 메시지를 납득할 수 있을까?

동작의 실패 가능성 관점
주문을 취소한다
	  ↓ 
주문 취소 완료 이메일을 발송한다

'이메일 발송'처럼, 외부 API에 의존하는 기능들이 존재한다.
이런 기능은 다른 기능에 비해 실패 확률이 높다.

이렇게 부가 기능의 실패 확률이 높을수록, 트랜잭션 분리를 고려할 만 하다.
앞선 예시처럼 "이메일 발송에 실패해서 주문이 취소되지 않았습니다"라는 메시지를 볼 확률이 높은 상황이기 때문이다.

주문을 취소한다
	  ↓ 
주문 취소 로그를 남긴다

반면, '히스토리 저장'이나 '로그 기록'처럼 실패 확률이 낮은 동작들도 있다.

이런 기능은, 별도의 트랜잭션으로 분리해서 얻는 이점은 적다.
따라서, 추가적인 이유가 없다면 하나의 트랜잭션으로 관리해도 무방하다.
