우리 모두를 합친 것보다 더 현명한 사람은 없다.
- 켄 블랜차드(Ken Blanchard)

협력

1. 협력의 구성

협력은 한 객체가 다른 객체에게 도움을 요청할 때 시작된다
즉, 메시지를 보낼 때 시작된다

도움을 요청받은 객체는 또 다른 객체에게 도움을 요청할 수 있다
즉, 협력은 다수의 연쇄적인 요청과 응답의 흐름으로 구성된다

2. 일상생활 속 협력


다들 스마트폰 하나쯤 갖고 있지 않은가? 당신이 아이폰으로 카톡을 확인하는 과정에서도 우리는 객체간 협력을 찾아볼 수 있다

  1. 누군가 당신에게 카톡을 확인하라고 요청하면서 협력이 시작된다
  2. 당신이 아이폰에게 카카오톡 앱을 요청한다
  3. 아이폰이 카카오톡에게 앱 실행을 요청한다
  4. 카카오톡이 카톡 앱을 실행해, 아이폰의 요청에 응답한다
  5. 카톡 앱의 실행은, 당신이 아이폰에게 요청한 것에 대한 응답이기도 하다
  6. 당신은 카톡 앱에게 카톡 내역을 요청한다
  7. 카톡 앱은 카톡 내역을 보여줌으로써, 당신의 요청에 응답한다

위의 협력에 보이는 요청과 응답에 초점을 맞춰보자

  • 누군가 아이폰에게 앱을 요청한다는 것은, 아이폰이 앱을 제공할 의무가 있으며, 앱을 제공하기 위한 방법을 알고 있음을 의미한다
  • 누군가 카카오톡에게 카톡 앱 실행을 요청한다는 것은, 카카오톡이 카톡 앱을 실행할 의무가 있으며, 앱을 실행하기 위한 방법을 알고 있음을 의미한다

즉, 어느 객체가 어떤 요청을 받아들일 수 있는 이유는, 그 요청에 대해 적절한 방식으로 응답하는데 필요한 지식과 행동 방식을 가지고 있기 때문이다

책임

객체지향 개발에서 가장 중요한 능력은, 책임을 능숙하게 객체에 할당하는 것이다
책임을 어떻게 구현할지는, 모든 객체와 책임이 제자리를 잡은 후에 고민해도 늦지 않다
책임을 구현하는 방법에 대한 고민은 최대한 뒤로 미루자

1. 책임이란?

객체지향 세계에서는 어떤 객체가 다음 중 하나라도 만족할 경우, 해당 객체가 책임을 가진다고 말한다

  1. 어떤 요청에 대해 대답해줄 수 있음
  2. 어떤 행동에 대해 적절한 행동을 할 의무가 있음

이전에 든 예시를 보면 각 객체의 책임은 다음과 같다

  1. 당신은 누군가의 ‘카톡을 확인하라’는 요청에 응답해야 하므로, ‘카톡을 확인할’ 책임을 지게 된다
  2. 아이폰은 ‘카톡 앱을 제공하라’는 요청에 응답해야 하므로, ‘카톡 앱을 제공할’ 책임을 지게 된다
  3. 카카오톡은 ‘카톡 앱을 실행하라’는 요청에 응답해야 하므로, ‘카톡 앱을 실행할’ 책임을 지게 된다
    또한, ‘카톡 내역을 제공해라’는 요청에 응답해야 하므로, ‘카톡 내역을 제공할’ 책임도 지게 된다

위와 같이, 어떤 대상에 대한 요청은, 그 대상이 요청을 처리할 책임이 있음을 암시한다

2. 책임의 분류

객체의 책임은 doing(무엇을 할 수 있는가)과 knowing(무엇을 알고 있는가)으로 구성된다

크레이그 라만이 제시한 객체의 책임에 대한 두 가지 범주는 다음과 같다

  1. 하는 것(doing)
    • 객체를 생성하거나 계산을 하는 등, 스스로 하는 것
    • 다른 객체의 행동을 시작시키는 것
    • 다른 객체의 활동을 제어하고 조절하는 것
  2. 아는 것(Knowing)
    • 개인적인 정보에 관해 아는 것
    • 관련된 객체에 관해 아는 것
    • 자신이 유도하거나 계산할 수 있는 것에 관해 아는 것

이전에 든 예시를 보면, 각 객체의 책임은 다음과 같이 분류할 수 있다

  1. 당신은 아이폰에게 카톡 앱을 요청한 후, 카톡 앱에게 카톡 내역을 제공하라고 요청한다
    즉, 다른 객체들의 활동을 제어하고 조율하고 있다
    → 당신은 하는 것(doing)과 관련된 책임을 수행한다

  2. 아이폰은 카톡 앱에게 실행을 요청한다
    즉, 다른 객체의 행동을 시작시키고 있다
    → 아이폰은 하는 것(doing)과 관련된 책임을 수행한다

  3. 카톡 앱의 경우 ‘앱 실행’에 대한 책임과, ‘카톡 내역을 제공’할 책임을 지닌다

    1. 앱 실행에 대한 책임은 ‘객체를 생성하거나 계산을 하는 등의 스스로 하는 것’의 범주에 해당하므로, 카톡 앱은 하는 것(doing)과 관련된 책임을 수행한다
    2. 카톡 내역을 제공하는 책임은 ‘자신이 유도하거나 계산할 수 있는 것에 관해 아는 것’에 해당하므로, 카톡 앱은 아는 것(knowing)에 관련된 책임도 수행한다

3. 책임과 공용 인터페이스

객체의 책임을 이야기할 때는, 일반적으로 외부에서 접근 가능한 공용 서비스의 관점에서 이야기한다

즉, 책임은 외부에 제공해줄 수 있는 정보(아는 것)와 외부에 제공해줄 수 있는 서비스(하는 것)의 목록이라고 볼 수 있다

따라서, 책임은 객체의 공용 인터페이스(Public interface)를 구성한다
(공용 인터페이스는 캡슐화로 이어지는데, 이는 5장에서 자세히 설명할 것이다)

4. 책임과 메시지

객체는 다른 객체로부터 요청이 전송됐을 경우에만 자신의 책임을 수행한다

  • 아이폰이 앱을 실행할 때는, 오직 사용자로부터 요청이 들어왔을 때뿐이다

이처럼 객체가 다른 객체에게 책임을 수행하도록 요청하는 것을 메시지 전송(Message-send)이라고 한다
따라서, 두 객체 간의 협력은 메시지를 통해서 이루어진다

  • 이 때, 메시지를 전송하는 객체는 송신자, 메시지를 받아 요청을 처리하는 객체는 수신자라고 한다

하지만, 책임과 메시지의 수준이 같지 않다는 것에 유의하자

  • 책임은, 객체가 협력에 참여하기 위해 수행해야 하는 행위를 개략적으로 서술한 것이다
  • 협력을 실제로 메시지로 변환할 때는, 하나의 책임이 여러 메시지로 분할되는 것이 일반적이다

5. 책임과 협력의 관점 차이

책임은, 요청을 수신하는 객체의 관점에서 무엇을 할 수 있는지를 나열한다

  • 아이폰은 요청받은 앱을 실행할 책임이 있다
  • 이것은, 다른 객체의 존재 여부와 상관없이 아이폰이 외부에 제공할 수 있는 행위의 일부다

협력은, 요청을 송수신하는 두 객체 사이의 관계를 강조한다

  • 당신은 아이폰에게 앱을 실행하라고 요청한다
  • 당신은 아이폰이 이해할 수 있는 메시지를 전송할 수 있고, 아이폰은 당신이 전송하는 메시지에 대해 적절한 책임을 수행할 수 있음을 의미한다

역할

역할이라는 개념을 사용하면, 유사한 협력을 추상화해서 다음과 같은 이점을 누릴 수 있다
1. 복잡한 협력을 단순화할 수 있다(단순성)
2. 다양한 객체가 협력에 참여할 수 있게 되어, 협력이 유연해진다(유연성)
3. 다양한 객체들이 동일한 협력에 참여할 수 있게 되어, 객체의 재사용성이 높아진다(재사용성)

1. 역할과 추상화

우리는 이전에 당신이 아이폰으로 카톡을 확인하는 예시를 사용했다
해당 예시에 등장한 객체들 각각의 책임과 역할을 확인해보자

  1. 당신이 ‘앱을 요청한다’라는 책임과 ‘앱을 사용한다’라는 책임을 지는 것은 무엇을 의미하는가?
    당신이 ‘사용자’라는 역할을 수행하고 있음을 의미한다

  2. 아이폰이 ‘앱을 제공한다’라는 책임을 지는 것은 무엇을 의미하는가?
    아이폰이 ‘스마트폰’이라는 역할을 수행하고 있음을 의미한다

  3. 카톡이 ‘앱을 실행한다’라는 책임을 지고, 사용자에게 ‘사용된다’라는 책임을 지는 것은 무엇을 의미하는가?
    카톡이 ‘앱’이라는 역할을 수행하고 있음을 의미한다

즉, 어떤 객체가 수행하는 책임의 집합은, 객체가 협력 안에서 수행하는 역할을 암시한다
또한, 역할은 협력의 추상화를 가능하게 해 재사용 가능하고 유연한 객체지향 설계를 낳는다

이해가 가지 않는다면, 역할을 통해 다음 상황들을 어떻게 추상화할 수 있을지 생각해보라

  1. 당신이 아이폰으로 카톡을 확인하는 상황
  2. 당신이 갤럭시로 카톡을 확인하는 상황
  3. 내가 아이폰으로 카톡을 확인하는 상황
  4. 내가 LG폰으로 네이버 웹툰을 보는 상황

모두 ‘사용자’가 ‘스마트폰’으로 ‘앱’을 사용하는 상황으로 추상화할 수 있다
즉, 역할이라는 개념을 사용하면, 위의 상황을 모두 다음과 같이 하나의 협력으로 추상화할 수 있다

  1. 누군가 사용자에게 앱을 사용하라고 요청하면서 협력이 시작된다
  2. 사용자가 스마트폰에게 앱을 요청한다
  3. 스마트폰이 앱에게 실행을 요청한다
  4. 앱이 실행해, 스마트폰의 요청에 응답한다
  5. 앱의 실행은, 사용자가 스마트폰에게 요청한 것에 대한 응답이기도 하다
  6. 사용자는 앱에게 사용을 요청한다
  7. 앱은 사용됨으로써, 사용자의 요청에 응답한다

2. 역할과 대체 가능성

역할은 협력 내에서 다른 객체로 대체할 수 있음을 나타내는 표식 역할을 한다

앞에서 ‘스마트폰’이라는 역할은 ‘아이폰’으로 대체할 수도 있고, ‘갤럭시’로 대체할 수도 있다
또한, ‘아이폰’과 ‘갤럭시’ 뿐 아니라, ‘스마트폰’ 역할을 수행할 수 있는 어떤 객체라도 협력에 참여할 수 있게 된다

그렇다고, 어느 객체이든지 역할을 대체할 수 있는 것은 아니다

  • 당연하게도, 당신은 ‘스마트폰’ 역할을 대체할 수 없다

객체가 어느 역할을 대체할 수 있기 위해서는, 해당 역할이 수신할 수 있는 모든 메시지를 동일한 방식으로 이해해야 한다

  • 당신은 ‘앱을 제공하라’라는 메시지를 동일한 방식으로 이해할 수 없기 때문에, 스마트폰 역할을 대체할 수 없다

즉, 어떤 객체들이 동일한 역할을 수행한다는 것은, 해당 객체들이 동일한 메시지를 수신할 수 있다는 것이고, 이는 해당 협력 내에서 동일한 책임의 집합을 수행할 수 있다는 것을 의미한다

협력이 객체의 형태를 결정한다

1. 객체지향에 대한 잘못된 선입견

  1. 객체는 데이터를 저장하기 위해 존재한다?

    • 아니다. 객체가 존재하는 이유는 행위를 수행하며 협력에 참여하기 위해서다
    • 물론 객체는 상태의 일부로 데이터를 존재하지만, 이는 행위를 수행하기 위한 재료일 뿐이다

  2. 객체지향은 클래스와 클래스 간의 관계를 표현하는 정적인 측면에 중점을 둔다?

    • 아니다. 중요한 것은 정적인 클래스가 아닌, 협력에 참여하는 동적인 객체다
    • 클래스는 단지, 객체를 표현하기 위한 구현 메커니즘일 뿐이다
    • 즉, 객체지향의 핵심은 객체가 협력 안에서 어떤 책임과 역할을 수행할 것인지를 결정하는 것이다

2. 협력이라는 문맥을 고려해라

한번 이전 예제에서 사용한 ‘당신’이라는 객체를 만들어 보자

  • ‘당신’의 인스턴스를 모델링할 경우, 당신의 이름/키/성별/몸무게 등과 같은 정보부터 떠올릴 것이고, 그 내용을 기반으로 클래스를 개발할 것이다

언뜻 그럴싸해 보이지만, 다시 한번 생각해 보자
위의 내용이 ‘사용자가 스마트폰을 통해 앱을 실행’하는 협력에 ‘사용자’ 역할로 참여할 때 중요한 내용인가?

이런 문제가 발생한 것은, 객체를 협력이라는 문맥에서 떼어놓은 채 설계했기 때문이다

객체는 섬이 아니다
객체는 행위를 통해 협력에 참여하는 존재라는 것을 잊지 말자

3. 협력 안에서 책임을 분배해라

올바른 객체를 설계하기 위해서는, 견고하고 깔끔한 협력을 설계하는 것이 선행되어야 한다

  • 협력을 설계한다는 것은, 협력에 참여할 객체들이 주고받을 요청과 응답의 흐름을 결정한다는 것을 의미한다
  • 이렇게 결정된 요청과 흐름은 곧, 객체가 협력에 참여하기 위해 수행할 책임이 되고, 책임은 곧 객체가 외부에 제공하게 될 행동이 된다

즉, 올바른 객체를 설계하는 흐름은 다음과 같다

  1. 협력을 설계한다(객체간의 요청과 응답의 흐름을 결정한다)
  2. 요청과 흐름을 통해 객체가 수행할 책임이 결정된다
  3. 결정된 책임을 통해, 객체가 외부에 제공할 행동이 결정된다
  4. 결정된 행동을 통해, 객체가 지녀야 할 데이터를 결정한다
  5. 결정된 행동과 데이터를 통해, 클래스의 구현 방법을 결정한다

여기서 가장 중요한 것은, 협력과 책임이 결정된 후에야 데이터와 클래스를 고민하기 시작한다는 것이다

객체지향 설계 기법

1. 책임 주도 설계(Responsibility-Driven Design)

협력에 필요한 책임들을 먼저 식별한 후, 적합한 객체에게 책임을 할당하는 방식이다
즉, 말 그대로 책임을 중심으로 시스템을 설계하는 방식을 말한다

자세히 서술하자면, 다음과 같은 방식이다

  1. 시스템의 책임을 파악한다
  2. 시스템의 책임을 더 작은 규모의 책임으로 분할한다
  3. 각 책임을, 책임을 수행할 적절한 객체에게 할당한다
  4. 만일 객체가 책임을 수행할 때 도움이 필요하다면, 이를 책임질 적절한 객체 혹은 역할에게 도움을 요청한다

4번에서 요청된 작업을 수행하는 일은, 해당 작업을 위임받은 객체의 책임이 된다
이를 통해 객체들 간의 협력 관계가 만들어진다

만일 한 책임을 여러 종류의 객체가 수행할 수 있다면, 협력자는 객체가 아니라 역할로 추상화된다

2. 디자인 패턴(Design Pattern)

전문가들이 반복적으로 사용하는 해결 방법을 정의해 놓은 설계 템플릿의 모음이다
즉, 어떤 문제에 대해 이미 제시된 훌륭한 결과물들을 말한다

디자인 패턴은 다음과 같은 쌍으로 정의된다

  1. 반복적으로 발생하는 문제
  2. 해당 문제에 대한 해법

즉, 해결하려고 하는 문제가 무엇인지를 명확하게 서술하고, 패턴을 적용할 수 있는 상황과 없는 상황을 함께 설명한다
또한, 특정 상황에 해당 패턴이 왜 효과적인지에 대한 이유를 설명한다

디자인 패턴은 이미 책임-주도 설계의 절차를 순차적으로 잘 따른 훌륭한 결과물이다
즉, 적절하게 디자인 패턴을 적용하는 것은, 객체지향 설계의 지름길을 이용하는 것이다

3. 테스트 주도 개발(Test-Driven Development)

테스트를 먼저 작성한 후, 테스트를 통과하는 구체적인 코드를 추가하며 애플리케이션을 완성하는 방식이다

개략적인 절차는 다음과 같다

  1. 실패하는 테스트를 작성한다
  2. 테스트를 통과하는 가장 간단한 코드를 작성한다(이 때는 코드 중복이 존재해도 괜찮다)
  3. 리팩터링을 통해 코드 중복을 제거한다

테스트 주도 개발의 장점은 다음과 같다

  1. 응집도가 높고 결합도가 낮은 클래스를 개발하기 좋다
  2. 자연스럽게 테스트 코드가 생성된다

단, 테스트 코드는 부가적인 이점일 뿐이고, TDD를 사용하는 가장 큰 목적은 객체지향 설계라는 것을 잊지 말자

하지만 테스트 주도 개발은 객체지향에 대한 깊이 있는 지식과 경험을 요구한다는 단점이 있다
