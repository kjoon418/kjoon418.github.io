개요

나는 주로 Spring Data JPA를 사용해 DB 관련 로직을 처리해 왔다.
Spring Data JPA를 사용하기 위해, 데이터를 담는 객체들은 데이터베이스의 각 레코드와 1:1 매핑될 수 있는 엔티티 객체로 만들었다.
이 방식만 사용할 때는 자연스럽다 생각했는데, 저번에 초록 스터디에 참여해 순수 Java 코드로만 콘솔 기반 애플리케이션을 만들며 새로운 의문이 생겼다.

내가 생각하는 좋은 객체지향이란 '본인의 책임을 다하는 객체들의 협업으로 동작하는 시스템'인데, 지금처럼 Entity 객체를 단순 데이터 저장용으로만 사용하는 것이 최선일까?
어쩌면 나는 지금까지 Service 객체에 과도한 책임을 짊어지게 했던 것은 아닐까?

자신의 상태 변경은 스스로 책임지자

@Entity
public class Order {
    @Enumerated(EnumType.STRING)
    private OrderStatus status;

    public void cancel() {
        if (this.status == OrderStatus.SHIPPED) {
            throw new IllegalStateException("배송된 주문은 취소할 수 없습니다.");
        }
        this.status = OrderStatus.CANCELLED;
    }
}

위의 코드를 살펴보면, 상태를 변경하는 로직을 Order 엔티티가 스스로 담당하고 있다.
status에 Setter를 두어 Service 객체 측에서 order.setStauts()를 호출하는 것과 비교하면 어떤 장점이 있을까?

내가 가장 먼저 떠올린 장점은, 검증 로직의 위치가 자연스럽다는 것이다.
여러분이 이 프로젝트를 아예 모르는 외부 개발자라고 가정해보자. Order에 대한 검증 로직을 찾고 싶다면 어느 클래스를 먼저 살펴볼 것 같은가?

그 다음으로 떠올린 장점은, 중복 코드를 방지할 수 있다는 것이다.
위와 같이 "배송된 주문은 취소할 수 없음"이라는 규칙이 프로젝트 전체에 적용되어야 한다면, Order.status를 변경해야 하는 모든 서비스 객체에서 위 검증 로직을 작성해야 할 것이다.
이런 중복 코드가 생기면 하나의 요구사항 수정이 필요할 때 여러 클래스를 수정해야 하고, 깜빡하고 수정하지 못하는 휴먼 에러가 발생하기 쉬워진다.

위 방식으로 중복 코드를 제거하면, 자연스럽게 엔티티의 일관성까지 보장할 수 있다.
모든 Order 엔티티는 상태 변경에 대해 똑같은 규칙을 적용할 것이다. 어디서는 허용하고 어디서는 허용하지 않는 불일치를 아주 간단하게 방지할 수 있다!

반대로 엔티티가 가지면 안되는 책임은?

@Transactional
public void transferMoney(Long fromId, Long toId, int amount) {
    Member from = memberRepository.findById(fromId).orElseThrow();
    Member to = memberRepository.findById(toId).orElseThrow();

    from.withdraw(amount);
    to.deposit(amount);
}

만약 Entity 내부에서 처리할 수 없어서 여러 도메인 간 협력이 필요하다면 Service가 책임지는 것이 더 적절하다 볼 수 있다.
반대로 얘기하면, 외부에 의존하지 않아도 되는 로직은 Entity가 책임지는 것이 적절할 수 있다.
외부에 의존하지 않는다고 반드시 Entity가 책임져야 하는 것은 아니지만, Entity가 책임지는 방향을 고려해 보고 더 자연스러운 방법을 선택하도록 하자.

별개로, 도메인 모델이 단순하고 CRUD 중심이라면 대부분의 로직을 Service에 두는 것이 더욱 간편하고 직관적일 수 있다.

Persistence-agnostic

Persistnce - 영속성(데이터를 영속적인 저장소에 저장하는 것)
agnostic - 무관한, 독립적인

즉, 데이터 저장 방식에 종속적이지 않은로직을 Persistence-agnostic한 로직이라고 부른다.
다르게 말하면 DB 저장 기술과 관계 없는 순수한 비즈니스 로직이라고 표현할 수 있다.
JPA Entity는 위에서 말한 것 이외에도 Persistence-agnostic한 로직만을 지녀야 하는데, 그리 어렵지 않으니 아래에서 간단한 예시 코드로 이해해 보자.

@Entity
public class Order {
    @PersistenceContext
    private EntityManager em;

    public void cancel() {
        this.status = OrderStatus.CANCELLED;
        em.persist(this); // JPA에 의존
    }
}

이 Entity는 EntityManager를 직접 의존하고 있다. 설명을 듣지 않아도, 개발자의 직감이 부적절한 코드라고 외치고 있을 것이다.

이미 보자마자 이상하다는 것을 느꼈을 테지만, 실제로 이 클래스가 어떤 문제를 야기하는지 살펴보자.

잠재적으로 여러 가지 문제가 있겠지만, 제일 큰 문제는 JPA 없이 실행할 수 없다는 것이다.
이는 당신이 만약 Spring Data JPA가 아닌 다른 기술을 사용하겠다고 마음 먹었을 때 굉장한 양의 코드 변경을 초래할 것이다.
또한 JPA에 의존적이라는 문제 덕분에, Spring Boot에 독립적인 테스트 코드도 작성할 수 없다.

여러분 대다수가 이미 그리 하고 있겠지만, Persistence에 의존하는 로직은 최소한 Service가 지니도록 하자.
일반적으로 트랜잭션의 생명 주기를 서비스 계층에서 담당하는 것 역시 비슷한 목적이라고 생각한다.
