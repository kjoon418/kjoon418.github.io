개요

레벨 2의 첫 프로그래밍 미션인 '방탈출 예약 관리 미션'을 끝마쳤다.
1주일이라는 짧은 기간동안 진행된 미션이었지만, 그 과정에서 배운 점을 기록해보도록 하겠다.

깨달음

도메인과 DB의 타입은 같을 필요 없다.

CREATE TABLE orders (
	id INT NOT NULL AUTO_INCREMENT,
    price INT NOT NULL,
    date VARCHAR(255) NOT NULL,
    PRIMARY KEY (id)
);
public record Order(
	int id,
    int price,
    // 데이터베이스의 타입과 맞추기 위해 String 사용
    String date
) {
}

DB의 orders 테이블은 date 컬럼을 VARCHAR 타입으로 지니고 있다.
그렇다고 애플리케이션의 Order.date의 타입도 String이어야 할까?

public record Order(
	int id,
    int price,
    // 꼭 String으로 맞출 필요 없다
    LocalDate date
) {
}

데이터베이스의 스키마에 맞추는 것도 좋지만, "도메인에서 어떤 연산이 필요한지"를 먼저 고려해보자.

String을 사용한다면, 시간 값이 잘못되었을 때 어떻게 검증할 것인가?
LocalDate를 사용한다면, 아주 쉽게 시간 값을 검증할 수 있다.
이 경우엔 '시간에 대한 연산'이 필요하니, String보다 LocalTime이 적절하다 볼 수 있다.

서비스를 나누는 기준은?

다음과 같은 기능이 필요하다고 가정해보자.
1. 방탈출 예약 생성/조회/삭제
2. (관리자 기능) 방탈출 테마 생성/조회/삭제
3. (관리자 기능) 방탈출 예약 가능 시간 생성/조회/삭제

이때, 다음과 같은 도메인이 존재한다.
1. Time(예약 시간을 표현하는 도메인)
2. Theme(방탈출 테마를 표현하는 도메인)
3. Reservation(예약을 표현하는 도메인)

'도메인 간의 연관성'을 중심으로 나눌 수도 있지만, 그 기준으로 서비스를 나누다 보면, 한 서비스가 너무 비대해지기 쉽다.

'도메인 간의 연관성'을 중심으로, 서비스를 구현한다면 어떻게 될까?

Reservation(예약)은 Time(예약 시간)과 Theme(테마)를 의존한다.
즉, 예약 관련 기능, 테마 관련 기능, 시간 관련 기능은 모두 하나의 서비스에 배치해야 한다.

-> ReservationService에서 모두 처리한다.

Reservation은 결국 Time과 Theme과 밀접하게 연관되어 있다.
'도메인 간의 연관성'을 기준으로 서비스를 나누다보면, 하나의 서비스가 비대해지기 쉽다.
그렇다면 어떤 기준을 사용해야 할까?

1. 예약 생성/조회/삭제: 예약 관리 유스케이스
2. 테마 생성/조회/삭제: 테마 관리 유스케이스
3. 시간 생성/조회/삭제: 시간 관리 유스케이스

따라서, 다음과 같은 서비스가 필요하다.
1. ReservationService
2. ThemeService
3. TimeService

'어떤 유스케이스를 담당하는가' 혹은 '변경 이유가 같은가'를 기준으로 고민해보자.

아마 당신은 무의식적으로 이 방법을 사용하고 있었을 것이다.
이 기준을 의식해서, 복잡한 상황을 맞이하더라도 서비스를 쉽게 분리해보자.

참고로, 이 기준으로 정했다면 '서비스가 서비스를 의존'하지 않도록 하자.
유스케이스가 또 다른 유스케이스를 호출하는 구조가 되니, 흐름을 이해하기 매우 어려워진다.

어떤 로직은 서비스에, 어떤 로직은 도메인에 둘까?

결론부터 말하면, 다음과 같다.

  • 모든 상황에 적용되는 규칙은 도메인에 둔다.
  • 특정 유스케이스에만 적용되는 규칙은 서비스에 둔다.
public record User(
	String name
) {
	public User {
    	if (name == null) {
        	// 모든 회원은 항상 이름이 있어야 한다.
        	throw new IllegalArgumentException("회원은 이름이 필요합니다.");
        }
    }
}

"모든 회원은 이름이 있어야 한다"라는 규칙이 존재한다면, 이 규칙은 도메인에 두는게 바람직하다.
규칙을 도메인에 배치했으니, 어느 서비스에서든 일관된 규칙으로 도메인을 사용할 수 있다.

물론, 모든 상황에 적용되는 규칙임에도 도메인에 두기 어려울 때가 있다.
(ex_ 검증을 위해 레포지토리의 도움이 필요한 기능, 많은 도메인이 협력해야 하는 기능 등)
이런 규칙은 가능하면 도메인에 두되, 어렵다면 서비스에 두도록 타협해보자.

public class FruitService {

	// ...
	
    public void saveFruit(String fruitName, Integer price) {
    	// 일반 유저가 과일을 저장할 땐 가격이 있어야 한다.
        if (price == null) {
        	throw new IllegalArgumentException("과일엔 가격이 필요합니다.");
        }
        Fruit fruit = new Fruit(fruitName, price);
        
        fruitRepository.save(fruit);
    }
    
    public Fruit getFruitByAdmin(String fruitName) {
    	// 관리자는 가격 없는 과일도 저장해야 한다.
        Fruit fruit = new Fruit(fruitName, price);
        
        fruitRepository.save(fruit);
    }
}

만일 '과일엔 가격이 있어야 한다'라는 규칙이 특정 유스케이스에서만 적용된다면, 이 규칙은 서비스가 구현하는게 바람직하다.
정확히는, 도메인의 불변식으로 구현할 수 없다.

물론, 이런 규칙도 도메인이 갖고, 서비스에서 도메인을 적절히 사용해서 해결할 수도 있다.
(ex_ Fruit.createByAdmin() 메서드로 생성할 때는 검증하지 않음)
그럼에도 "애플리케이션 전역에 같은 규칙을 적용한다"라고 보장하진 못하니, 위에서 '도메인에 규칙을 두어 해결'한 이점을 모두 누릴 수는 없다.

서비스 계층은 웹 환경에 독립적이어야 한다

@RestController
@RequestMapping("/fruits")
public FruitController {
	private final FruitService fruitService;
    
    // ...
    
    @PostMapping
    public void register(@RequestBody FruitRegisterRequest request) {
    	fruitService.register(request);
    }
}

위 예시의 FruitService는, 웹 HTTP 요청을 받아오기 위한 DTO인 FruitRegisterRequest를 의존하고 있다.
그러므로, 웹 요청 형태의 변경에 서비스가 영향 받기 쉽다.

원칙적으로 서비스 계층은 컨트롤러 계층과 무관하게 존재해야 한다.
갑자기 "웹 뿐 아니라 콘솔 UI로도 요청할 수 있게 구현해주세요"라는 요청이 생겼다고 가정해보자.
웹 환경에 의존하는 서비스를 콘솔 환경에서 재사용할 수 있겠는가?

@RestController
@RequestMapping("/fruits")
public FruitController {
	private final FruitService fruitService;
    private final FruitRequestMapper requestMapper;
    
    // ...
    
    @PostMapping
    public void register(@RequestBody FruitRegisterRequest request) {
    	// 서비스 계층을 위한 DTO인 FruitRegisterCommand로 변환한다
    	FruitRegisterCommand command = new FruitRegisterCommand(
        		request.name(),
                request.price()
        );
        
    	fruitService.register(command);
    }
}

서비스 계층을 위한 DTO인 FruitRegisterCommand를 만들어 해결했다.
이제 서비스는 웹 환경에 의존하지 않으니, 콘솔 UI 등 새로운 환경에 재사용할 수 있어졌다.

단! 이것은 엄격한 '클린 아키텍처' 관점의 이야기이다.
위 예시에서 알 수 있듯이, 서비스를 컨트롤러와 완전 분리하기 위해 적지 않은 보일러플레이트가 필요하다.
(새로운 DTO 클래스를 작성해야 하고, '웹 DTO → 서비스 DTO 변환 로직'을 구현해야 한다)

만일 '서비스용 DTO가 지닐 책임'이 없거나, '다른 환경으로 확장할 가능성'이 낮다면, 굳이 서비스와 컨트롤러를 엄격하게 분리하지 않아도 되겠다.
(혹은, 분리할 필요성이 느껴질 때 분리해도 문제 없을 가능성이 높다)

커스텀 예외는 '외부에서 예외를 다뤄야 할 때' 유용하다.

아래 예시는 "레포지토리가 비즈니스 요구사항을 알고 있다"라는 관점에서 부적절할 수 있다.
단순 예시로만 참고하자.

public class FruitRepository {
	
    // ...
	
    public void delete(long fruitId) {
    	try {
        	fruitDao.delete(fruitId);
        } catch (DataIntegrityViolationException e) {
        	throw new IllegalArgumentException("Order에서 참조 중인 과일은 제거할 수 없습니다.);
        }
    }
}

orders 테이블이 fruits 테이블을 참고하고 있다고 가정해보자.

orders 테이블에서 참조 중인 fruits 레코드는 삭제할 수 없다.
이를 레포지토리 계층에서 다음과 같이 처리하면, 외부(서비스)에서는 어떻게 될까?
(예외를 대충 잡고 있지만, 중요하지 않으니 넘어가자)

public class FruitService {
	
	// ...
    
    public void delete(long fruitId) {
    	try {
        	fruitRepository.delete(fruitId);
        } catch (IllegalArgumentException e) {
        	// 주문된 과일이라 실패한 삭제를 처리하는 로직
        }
    }
}

만일 "외래키로 인해 과일 삭제에 실패하면 ...하게 구현해주세요"라는 요구사항이 생기면 어떻게 될까?
서비스는 IllegalArgumentException를 "외래키로 인한 삭제 실패"로 가정하고 처리해야 한다.
(혹은 레포지토리가 던지는 예외 메시지를 확인해봐야 할 것이다)

만일 레포지토리가 '맥락을 잘 표현하는 커스텀 예외'를 사용했다면 어땠을까?

public class FruitService {
	
	// ...
    
    public void delete(long fruitId) {
    	try {
        	fruitRepository.delete(fruitId);
        } catch (OrderedFruitException e) {
        	// 주문된 과일이라 실패한 삭제를 처리하는 로직
        }
    }
}

FruitRepository가 IllegalArgumentException 대신 OrderedFruitException를 던지도록 개선해보자.
이 예외를 catch하는 측에서, 내가 어떤 예외 상황을 잡고 처리하는지 너무나 명확해진다.

이처럼, 커스텀 예외는 외부에서 이 예외를 다룰 이유가 있을 때 큰 이점을 지닌다.

마치며

Spring Data JPA를 사용할 때는 레포지토리 계층이 정형화되어 있으니, 서비스/도메인 계층만 잘 고민하면 됐었다.
그 때문에 레포지토리와 서비스가 어떻게 협업하는게 바람직한지 잘 고민하지 못했는데, 이번 미션 덕분에 어느 정도 감을 잡아 기쁘다.
