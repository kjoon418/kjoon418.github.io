0. 개요

작년부터 꿈꿔왔던 우아한테크코스에 합격하게 됐다.
아쉽게도 그동안 일정 탓에 회고를 작성하지 못했기에, 지원부터 최종 합격까지의 회고를 한 포스트에 간결하게 담아보고자 한다.

1. 지원서

우리는 당신이 어떤 사람인지, 무엇을 중요하게 생각하는지 알고 싶습니다.
가장 깊이 몰입하였던 도전 경험을 들려주세요. 프로그래밍이 아닌 다른 분야여도 좋습니다.

지원서를 쓸 당시에는 '이번에 붙진 못할 거니, 내년을 위해 미리 연습하는 것에 의의를 두자'라고 생각해서, 사실 그렇게까지 큰 공을 들이진 않았다.
지원서 분량은 최대 10,000자였지만, 분량만 억지로 채우는 것은 안하느니만 못하다고 생각했다.
그렇기에 심사 위원이 읽기 쉽게 작성하는 것을 목표로, 최대한 핵심만 담아 간결하게 작성했던 것 같다.
공백 제외 1,130자로 짧게 작성한 것을 나중 가서는 많이 후회했는데, 우테코 측에서 좋게 봐준 것 같아 다행이다.

도전 경험

내가 가장 깊게 몰입하고 가장 많이 성장한 도전은 무엇이었을까?

사실 살아오면서 그렇게 굉장한 도전을 해본 적이 없어서, 대체 무엇을 써야 할지 많이 고민했다.
역시 가장 힘들었지만 성공적으로 극복한 경험을 써야 한다 생각했고, 작년에 코딩 초보자 수준임에도 개발 동아리 운영진에 도전했던 일화를 적었다.

이제 막 Spring을 공부하기 시작한 초보였지만, 운이 좋게 동아리 운영진이 되어 멤버들을 가르쳐야 하는 상황에 놓였었다.
부담감도 심했지만 절대 민폐를 끼치긴 싫었기에, 단기간에 40시간 이상의 인프런 강의를 수강하고 복습하고 정리하여 내 지식으로 만들었던 경험을 진솔하게 작성했다.

단순히 '그렇게 공부했습니다'로 끝내면 심사 위원에게 별 감흥을 줄 수 없을 것 같아, 그때의 성장곡선을 유지하기 위해 지금도 많은 프로젝트를 진행하며 매번 새롭게 도전하고 있음을 강조했다.

지원 동기

내가 꼭 우아한테크코스에 합격하고 싶다고 생각한 이유는 무엇이었을까?

비록 우테코 측에서 지원 동기를 적어달라고 언급하진 않았지만, 단순히 도전 경험만으로 지원서를 끝내기에는 아쉬워서, 지원 동기를 같이 적으며 마무리해야겠다고 생각했다.

당시에 우테코를 너무나 동경하여 3년 내로 꼭 합격하겠다고 다짐했는데, 내가 왜 이 정도로 우테코를 가고 싶은지에 대해서는 제대로 정리해 본 적 없었다.
나도 잘 모르는 내용으로 타인을 설득할 순 없으니, 내 행적을 되짚어보며 내가 왜 우테코에 가고 싶은지를 천천히 고민해 보았다.

초록스터디 회고

  • 1주 차
  • 2주 차
  • 3주 차

2025년 초에 같은 대학교에서 우테코를 수료한 선배가 개최한 초록스터디에 참여했었는데, 여기서 우테코 출신 선배 개발자들에게 클린 코드와 객체지향에 대해 정말 많이 배웠다.

그 이전엔 클린 코드라고 하면 변수명을 제대로 짓는 것 정도만 알던 나에게, 초록 스터디에서의 코드 리뷰는 상당히 큰 충격으로 다가왔다.
이때부터 '가독성 좋은 코드를 짜자'를 좌우명으로 하여 열심히 노력해 왔기에, 이 계기가 된 우아한테크코스에 꼭 합격하고 싶다고 생각했던 것 같다.
나아가서, 우아한테크코스를 수료한 후 직접 초록 스터디를 주도하고 싶다는 열망도 생겼다.

이때 내가 느꼈던 감동을 모두 적기엔 너무 장황해질 것 같아, 최대한 진솔하면서도 간결하게 적어내려 노력했다.

2. 프리코스

목표

TDD(Test Driven Development)에 도전해 보자

초록 스터디 때도 그렇고, 프리코스 피드백도 그렇고, 우테코에서는 테스트 코드를 상당히 중요하게 여겼다.
『객체지향의 사실과 오해』의 내용을 프로젝트에 도입해 본 경험은 있으니, 이번에는 미뤄왔던 TDD(Test Driven Development)에 도전해야겠다 마음먹었다.

도전과 성장

미션은 전반적으로 쉽게 느껴졌지만, 배울 점은 많았다.
이번 기수의 프리코스는 총 3개의 미션과 1개의 오픈 미션(본인이 스스로 미션을 만들어 수행하는 것)으로 구성되었는데, 매주 하나씩 부족함을 깨닫고 성장하는 즐거운 시간이었다.

1주 차 미션 PR - 문자열 덧셈 계산기

1주 차는 책임 분배에 대해 고민하고 성장하는 시간이었다.
과제를 제출했을 때까지는 내 코드가 만족스러웠지만, 이후 다른 지원자들과 코드리뷰를 주고받으며 내가 너무 한 객체에 과한 책임을 부여하고 있다는 깨달음을 얻었다.

또한, 지금까지 내가 구현한 프로젝트 코드가 '모든 책임을 Service 객체에 떠넘기고 있는 게 아닌가'라는 점도 같이 고민해 볼 수 있었다.

2주 차 미션 PR - 자동차 경주

2주 차는 객체들이 서로 강결합하지 않는 것을 목표했다.

객체가 다른 객체를 의존한다면 테스트 코드 작성이 어려워진다고 느꼈기 때문에, 2주 차에는 객체가 다른 객체를 의존하지 않도록 설계해 봤다.
대신 Controller 계층에서 객체의 협력을 전담하도록 구현했는데, 그 덕에 각 객체에 대한 단위 테스트 작성이 수월해짐을 경험했다.

3주 차 미션 PR - 로또

3주 차는 특별한 것을 도전하진 않았고, 비교적 복잡한 요구사항을 준수하면서도 코드의 가독성을 유지하고 깔끔한 단위 테스트 작성을 목표로 했다.

본격적으로 TDD를 도입하진 않았지만, 객체를 설계할 때 부터 '테스트를 어떻게 짜야 할까?'를 고민했고, 그 덕에 테스트하기 용이한 구조로 설계할 수 있었다.

3. 오픈 미션

오픈 미션 레포지토리

기존의 4주차 미션을 대체하는 미션으로, 이번 기수부터 새롭게 도입됐다.
본인이 스스로 미션을 만들어서 수행하면 되는데, 나는 Kotlin으로 서버 프레임워크를 만드는 미션을 수행했다.

왜 Kotlin?

그때 당시에 Java를 대체할 언어로 Kotlin에 푹 빠져 있었다. 하지만 Kotlin의 숙련도가 그리 높지 않았기에, Kotlin을 이용해 미션을 풀며 숙련도를 향상하고 싶었다.

왜 프레임워크?

처음 Spring을 배울 때부터, '대체 이런 기능은 어떻게 구현하는 거지?'라는 궁금증이 있었다.
그때 당시에는 찾아봐도 잘 이해되지 않았는데, Java에 어느 정도 익숙해진 지금이라면 이해할 수 있을 것 같아 도전해 봤다.

또한, 학습을 위해선 해당 지식에 대한 필요성을 먼저 느껴보는 것이 중요하다 생각해, 내가 어떤 지식을 학습해야 할지 알아가는 시간이 될 것이라 기대했다.

구현 과정

학습에 사용한 강의

  • 김영한 실전 Java - 고급 2편
  • 최태현 - 코틀린 고급편

프레임워크 기능을 구현하는 것이다 보니, 한 번도 직접 사용해 보지 않은 리플렉션과 애노테이션을 사용해야 했다.
또한, Kotlin 제네릭만의 특징인 공변, 무공변, 반공변에 대해서도 이해해야 했다.

다행히 이전에 구매해 둔 강의에서 해당 내용을 다루고 있어, 오랜만에 강의 진도도 나갈 겸 강의를 수강하며 해결했다.

하지만 그럼에도 처음 써보는 기술이라 많은 어려움이 있었고, 결국 AI를 활용해 다음과 같은 프로세스로 미션을 구현했다.

  1. 해당 객체가 어떤 역할을 해야 하는지 설계한다.
  2. AI에게 해당 객체를 구현해달라고 요청한다.
  3. AI가 제공해 준 코드를 수정하여, 가독성을 개선하고 기존 객체와 적절히 협력하도록 개선한다.

AI의 역할이 컸기 때문에 불만족스러운 부분도 있었지만, 대강 돌아가는 쓰레기인 코드를 개선하는 과정이 상당히 재미있었다.
AI에게 너무 의존하는 것은 좋지 않지만, 위와 같이 AI의 코드를 무작정 사용하지 않고 직접 이해하며 개선하는 과정을 거친다면, 생산성은 올라가는데 코드의 품질을 해치진 않으니 바람직한 방식이라고 느꼈다.

다만 일부 기능을 구현하기 위해 복잡한 정규식을 사용해야 했는데, 내가 정규식에 대해 잘 모르니 AI가 짜준 코드를 개선할 수도 없었다.
AI를 잘 활용하기 위해서는 개발자의 숙련도가 필수적임을 다시 한번 느끼는 순간이었다.

4. 최종 코딩 테스트

우테코 측에서 내 지원서와 코드를 좋게 봐준 건지, 1차 심사에 합격해 최종 코딩 테스트를 보러 갔다.
오픈 미션은 AI도 다소 사용했고, 지원서도 그리 잘 쓰지 않았다 생각했는데, 합격 소식을 듣고 정말 놀랐다.

코테 미션

최종 코딩 테스트 미션 레포지토리

최종 코테 미션은 '행성 로또'로, 기존의 로또 미션을 더 단순화한 요구사항을 제시했다.
코테를 준비하며 연습한 미션들보다 너무나도 쉬워 오히려 난감할 정도였다.

대신 도전 과제라는 추가 미션이 있었고, 우선 미션을 구현한 후 다음 선택지 중 하나를 추가로 수행하는 방식이었다.
1. 기존 코드를 개선한다.
2. 새로운 기능을 추가한다.

기본 미션 요구사항에는 수동 로또 기능이 없고 자동 로또 발급만 수행하면 됐기에, 사용자의 입력에 따라 수동 로또를 발급하는 기능을 추가하려고 했다.
하지만 사용자의 입력을 받아야 하니 기존 테스트가 실패하게 됐고, 결국 구현해 둔 것을 다 롤백한 후 기존 코드 리팩터링으로 도전 과제를 변경했다.

최종 코테에서의 TDD

기본 문제 요구사항이 너무 쉬웠던 만큼 다른 지원자들도 모두 깔끔하게 구현할 것이라는 확신이 있었다.
따라서, 프리코스 과정을 거치며 내가 TDD에 대해 얼마나 고민했고 성장했는지를 보여줘야만 합격할 수 있을 것이라 생각했다.

다음과 같은 순서로 미션을 구현했다.
TDD가 처음이라 이 방식이 바람직한지는 모르겠지만, 실제로 모든 모델을 깔끔하게 설계할 수 있어서 만족스러웠다.

  1. 전체 요구사항을 분석한다.
  2. 요구사항이 필요로 하는 기능을 작은 단위로 나눈다.
  3. 기능 수행을 위해 '알아야 할 것'이 같은 책임(기능)들을 모은다.
  4. 해당 책임을 담당할 객체를 생성한다. (기능은 구현하지 않는다)
  5. 해당 객체가 지닌 책임을 기반으로 테스트 코드를 작성한다.
  6. 작성한 테스트 코드가 성공하도록 객체를 구현한다.

확실히 TDD를 도입하니, 테스트 코드가 상당히 간결하고 직관적으로 작성됨을 느꼈다.
지금까지 진행한 프로젝트에서는 항상 테스트 코드 작성이 너무 어려워 큰 스트레스였는데, 설계가 잘못됐기 때문에 테스트가 어려워진 것이었음을 뼈저리게 느끼는 순간이었다.

중요한 것은 '테스트 그 자체'가 아니라 '테스트에 용이한 구조'임을 최종 코테에서라도 깨닫게 된 것이 정말 큰 수확이었다.

도전 과제

위에서 언급했듯, 기능 추가에 어려움을 느껴 코드 리팩터링을 수행했다.
지원서 때부터 일관적으로 코드의 가독성을 중시한다고 써 놨기에, 이를 증명하는 시간으로 만들어야겠다 다짐했다.

하지만 마냥 쉽지는 않았는데, 애당초 TDD를 도입해 구현했고 문제도 쉬웠기 때문에 크게 수정할 부분이 보이지 않았다.
하지만 그렇다고 포기할 순 없으니, 코드를 샅샅히 살펴보며 다음과 같은 순서로 가독성을 개선했다.

  1. 모든 메서드가 예상대로 동작하도록 개선 및 분리한다.
  2. 변수명이 어색하거나 모호하다면 직관적이고 가독성 좋게 개선한다.
  3. 테스트 코드에 Fixture를 도입한다.
  4. 개행 등의 코드 컨벤션을 완전히 통일한다.

테스트 코드에 Fixture를 도입하는 것은 리스크 있는 도전이었다.
이전에 초록 스터디 때 배운 개념이었지만, 당시에 사용했을 때는 오히려 코드의 가독성을 헤치고 개발 생산성이 하락했기 때문이다.

하지만 테스트에 대한 숙련도가 높아진 지금이라면 도입해서 장점만 살릴 수 있을 것이란 확신이 있었고, 단점보다 장점이 크게 느껴지는 부분에만 Fixture를 도입하여 코드를 약간이나마 개선할 수 있었다.
(물론, 나중에 다시 보면 부족한 부분이 많이 보이겠지만, 당시로서는 만족스러웠다)

5. 최종 합격

아직도 최종 합격한 게 믿기지 않아, 혹시 합격 메일이 잘못 발송된건 아닐까 메일함을 새로고침하고 있다.
3번 이상 시도할 마음으로 시작했던 우테코 도전기가 첫 회만에 성공으로 끝나게 되었음이 감격스럽다.

돌이켜보면 지금까지 많은 프로젝트에 참여하며 항상 새로운 것에 도전하고 많이 배워 왔었다.
열심히 노력하며 성장해 왔지만, 그 방향이 올바른지에는 확신이 없던 나날들이었다.

이번 합격이, 지난 방향이 최소한 오답은 아니었음을 검증해 주는 것 같아 기쁘다.
