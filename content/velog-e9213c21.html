(다른 크루가 만든 행성이 메이커로 제작한 행성이 이미지)

개요

드디어 레벨 1의 첫 코딩 미션인 '블랙잭'을 완수했다.
너무 많은(고봉밥) 깨달음을 얻었는데, 다소 장황해지더라도 모두 정리해보고자 한다.

코딩 내적인 깨달음

이번 미션 동안에는 코딩 내외적으로 많은 깨달음을 얻었는데, 코딩 내적인 이야기부터 살펴보자.

View는 Model을 의존할 수 있다.

public class OutputView {
	
    // View가 Model(Card)에 의존할 수 있다.
    public void printCards(List<Card> cards) {
        List<String> cardOutputs = parseCardsToOutputs(cards);
        String joinedCards = String.join(DELIMITER, cardOutputs);

        System.out.println(playerName + "카드: " + joinedCards);
    }
}

Model이 View를 의존하는 것은 절대 금지지만, 반대로 View가 Model을 의존할 수는 있다.
(의존하는게 바람직하다는 얘기는 아니다)

View가 Model을 직접 의존할 경우, Model의 변경에 크게 영향 받을 수 있다는 것은 인지해야 한다.
프로젝트 규모가 크다면, 유지보수성을 위해 DTO 도입을 고민해보자.
하지만, 무조건적인 DTO 도입은 되려 보일러플레이트를 증가하는 꼴이 되니, 트레이드오프를 두고 잘 고민해보자.

패키지 분류가 어렵다면, 클래스의 '목적'을 생각해라.

// View에 출력하기 위한 DTO이므로, 패키지는 view.dto가 적절하다.
package blackjack.view.dto;

public record CardDto(
        Rank rank,
        Suit suit
) {
}

DTO라고 해서 무작정 dto 패키지에 몰아넣는 것은 바람직하지 않다.
어떤 클래스를 어느 패키지에 배치해야 할지 모호하다면, 해당 클래스를 만든 목적을 생각해보자.
위의 CardDto의 경우, OutputView에서 카드를 출력하기 위한 객체이므로, view.dto 패키지에 배치하는 것이 적절하다.

적절한 패키지명만으로도, 해당 객체가 어떤 역할을 하는지 추론 가능해진다.
다른 개발자를 위해서라도, 패키지 경로를 고민하는 습관을 갖도록 하자.

응집도를 신경쓰자

package blackjack.model.card;

public final class Hand {
	
    private final List<Card> cards; 

    public int calculateScore() {
    	// 점수를 계산한다.
    }
    
    public boolean isBust() {
    	// 손패의 상태가 버스트인지 판단한다.
    }
    
    public Result judgeResultVersus(Hand otherHand) {
    	// 승패를 판단한다.
    }
}

위의 Hand 객체를 살펴보자.
점수를 계산하고, 상태를 판단하고, 승패를 판단하고 있다.
이 기능 각자를 하나의 책임으로 보고 별도의 객체로 분리할 것인가?

그 방법이 잘못되었다고 말할 수는 없다. 하지만, 위 기능들은 모두 "Hand 스스로 해낼 수 있는" 기능들이다.
즉, 위 기능들을 수행하는데 있어 외부의 정보에 의존하지 않는다.

이런 관점을 "아는 것에 대한 책임"이라고 부르는데, Hand가 List<Card>를 알고 있으므로, 위 책임들을 직접 수행하는게 바람직하다고 볼 수 있다.

물론 각 기능들을 별도의 객체로 추출하면, 각각의 기능만을 독립적으로 테스트할 수 있어진다는 장점도 존재한다.
이 경우엔 응집도와 테스트 용이성이 충돌한다고도 볼 수 있는데, 현재 상황을 보고 각 방식의 장단점을 나열한 후 선택하도록 하자.
(물론, 잘 응집할 경우엔 테스트 용이성도 챙길 수 있을 것이다)

뷰는 본질적으로 복잡할 수 있다

public class OutputView {

    private static final String DELIMITER = ", ";

    public void printInitialDeal(List<CardDto> dealerCards, List<PlayerDto> players) {
        String joinedPlayerNames = players.stream()
                .map(PlayerDto::playerName)
                .collect(Collectors.joining(DELIMITER));
        System.out.println("딜러와 " + joinedPlayerNames + "에게 2장을 나누었습니다.");

        printDealerCards(dealerCards);
        for (PlayerDto player : players) {
            printPlayerCards(player.playerName(), player.cards());
        }
        System.out.println();
    }
}

뷰는 데이터를 포멧팅하고, 어떤 형식으로 입출력해야 하는지를 정의한다.
그러므로, 뷰의 코드는 본질적으로 복잡할 수 있다.

이전에는 출력 뷰 코드의 가독성도 많이 신경쓰느라 골치 아팠는데, 어느 정도 내려놓고 다른 부분을 더 고민해보도록 하자.

Getter를 무조건 지양해야 하는 것은 아니다.

package blackjack.model.card;

public final class Hand {
	
    private final List<Card> cards; 

    public List<Card> getCards() {
    	return List.copyOf(cards);
    }
}

만일, 어떤 방식이든 카드를 출력해야 하는 상황이라고 가정해보자.
Hand.getCards 없이 이를 구현할 수 있겠는가?
안될 것은 없다만, 그 단순한 요구사항을 충족하기 위해 아주 장황한 코드를 작성하게 될 것이고, 어쩌면 Hand가 View에 의존하게 될지도 모른다.

또한, Getter는 직관적인 테스트 코드 작성에도 도움이 된다.
"테스트만을 위한 코드는 지양하자"라는 말이 있지만, Getter를 추가했을 때 얻을 수 있는 이점과, 캡슐화 저해로 인한 단점을 비교해보고 판단하도록 하자.

DTO의 네이밍도 신경써보자

dto라고 해서 dto라는 postfix를 붙이게 되면, 네이밍으로 의도를 표현할 수 있는 기회를 놓칠 수 있다고 생각해서요. 정말 개인적이지만 DTO라는 패키지를 쓰더라도 네이밍에서는 지양하는 편입니다 (이건 사람마다 천차만별이니 하나의 의견으로 바라봐주셔요)
- 블랙잭 리뷰어 아루(donghoony)

그간 의식하지 않고 CardDto, PlayerResultDto 와 같이 ...Dto 형식으로 작명해왔다.
해당 클래스가 DTO임이 명확해지므로, 잘못된 방법으로 볼 순 없다.

하지만, 이런 습관으로 인해 좋은 이름들을 놓치고있진 않은지 검토해볼 필요가 있다.

클래스가 제어할 수 없는 것만 주입하라

public class Hand {

    private final List<Card> cards;
    private final AceAdjustPolicy aceAdjustPolicy;

    // Hand를 생성하려는 쪽에서 AceAdjustPolicy의 존재도 알아야 한다
    public Hand(AceAdjustPolicy aceAdjustPolicy) {
        this.cards = new ArrayList<>();
        this.aceAdjustPolicy = aceAdjustPolicy;
    }
}

어떤 정책이나 인터페이스를 외부에서 주입받게 되면, 다형성을 활용하기 쉬워지고 테스트하기 용이한 객체로 만들 수 있다.

하지만, 이런 객체를 생성하는 쪽의 인지 부하가 높아진다는 큰 문제가 발생한다.
위의 경우에도, Hand를 생성하는 쪽에서 AceAdjustPolicy까지 알고 있어야 하는 것이다.

한 쪽이 정답이라고 할 순 없지만, 무언가를 주입하려 할 때, 정말 외부에서 주입받아야 하는 값인지 생각해보자.
이를테면, 객체가 절대로 제어할 수 없는 시간이나 Random 등은 주입하도록 구현하는게 바람직할 것이다.
반면, (정책이 잘 바뀌지 않을 것이라 가정할 때) AceAdjustPolicy같은 의존은 객체 내부에서 스스로 해결하는게 더 바람직할 수 있다.

반환할 값을 굳이 추상화할 필요 없다.

public final class Hand {

    private final List<Card> cards;

	// 굳이 List를 Collection으로 추상화해서 얻을 수 있는 이점이 없다.
    public Collection<Card> getCards() {
        return List.copyOf(cards);
    }
}

위 예시의 경우, 이미 List.copyOf를 사용하고 있으니, 반환값이 List임이 명확하다.
이를 굳이 Collection으로 추상화한다면, 외부에서 반환값을 'List로 사용할지 Collection으로 사용할지 선택할 권리를 박탈'하는 꼴이 된다.

외부에서 값을 받아올 때는 추상화가 충분히 유용할 수 있지만, 이미 내부적으로 특정 구현체에 의존하고 있다면, 그 반환값을 굳이 추상화할 필요는 없다.

외부의 인지 부하를 신경써라

public class Player {
	
    private final Name name;
    private final Bet bet;
    
    // Player를 생성하는 곳에서 Name과 Bet도 알아야 한다
    public Player(Name name, Bet bet) {
    	this.name = name;
        this.bet = bet;
    }
    
    // Player를 생성하는 곳에서 Name과 Bet을 몰라도 된다
    public Player(String name, int bet) {
    	this.name = new Name(name);
        this.bet = new Bet(bet);
    }
}

첫 번째 생성자를 사용할 경우, Player를 생성하는 곳에서 new Name(name), new Bet(bet)처럼 Name과 Bet을 같이 다루어야 한다.

반대로, 두 번째 생성자를 사용할 경우, Name의 세부 타입이 String이고 Bet의 세부 타입이 int라는 것을 외부에 노출하게 된다.
(노출하지 않고 감추는 것을 타입 은닉이라고 부른다)

두 방법 중 무엇이 좋은지 정답은 없다.
(두 생성자를 모두 선언해도 문제없다)
각 방법의 트레이드오프를 고려하여, 현재 상황에 적합한 방법을 선택하도록 하자.

코딩 내적인 깨달음

이번엔 코딩 외적으로 넘어가, '개발'에 대한 깨달음을 정리해보자.

도메인을 깊이 있게 이해해라

개발을 시작하기 전에, 개발하고자 하는 도메인을 깊이 있게 이해하는 과정을 반드시 선행해야 한다.
'블랙잭'이나 '장기'라면 실제 게임을 플레이 해 보는 것도 좋고, '도서 대여 시스템' 같은 서비스라면 기존 서비스를 이용해보거나, 기획자와 소통하여 꼼꼼하게 학습하면 된다.

도메인을 깊이 있게 이해하는 것은 '소프트웨어 장인정신'과도 밀접한 연관이 있는데, 내가 직접 느낀 장점만을 나열해보겠다.

  1. 모호한 요구사항을 명확하게 바꿀 수 있다.
    • '블랙잭'에서 딜러와 플레이어가 둘 다 버스트라면 어떻게 처리해야 할까?
    • 요구사항이 이를 알려주지 않는다면, 실제 게임에서 어떻게 처리하는지를 살펴보면 된다.
    • 요구사항이 A부터 Z까지 상세한 경우는 거의 없다. 도메인을 잘 알지 못하는 개발자라면 매번 해매거나, 잘못 구현하기 십상이다.
  2. 도메인 용어를 사용할 수 있다.
    • '에이스가 존재하면서, 에이스를 11로 계산해도 버스트되지 않는 패'를 무엇이라고 부르는지 알고 있나?
    • 이런 손패를 '소프트 핸드'라고 부른다.
    • 이런 도메인 용어를 사용하면 용어의 함축적인 의미를 전달할 수 있으니 가독성을 향상할 뿐 아니라, 다른 파트(PM, 디자이너 등)의 동료들과 소통하기도 편하다.
    • 소프트 핸드 기능에 대해 소통하는데, 백엔드가 '에이스가 존재하면서, 에이스를 11로 계산해도 버스트되지 않는 패'라고 설명한다 상상해보라.
  3. 개발로 해결하기 어려운 문제를 정책으로 해결할 수 있다.
    • 블랙잭에 베팅 기능을 구현한다고 가정해보자. 플레이어는 블랙잭으로 승리하면 베팅금의 1.5배를 얻어야 한다.
    • 만일 베팅금이 홀수(ex_ 123)라면 어떻게 처리해야 할까? 수익 금액은 실수(float)로 처리해야 할까? 아니면 소수점 아래는 버려야 할까?
    • 도메인을 깊이 있게 이해하고 있다면 '베팅 금액은 100원 단위만 가능하다'와 같은 정책을 도입해서 쉽게 해결할 수 있다.
    • 요구사항을 재정의하는 것이니만큼, 도메인을 잘 알고 있어야 시도할 수 있을 것이다.

PR은 빨리 올려라

요구사항은 모두 만족하나 아직 시간이 조금 있는 것 같아서 RC를 드리니, 반영하고 싶으시면 진행해주시고 머지를 원하시면 코멘트로 말씀해주세요.

우테코 리뷰 뿐 아니라, 코드리뷰 문화가 있는 어디든 통용되는 내용 같아서 회고록에 포함한다.

마감기한에 아슬아슬하게 제출하게 되면, 리뷰어 입장에서 하고 싶은 말이 더 많음에도, 사소한 것들은 넘어가기 마련이다.
이는 결론적으로, 리뷰이의 성장에 악영향을 미친다.

반대로, 마감기한이 넉넉하다면, 리뷰어는 리뷰이의 성장을 위해 하고 싶은 말을 모두 꺼낼 수 있다.
또한, (코드 품질이 좋다면) 빠르게 작업해온 리뷰이의 역량을 좋게 평가하게 되므로, 더 심화적인 내용까지 조언할 수 있을 것이다.

우아한테크코스에서 빠르게 구현하고, 빠르게 PR을 보내라를 강조하는 이유는 이 때문인 것 같다.

마치며

단순히 어떤 것을 배운 것도 중요하지만, 앞으로 어떤 것을 배울 수 있는 자세도 같이 배웠다.

리뷰어의 조언에 따라, 앞으로는 다음과 같은 흐름으로 고민해볼 것이다.

  1. 현재 맞이한 문제를 정의한다.
  2. 문제를 해결할 수 있는 방법들을 나열한다.
  3. 각각의 방법이 지닌 장단점을 비교한다.
  4. 트레이드 오프를 고려해, 지금 상황에 최선이라 생각되는 방법을 선택한다.

'코딩엔 정답이 없다'라는 것을 알면서도, 막연하게 '지금 상황에서의 정답은 뭐지?'라고 생각하고 있었다.
명확한 정답이란 없으니, 충분한 근거가 있다면 어떤 방법이든 적용할 수 있을 것이다.

위와 같은 흐름으로 고민하다보면, 내 코드에 근거가 충분해질거라 믿는다.
이는, 동료와 협업할 때 내 코드를 설명하는 데도 도움을 줄 것이다.

당분간 위와 같은 흐름으로 코드를 작성해보고, 더 좋은 방법이 있는지 찾아볼 것이다.
