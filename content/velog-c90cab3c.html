개요

이번 과제는 로또 애플리케이션을 구현하는 과제로, 2주에 걸쳐 진행됐다.
'나만의 클린 코드 기준 세우기'를 목표로 한 과제이니만큼, 가독성이 좋고 유지보수하기 좋은 코드를 짜기 위해선 어떻게 해야 하는지 많이 고민하여 과제를 구현했다.

새로 배운 것

메서드 선언 순서도 컨벤션이 있다

public class 클래스 {

	생성자() {}
    
    static 정적_메서드() {}
    
    public 퍼블릭_메서드() {}
    
    private 프라이빗_메서드() {}
    
    @Override
    public 오버라이드_메서드() {}

}

그동안에도 무의식적으로 사용하던 메서드 선언 순서가 있었지만, 이것을 팀 내 컨벤션으로 준수해야 한다는 것은 모르고 있었다.
해당 포스트를 보면 메서드 순서를 어떻게 배치해야 할지 아이디어를 얻을 수 있을 것이다.

항상 똑같이 적용되는 절대적인 기준이 있는 것은 아니지만, 각 방법의 장점과 단점을 고려해 나의 팀 내에 통용되는 컨벤션을 만들어야 할 것이다.

우선 내가 적절하다 생각하는 순서는 다음과 같다.
1. 생성자
2. 정적 팩터리 메서드
2. 정적 public 메서드
3. private 메서드
4. Override 메서드

우선, 인스턴스 생성과 관련된 메서드는 최상단에 배치하도록 했다.
다른 메서드와 성격이 크게 다르다고 판단했기 때문에, 맨 위에 별도로 모아 놓도록 하였다.

그 다음으로는 외부에서 사용될 public 메서드를 상단에 모아서 배치하도록 했다.
해당 클래스를 사용하고자 하는 외부 클래스 입장에서 가장 중요한 메서드는 public 메서드라고 생각했기 때문이다.

private 메서드는 다른 메서드와 달리, 연관되어 호출될 메서드들을 모아 두는 것이 좋다고 판단했다.
A 메서드가 내부적으로 B 메서드를 호출한다면, A 메서드를 읽는 개발자는 B 메서드의 동작이 제일 읽고 싶다고 생각했기 때문이다.

추가적으로, private 메서드는 결국 public 메서드에 의해 호출될 것이기 때문에, 위의 기준대로 그룹화한 private 메서드는 가능한 한 public 메서드의 순서와 일치하도록 노력했다.

DTO는 요구 사항을 알 필요가 없다

@AllArgsConstructor
public class UserDto {

	private final String name;
    private final int age;
    
    @Override
	public String toString() {
    	if (age > 19) {
        	return "이름: " + name ", 나이: " + age + ", 성인입니다.";
        }
        
        return "이름: " + name ", 나이: " + age + ", 성인이 아닙니다.";
	}
    
}

위와 같이 사용자의 이름과 나이 정보를 가지는 DTO가 있다 가정해보자.
현재 요구사항에서 사용자가 성인인지 아닌지를 출력해 줘야 하기 때문에, DTO가 그 요구사항을 처리하고 있다.
이것이 왜 문제가 되는 것일까?

사실 출력 형태에 관련된 로직을 DTO가 가지고 있는 것 까지는 크게 문제되지 않는다.
이 경우 View의 변경이 DTO에 영향이 가게 되지만, 그것이 DTO를 사용하는 이유라고 볼 수도 있기 때문이다.

비교적 사소한 단점으로는, 해당 DTO가 유연하게 사용되지 못할 수 있다는 것이다. 위의 DTO는 무조건 이름: {name}, 나이: {age}, 성인입니다. 형식으로 출력하도록 설계되어 있으니, 유저 정보를 다르게 활용하고 싶은 경우가 추가로 생긴다면 해당 DTO를 수정해야 하거나 새로운 DTO를 만들어야 할 수도 있다.

이 방식의 제일 큰 단점은 다른 개발자와 협업할 때 드러난다.
DTO는 이름에서부터 알 수 있듯 데이터 전달 목적으로 사용되는 객체이기 때문에, 내부적으로 비즈니스 로직을 지니고 있을거라 예상하기 어렵다.
이는 해당 DTO를 사용하는 코드의 가독성을 악화시키며, 다른 개발자가 로직을 제대로 이해하기 어렵게 한다.

DTO는 데이터 전달 목적의 객체라고 이름에서부터 약속되어 있다.
다른 개발자의 입장을 고려해, 본연의 목적에 맞게 사용하도록 하자!

디미터의 법칙을 준수하자

참고자료

public class Application {

	// 디미터의 법칙을 위배한 코드
	public static void main(String[] args) {
    	new Controller().run();
    }
    
    // 디미터의 법칙을 준수한 코드
    public static void main(String[] args) {
    	Controller controller = new Controller();
        controller().run();
    }
    
}

다들 한번쯤 들어본 법칙이라 생각한다.
나도 디미터의 법칙이 무엇인지 알고는 있었지만, 내 코드가 디미터의 법칙을 준수하는지 아닌지를 검사해본적은 없었던 것 같다.

물론 위의 예시 코드는 디미터의 법칙을 위배했다고 해서 유지보수상의 큰 문제가 발생할 코드로 보이지는 않는다만, 코드리뷰에서 위와 같은 코드에서 피드백 받았기 때문에 그대로 들고 왔다. 😅

View 계층이 입력을 가공해도 될까?

사실 도메인의 요구 사항이 View에 녹아 있는 것이 좋지 않을 수도 있습니다. 다만, 로또 같이 간단한 서비스에서는 전 최대한 관리 포인트를 줄이는 편이 유지 보수하기 쉽다고 생각해서 제 스타일을 말씀드린 겁니다! 😁

  • hangillee(초록 스터디 리뷰어)
public class InputView {

	private static final INPUT_SEPARATOR = ",";
    
    private static final Scanner scanner = new Scanner(System.in);

    // 입력값을 그대로 반환하는 버전
    public String getInputs() {
    	System.out.println("값들을 입력해주세요(쉼표로 구분)");
        
        return scanner.nextLine();
    }
    
    // 입력값을 split하는 버전
    public String[] getInputs() {
    	System.out.println("값들을 입력해주세요(쉼표로 구분)");
        String inputs = scanner.nextLine();
        
        return inputs.split(INPUT_SEPARATOR);
    }
    
}

이전 과제를 수행하면서 View 계층은 입출력에 대한 책임만을 가져야 하기에 데이터 가공 등의 책임을 지면 안된다라고 이해했었다. 그렇기에 이번 과제에서의 Input View는 단순히 날것의 입력값을 받아오기만 하도록 설계했다.

그로 인해 View가 받아온 데이터를 View 외부에서 String -> String[] -> List<Integer> -> Lotto로 변환해야 했는데, 이 과정이 번거롭다 느껴져 이를 처리해줄 별도의 InputConverter라는 클래스를 두었다.

하지만 그 과정에서 데이터를 어떻게 분리하는지에 대한 정보가 데이터를 받아오는 View 측이 아닌 InputConverter에 위치하게 되었는데, 이런 구조가 굉장히 부자연스럽다 느껴졌지만 View가 입출력에 대한 책임만을 갖도록 하기 위해 감당해야할 트레이드 오프라고 생각했다.

하지만 이제 와서 생각해보면 View가 입출력 데이터를 split하는게 문제가 되는지 의문이 들긴 한다. 만약 View가 입출력을 split하는 것 까지 담당한다면, 외부 클래스에서는 string[] 혹은 파싱된 int[] 값을 받아와 Lotto 객체로 바꿔주면 되니 코드가 훨씬 간결해진다.
또한 InputConverter라는 별도의 클래스가 있어야 할 필요도 없어진다!

물론 View는 가급적 비즈니스 요구사항을 모르는 것이 좋다.
View가 입출력 값을 가공하도록 할 때 오는 장단점을 고려하며 선택하자!

상수를 별도의 클래스로 관리하면?

public class Constraints {
	
    public static final int LOTTO_PRICE = 1_000;
    public static final int MINIMUM_LOTTO_NUMBER = 1;
    public static final int MAXIMUM_LOTTO_NUMBER = 45;
    public static final int LOTTO_SIZE = 6;

}

만일 여러 클래스에서 동일한 상수를 각각 지니게 되면 데이터의 중복이 발생한다.
즉, 이후에 코드를 유지보수하며 데이터의 불일치가 발생할 가능성이 생긴다.

그렇다면 일반적으로는 위와 같이 하나의 클래스로 상수를 관리할 것이다.
위 방법의 문제점엔 무엇이 있을까?

우선 단순하게 해당 클래스가 관리하게 될 상수가 너무 많아져, 각 상수가 무슨 의미인지 구분하기 힘들어질 수 있다.
만일 위의 Contraints 클래스가 상수를 100개씩 관리하게 된다면?
여러분은 그때도 LOTTO_PRICE가 어떤 상수인지 한번에 파악할 수 있겠는가?

public class Lotto {

	public int calculatePurchasableLottoAmount(int purchaseAmount) {
    	return purchaseAmount / Constraints.LOTTO_PRICE;
    }

}

다른 문제도 있는데, 해당 상수를 사용하는 클래스에서 바로 값을 확인할 수 없다는 점이다.
위와 같이 해당 금액으로 얼마만큼의 로또를 구매할 수 있는지 반환하는 메서드가 있다고 하자.

여러분이 직접 쓴 코드라면 큰 문제 없겠지만 만일 다른 사람이 쓴 코드를 읽는 상황이라면?
해당 클래스만으로는 LOTTO_PRICE가 어떤 값인지 알 수 없으니, Contraints 클래스에 들어가서 값을 확인해야 할 것이다.

위와 같은 단점들이 있지만, 한 클래스로 상수를 관리하는 방식이 절대 잘못된 것은 아니다.
하지만 어떤 단점들을 가지고 있는지 알고 쓰는 것은 중요하다!

예외가 발생하지 않는다는건 어떻게 테스트하지?

public class LottoNumberTest {

	@Test
    @DisplayName("인스턴스를 생성한다")
    void createInstance() {
    	LottoNumber lottoNumber = new LottoNumber(20);
    }
    
}

로또는 1 ~ 45의 숫자로 구성되어 있으므로, 그 범위 내의 숫자를 통해 LottoNumber 인스턴스를 통해 인스턴스를 생성할 때는 예외가 발생하지 않아야 할 것이다.

예외가 발생하지 않는다는건 어떻게 테스트하는걸까.
테스트가 성공하면 예외가 발생하지 않은거니 검증에 성공하는걸까?

public class LottoNumberTest {

	@Test
    @DisplayName("인스턴스를 생성한다")
    void createInstance() {
    	assertThatCode(() -> new LottoNumber(20))
        	.doesNotThrowAnyException();
    }
    
}

그보단 더 명확한 방법이 있다.
위와 같이 assertThatCode().doesNotThrowAnyException()를 사용하면, 해당 코드가 예외를 발생시키지 않음을 테스트할 수 있다.

코드를 읽는 입장에서도 어떤 것을 테스트하는지 명확해지고, 예외가 발생했을 때 어디서 발생하는지 알기도 수월할 것이다.

Enum + Test Fixture를 사용하자!

public enum LottoNumbersFixture {

    WINNING_LOTTO(1, 2, 3, 4, 5, 6),
    THREE_EQUALS_LOTTO(1, 2, 3, 43, 44, 45),
    FOUR_EQUALS_LOTTO(1, 2, 3, 4, 44, 45),
    FIVE_EQUALS_LOTTO(1, 2, 3, 4, 5, 45),
    SIX_EQUALS_LOTTO(1, 2, 3, 4, 5, 6);
    
    // ...
    
}

우선 Fixture는 고정되어 있는 물체를 의미한다.
즉, 모든 테스트가 고정된 환경에서 수행되도록 보장하기 위해 Test Fixture를 사용하는 것이다.

위 예시의 경우, 로또 생성/삭제/비교 등의 로직 테스트에 해당 Fixture를 사용해 일관적으로 테스트할 수 있다.

초기 테스트 데이터를 구축하기 위해 Test 클래스 내에 private 메서드를 만들거나 @BeforeEach를 사용할 수 있지만, 위와 같이 Enum을 사용한 별도의 Test Fixture를 만들어서 코드를 보기 좋게 만들어 보자!

테스트 커버리지를 확인하자!

위와 같이 IntelliJ에서 제공하는 기능인 Run Tests with Coverage 기능을 사용해보자
내가 작성한 테스트 코드가 비즈니스 코드를 얼마나 검증하고 있는지를 백분율로 보여준다!

테스트 커버리지를 테스트 완성도의 절대적인 기준으로 사용할 순 없지만, 내가 모든 기능에 대한 테스트를 작성했는지 확인할 때 사용하면 편리하다!
