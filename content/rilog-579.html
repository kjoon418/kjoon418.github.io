실무에서 받는 요청은 항상 모호하다.
문제를 제대로 이해하기도 전에 해결하려 하면, 바람직한 방법보다 익숙한 방법을 사용하게 된다.
요구사항을 단계별로 구체화하며 설계하자.

지금부터 시스템 디자인 설계 순서에 따라 기능을 설계해볼 것이다.
이번 시간엔, 다음 순서 중 요구사항 정의 단계를 살펴보자.

  1. 기능/비기능 요구사항 정의: 무엇을 만들어야 하는지 구체화한다.
  2. Core Entities 정의: 시스템이 사용할 핵심 객체를 정의한다.
  3. API 설계: 요구사항마다 ‘무엇을 어떻게 호출하면 어떻게 처리하고 응답할지’ 정한다
  4. HLD: 동작하는 시스템을 설계한다.
  5. Deep Dive: 시스템이 비기능 요구사항까지 충족하도록 개선한다.

1. 기능 요구사항 정의

“우리 시스템이 무엇을 해야 하는가?”를 정하는 단계다.
사용자가 어떤 행동을 하면 시스템이 무엇을 돌려주는지 문장으로 정의하면 된다.

이 때, “기능이 어떻게 동작해야 하는가”와 “기능이 얼마나 잘 동작해야 하는가”를 구분해야 한다.
이 단계에서는 기능이 어떻게 동작해야 하는지만 다룬다.
기능이 얼마나 잘 동작해야 하는지는 비기능 요구사항에서 다루니, 지금 고민하지 말자.

핵심 흐름을 구현할 때 필요 없는 기능까지 당장 설계할 필요는 없다.
지금 설계하지 않고 범위 밖으로 제외할 기능도 정하자.

미리 정해두지 않으면 다음과 같은 문제가 생긴다.

  1. 팀원이 “이 기능은 왜 없어요?”라고 물어봤을 때 대답하기 어렵다.
  2. 나도 모르게 범위 밖 기능까지 설계하게 된다.

2. 비기능 요구사항 정의

이번엔 “얼마나 잘 동작해야 하는가”를 정하는 단계다.
다음 4가지 항목을 각각 정의해보자.

  1. 가용성: 서비스가 얼마나 멈추지 않고 동작해야 하는가?
  2. 확장성: 사용자와 데이터가 얼마나 늘어나도 감당 가능해야 하는가?
  3. 성능: 사용자가 얼마나 빨리 응답 받아야 하는가?
  4. 신뢰성: 저장한 데이터를 얼마나 잘 보관해야 하는가? 중복 처리나 누락이 얼마나 없어야 하는가?

만약 분산 시스템이라면 다음 항목까지 정의해야 한다.

  1. 일관성: 사용자가 항상 최신 데이터를 응답 받아야 하는가?

2-1. 가용성

‘서비스가 멈추지 않고 동작한 시간의 비율’을 가용성이라고 한다.
보통 %로 표현하는데, 얼마나 멈춰도 되는건지 쉽게 확인하기 위해 다운타임으로도 표현하면 좋다.

가용성 목표는 기능마다 각각 결정하면 된다.
해당 기능이 멈췄을 때 문제가 얼마나 큰지에 따라 정하자.

예를 들어, 영상 시청 기능은 장애 발생시 모든 사용자가 영향을 받으니 가용성 목표를 높게 설정할 수 있다.
반대로, 영상 업로드 기능은 일부 사용자만 영향을 받으니 낮게 설정할 수 있다.

2-2. 확장성

‘사용자와 데이터가 얼마나 늘어도 성능을 유지할 수 있는가’를 확장성이라고 한다.

어느 정도 규모를 감당해야 하는지를 결정하면 된다.
그 규모는 DAU, 가장 붐빌 때의 QPS, 하루에 쌓이는 데이터 양 등이 있을 수 있다.

2-3. 성능

‘사용자가 얼마나 빨리 응답받아야 하는지’를 성능이라고 한다.

성능을 표현할 땐 평균보다 p99를 사용하자.
평균만 관찰하면, 일부 사용자가 늦게 응답받는 문제가 발생하더라도 알아차릴 수 없다.

또한, 성능을 측정할 때 어디서부터 어디까지를 측정할건지 명확히 하자.
예를 들면, “사용자가 재생 버튼을 눌렀을 때 부터 화면에 영상이 재생될 때 까지 p99 5초 이하”처럼 정할 수 있다.

2-4. 신뢰성

‘맡긴 것이 끝까지 무사한지’를 신뢰성이라고 한다.
서버에 한 번 업로드한 데이터가 사라지거나 깨지지 않는 것, 요청이 누락되거나 중복 처리되지 않는 것을 등이 있다.

신뢰성은 ‘얼마나 포기해도 되는가’로 표현하자.
예를 들면 “업로드에 성공했다고 응답한 영상은 하나도 잃지 않는다”처럼 정할 수 있다.

2-5. 일관성

PACELC를 통해, 우리의 분산 시스템이 일관성을 어떻게 다룰지 표현해보자.
PACELC의 의미는 다음과 같다. 하나씩 알아보자.

  • PAC: 파티션이 발생했을 때 무엇을 선택할 것인가?
    1. Partition: 파티션이 발생했을 때(시스템 사이 네트워크가 끊긴 상황)
    2. Availability: 가용성을 선택한다
    3. Consistency: 일관성을 선택한다
  • ELC: 네트워크가 정상일 때 무엇을 선택할 것인가?
    1. Else: 네트워크가 정상일 때(시스템이 네트워크로 연결된 상황)
    2. Latency: 지연을 선택한다
    3. Consistency: 일관성을 선택한다

PAC

PAC는 파티션이 발생했을 때 무엇을 선택할지를 의미한다.

파티션이 발생했으니, 다른 시스템에 있는 최신 값을 조회할 수 없다.
이럴 때 어떻게 동작하도록 만들 것인가?

가용성(Availability)을 선택하면 현재 시스템에 있는 데이터로 응답한다.
이점과 한계는 다음과 같다.

  • 이점: 파티션이 발생해도 서버가 요청을 처리할 수 있다.
  • 한계: 과거의 데이터로 응답한다.

일관성(Consistency)을 선택하면 네트워크가 복구되기 전까지 오류를 응답한다.
이점과 한계는 다음과 같다.

  • 이점: 사용자가 최신 데이터만 응답 받는다.
  • 한계: 파티션이 발생하면 서버가 요청을 처리할 수 없다.

ELC

ELC는 평소(파티션이 발생하지 않았을 때)에 무엇을 선택할지를 의미한다.

시스템이 네트워크로 연결되어 있으니, 최신 값을 다른 시스템에도 반영해야 한다.
하지만, 다른 시스템에 값을 복제하는건 비교적 오래 걸린다.
이럴 때 어떻게 동작하도록 만들 것인가?

지연(Latency)을 선택하면 현재 시스템에만 최신 값을 반영하고 바로 응답한다.
이점과 한계는 다음과 같다.

  • 이점: 비교적 빠르게 응답할 수 있다.
  • 한계: 다른 시스템에 최신 값이 반영되기까지 서로 다른 값을 지닌다.

일관성(Consistency)을 선택하면 다른 시스템에도 최신 값을 반영하고 나서야 응답한다.
이점과 한계는 다음과 같다.

  • 이점: 모든 시스템에 최신 값이 동시에 반영된다.
  • 한계: 다른 시스템에 반영하고 나서야 응답하니, 응답까지 오래 걸린다.
