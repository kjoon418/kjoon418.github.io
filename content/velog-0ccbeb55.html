추상화

1. 추상화가 필요한 이유

현실은 너무나 복잡하기 때문에, 우리는 현실을 이해하기 쉽고 예측 가능한 수준으로 분해하고 단순화한다

이것의 대표적인 예시는 해리 벡의 지하철 노선도로, 지하철 이용자에게 불필요한 정보(역 간 거리, 지형, 경로)는 제거하고 목적에 맞게 필요한 정보만 남겨 추상화했다

위의 예시에서 알 수 있듯, 추상화의 목적은 불필요한 부분을 무시함으로써 복잡성을 극복하는 것이다

2. 추상화의 정의

어떤 양상, 세부 사항, 구조를 좀 더 명확하게 이해하기 위해 특정 절차나 물체를 의도적으로 생략하거나 감춤으로써 복잡도를 극복하는 방법이다

복잡성을 다루기 위해, 추상화는 두 차원에서 이루어진다

  1. 구체적인 사물들 간의 공통점을 취하고 차이점을 버리는 일반화
  2. 중요한 부분을 강조하기 위해 불필요한 세부 사항을 제거하는 단순화

개념

1. 개념, 분류, 인스턴스

개념(Concept)이란, 공통점을 기반으로 객체들을 묶기 위한 그릇이다
개념을 이용하면 객체를 여러 그룹으로 분류(Classification)할 수 있다

  • 아이폰 XS와 아이폰 16은 사양, 크기 등 다양한 것들이 다르지만, ‘아이폰’이라는 그룹으로 분류할 수 있다
  • 아이폰과 갤럭시는 많은 것들이 다르지만, ‘스마트폰’이라는 그룹으로 분류할 수 있다

결국, 각 객체는 특정 개념을 표현하는 그룹의 일원으로 포함된다
이처럼, 객체에 어떤 개념을 적용하는 것이 가능해서 개념 그룹의 일원이 될 때, 객체를 그 개념의 인스턴스(Instance)라고 한다

  • 아이폰은 스마트폰이라는 개념을 적용할 수 있으므로, 스마트폰 개념의 인스턴스라고 볼 수 있다

2. 개념의 세 가지 관점

일반적으로 객체의 분류 장치로서 개념을 이야기할 때는, 아래의 세 가지 관점을 함께 언급한다

  1. 심볼(Symbol)
    • 개념을 가리키는 간략한 이름이나 명칭을 의미한다
    • ex) 아이폰과 갤럭시가 사용하는 심볼은 ‘스마트폰’이다
  2. 내연(Intension)
    • 개념의 완전한 정의를 의미한다
      내연을 통해서, 어떤 객체가 해당 개념에 속하는지 여부를 확인할 수 있다
    • ex) ‘전화 뿐 아니라 다양한 애플리케이션 기능을 활용할 수 있는 휴대용 지능형 단말기’라는 조건이 바로 스마트폰의 내연이다
  3. 외연(Extension)
    • 개념에 속하는 모든 객체의 집합(Set)을 의미한다
      즉, 개념의 인스턴스들이 모여 이루어진 집합을 의미한다
    • ex) 스마트폰의 내연은 {아이폰 XS, 갤럭시 s3, …}이다

3. 분류의 목적

분류는 추상화를 위한 도구이다
개념을 통해 객체를 분류하는 과정은, 추상화의 두 가지 차원을 모두 사용한다

  1. 공통점은 취하고 차이점은 버리는 일반화

    • 아이폰과 갤럭시를 모두 ‘스마트폰’이라는 개념으로 묶은 것은, 개별 객체 간의 차이는 무시하고 공통점을 취한 결과이다

  2. 중요한 부분을 강조하기 위해 불필요한 세부사항을 제거하는 단순화

    • 아이폰에 속하는 객체들의 공통점 중에 중요한 특징은, ‘애플 사에서 출시한 스마트폰’이다
    • 그 외의 사항(구매처, 하드웨어적 특징 등)들은 중요하지 않으므로 무시했다
    • 즉, 개념은 객체들의 복잡성을 극복하기 위한 추상화 도구이다

우리는 소프트웨어 세계 뿐 아니라 현실 세계의 복잡하고 무수히 많은 사물들도 개념의 틀로 걸러가며 세상을 추상화한다

타입

1. 타입은 개념이다

타입의 정의는 개념의 정의와 완전히 동일하다
즉, 타입은 공통점을 기반으로 객체들을 묶기 위한 틀이다

타입 역시 심볼/내연/외연을 이용해 서술할 수 있고, 타입에 속하는 객체 역시 타입의 인스턴스라고 한다

단, 타입은 근본적으로 개념과 동일하지만 컴퓨터 내부에서 사용되기 위해 조금 더 기계적인 의미를 지니게 된다

2. 데이터 타입

데이터 타입은 메모리 안에 저장된 데이터의 종류를 분류하는 데 사용하는 메모리 집합에 관한 메타데이터이다.
데이터에 대한 분류는 암묵적으로 어떤 종류의 연산이 해당 데이터에 대해 수행될 수 있는지를 결정한다

타입 시스템(Type system)은 데이터가 잘못 사용되지 않도록 제약사항을 부과하기 위해 등장했다

타입이 존재하기 전엔 모든 데이터가 메모리 속에 저장된 이진수(10101010)였다
이진수만 보고는 해당 데이터가 주소인지, 숫자인지, 문자인지 알 수 없기 때문에, 데이터를 잘못 사용하는 문제가 발생하기 쉬웠다

즉, 타입은 다음과 같은 중요한 사실을 지닌다

  1. 타입은 데이터가 어떻게 사용되는지를 의미한다

    • 숫자형 데이터가 숫자형인 이유는, 데이터를 더하거나 빼거나 곱하거나 나눌 수 있기 때문이다
    • 문자열형 데이터가 문자열형인 이유는, 두 데이터로 새로운 문자열을 만들거나 데이터에 포함된 문자열의 길이를 알 수 있기 때문이다
    • 즉, 데이터에 어떤 연산자(Opreator)를 적용할 수 있는지가 그 데이터의 타입을 결정한다

  2. 타입에 속한 데이터를 메모리에 어떻게 표현하는지는 외부로부터 철저하게 감춰진다

    • 개발자는 해당 데이터 타입의 표현 방식을 몰라도, 데이터를 사용하는데 지장이 없다
    • 개발자는 해당 데이터 타입에 적용할 수 있는 연산자만 알고 있으면 된다
      (숫자형 데이터가 메모리에 어떻게 저장되는지 몰라도 된다)

3. 객체와 타입

우리는 프로그램을 작성할 때, 객체를 일종의 데이터처럼 사용한다
애플리케이션 내부의 모든 객체의 상태를 모으면, 결국 애플리케이션에서 관리해야 하는 전체 데이터를 표현할 수 있다

하지만, 객체는 데이터가 아니다
객체에서 중요한 것은 객체의 행동이고, 상태는 부수효과를 쉽게 표현하기 위해 도입된 추상적인 개념일 뿐이다

즉, 객체를 창조할 때 가장 중요한 것은, 객체가 이웃하는 객체와 협력하기 위해 어떤 행동을 해야 할지를 결정하는 것이다
달리 말하면, 객체가 협력을 위해 어떤 책임을 지녀야 하는지를 결정하는 것이 객체지향 설계의 핵심이다

따라서, 데이터 타입과 같이 객체의 타입도 다음 사실을 지닌다

  1. 객체가 어떤 타입에 속하는지를 결정하는 것은 객체가 수행하는 행동이다
    • 어떤 객체들이 동일한 행동을 수행할 수 있다면, 그 객체들은 동일한 타입으로 분류되어야 한다
  2. 객체의 내부적인 표현은 외부로부터 철저하게 감춰진다
    • 객체의 행동을 가장 효과적으로 수행할 수 있다면, 객체 내부의 상태를 어떤 방식으로 표현하더라도 상관 없다

4. 행동이 우선이다

위에서 말했듯, 객체의 타입은 객체가 어떤 행동을 하느냐에 따라 결정되고, 객체의 타입은 내부 표현과는 아무 상관이 없다
따라서, 내부 표현이 다르더라도 어떤 객체들이 동일하게 행동한다면 그 객체들은 동일한 타입에 속한다

  • 결과적으로, 동일한 책임을 수행하는 일련의 객체는 동일한 타입에 속한다

이것은 객체를 타입으로 분류할 때 사용해야 하는 기준을 명확하게 제시한다
어떤 객체를 다른 객체와 동일한 타입으로 분류하는 기준은, ‘동일한 행동을 수행하는가’이다

  • 그 객체가 어떤 데이터를 가지고 있는지는 상관 없다
  • 반대로, 동일한 데이터를 가지고 있지만 행동이 다른 객체들이 있다면 그 객체들은 서로 다른 타입으로 분류되어야 한다

행동이 타입을 결정한다는 사실은, 객체지향 패러다임을 특징 짓는 다음과 같은 몇 가지 원리원칙에 의미를 부여한다

  1. 같은 타입에 속한 객체는, 행동만 동일하다면 서로 다른 데이터를 가질 수 있다

    • 여기서 동일한 행동이란 동일한 책임을 의미한다
    • 또한, 동일한 책임이란 동일한 메시지 수신을 의미한다
      따라서, 동일한 타입에 속한 객체는 내부의 표현 방식이 다르더라도 동일한 메시지를 수신하고 이를 처리할 수 있다
    • 단, 내부의 표현 방식이 다르므로, 메시지를 처리하는 방식은 객체마다 서로 다를 수 밖에 없다
    • 이는 다형성(동일한 요청에 대해 서로 다른 방식으로 응답할 수 있는 능력)에 의미를 부여한다
      동일한 메시지를 서로 다른 방식으로 처리하기 위해선 객체들이 동일한 메시지를 수신할 수 있어야 하므로, 결과적으로 다형적인 객체들은 동일한 타입(또는 타입 계층)에 속하게 된다

  2. 타입의 고려 대상이 행동뿐이라는 것은, 외부에 데이터(상태)를 감추어야 한다는 것을 의미한다

    • 따라서, 좋은 객체지향 설계는 외부에 행동만을 제공하고, 데이터는 행동 뒤에 감춰야 한다
      이 원칙을 캡슐화라고 한다
    • 즉, ‘공용 인터페이스 뒤로 데이터를 캡슐화하라’는 원칙은, 객체를 행동에 따라 분류하기 위함이다

5. 타입의 목적

객체지향은 객체를 지향하는 것인데 왜 타입을 같이 사용하는 것일까?

그 이유는, 인간의 인지 능력으로는 시간에 따라 동적으로 변하는 객체의 복잡성을 극복하기 어렵기 때문이다

  • 나의 몸무게는 어느 시점엔 90kg고, 어느 시점엔 85kg이다
    그러나 모든 상황에 ‘나’는 항상 ‘나’일 뿐이다

객체의 상태는 변하지만, 해당 객체를 다른 객체와 구별할 수 있는 식별성은 동일하게 유지된다
따라서, 우리는 객체가 가질 수 있는 모든 상태값의 경우의 수를 생각할 필요 없이, 객체가 값이 변할 수 있는 상태를 가진다고 단순화해서 생각하면 된다

  • ‘나’라는 객체는 변할 수 있는 몸무게라는 상태를 지닌다고 단순화할 수 있다

즉, 타입은 시간에 따라 동적으로 변하는 객체의 상태를 시간과 무관한 정적인 모습으로 다룰 수 있게 해준다

이런 관점에서 결국 타입은 추상화다

  • 어떤 시점의 객체에 관해 생각할 때, 불필요한 요소(상태의 변화, 시간)를 제거하고 철저하게 정적인 관점에서 객체의 모습을 묘사하게 해준다
  • 즉, 타입을 이용하면 객체의 동적인 특성을 추상화할 수 있다

타입의 계층

1. 일반화, 특수화

타입과 타입 사이에는 일반화/특수화 관계가 존재한다
또한, 일반화와 특수화는 동시에 일어난다

  1. 일반화(Generalization)
    • 전화기는 스마트폰보다 더 일반적인(포괄적인) 개념이다
      더 포괄적이므로, 전화기는 스마트폰에 속하는 객체를 포함한다
  2. 특수화(Specialization)
    • 스마트폰은 전화기보다 더 특수한 개념이다
      특수하므로, 스마트폰 개념은 전화기 개념의 부분 집합이 된다

중요한 것은, 객체지향에서 일반화/특수화 관계를 결정하는 것은 데이터(상태)가 아니라 행동(책임)이라는 것이다
즉, 일반화/특수화 관계가 성립하려면 한 타입은 더 특수하게 행동해야 하고, 다른 타입은 더 일반적으로 행동해야 한다

행동의 관점에서 더 일반적인 타입이란, 특수한 타입이 가진 모든 행동 중 일부 행동만을 가지는 타입을 가리킨다
반대로 더 특수한 타입이란, 일반적인 타입이 가진 모든 행동을 포함하는 동시에 자신만의 행동을 추가로 가지는 타입을 가리킨다

  • 스마트폰은 전화 뿐 아니라 인터넷 접속 등의 행동도 포함한다
    즉, 스마트폰과 전화기는 특수화-일반화 관계이다

2. 슈퍼타입, 서브타입

일반화/특수화 관계에서 일반적인 타입은 슈퍼타입(Supertype), 특수한 타입을 서브타입(Subtype)이라고 한다

위에서 강조했듯, 슈퍼타입과 서브타입의 관계 역시 행동에 의해 결정된다
즉, 어떤 타입이 다른 타입의 서브타입이 되기 위해서는 행위의 호환성을 만족시켜야 한다

그 말은 즉슨, 서브타입은 슈퍼타입을 대체할 수 있어야 한다는 뜻이다

3. 일반화는 추상화를 위한 도구다

우리는 전화를 걸어야 할 때 전화기를 찾지, 스마트폰을 찾진 않는다
즉, 일반화 역시 추상화를 위한 도구이다

  • 스마트폰의 불필요한 기능(다양한 어플리케이션)은 제거하고, 그 시점에 중요한 ‘전화’ 기능에만 집중해서 상황을 단순하게 만든 것이다

더 자세히 말하면, 일반화는 추상화의 두 번째 차원(중요한 부분을 강조하기 위해 불필요한 세부 사항을 제거하는 단순화)를 적절히 활용하는 예시이다

동적 모델과 정적 모델

우리는 객체를 생각할 때, 두 가지 모델(동적 모델, 정적 모델)을 동시에 고려한다

1. 동적 모델(Dynamic model)

객체가 특정 시점에 구체적으로 어떤 상태를 가지는지를 표현한다
즉, 실제로 객체가 살아 움직이는 동안 상태가 어떻게 변하고 어떻게 행동하는지를 표현하는 모델이다

이를 객체의 스냅샷(Snapshot)이라고 한다

UML에서는 스냅샷을 객체 다이어그램(Object diagram)이라고도 부른다

2. 정적 모델(Static model)

객체가 가질 수 있는 모든 상태와 행동을, 시간에 독립적으로 표현한다
즉, 객체가 속한 타입의 정적인 모습을 표현하는 모델이다

타입 모델(Type model)이라고도 부른다

3. 클래스와 정적 모델

객체지향 프로그래밍 언어에서, 정적인 모델은 클래스를 이용해 구현된다
따라서, 타입을 구현하는 가장 보편적인 방법은 클래스를 이용하는 것이다

‘타입을 구현한다’라는 문장에서 알 수 있듯이, 클래스와 타입은 동일한 것이 아니다

  • 타입은 객체를 분류하기 위해 사용하는 개념이다
  • 클래스는 타입을 구현할 수 있는 여러 구현 메커니즘 중 하나이다
    (JS와 같은 프로토타입 기반 언어에는 클래스가 존재하지 않음을 기억하자)

클래스와 타입을 구분하는 것은 유연한 설계의 바탕이 된다

  • 클래스는 타입의 구현 외에도, 코드 재사용 등의 용도로도 사용된다
    즉, 클래스와 타입을 같은 것이라 생각하면 이런 부분에서 오해와 혼란이 발생한다

정리하자면 다음과 같다

  1. 객체를 분류하는 기준은 타입이다
  2. 타입을 나누는 기준은 객체가 수행하는 행동이다
  3. 클래스는 타입을 구현하는 방법 중 하나이다
    (즉, 클래스와 타입은 같은 것이 아니다)
