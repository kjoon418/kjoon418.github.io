객체지향 설계의 세 가지 관점

개념 관점, 명세 관점, 구현 관점은 동일한 코드를 바라보는 서로 다른 관점이다

훌륭한 객체지향 프로그래머가 되기 위해서는, 하나의 클래스 안에 세 가지 관점을 모두 포함하면서도, 각 관점에 대응되는 요소를 명확하고 깔끔하게 드러낼 수 있어야 한다

1. 개념 관점(Conceptual Perspective)

// 커피를 만드는 책임을 지니는 객체 이름을 Barista로 짓는다
public class Barista { }

도메인 안에 존재하는 개념과, 개념들 사이의 관계를 표현하는 관점이다
즉, 소프트웨어 클래스에 실제 도메인의 규칙과 규약을 최대한 반영하는 관점이다

소프트웨어 클래스가 도메인 개념의 특징을 수용할수록, 변경을 관리하기 쉽고 유지보수가 용이해진다

  • 만약 커피를 제조하는 과정을 변경해야 한다면 어디를 수정해야 할 것 같은가?
    현실 세계에서 그렇듯, 커피를 제조하는 사람은 바리스타이므로 Barista 클래스를 수정하면 된다

즉, 소프트웨어 클래스와 도메인 클래스 사이의 간격이 좁을수록, 유지보수의 복잡도가 줄어든다

2. 명세 관점(Specification Perspective)

public class Barista {
	// 커피를 만드는 메서드를 공용 인터페이스로 만든다
	public Coffee makeCoffe(String coffeeName) { }
}

객체가 협력을 위해 ‘무엇’을 할 수 있는가에 초점을 맞추는 관점이다
즉, 객체의 인터페이스를 바라보는 관점이다

인터페이스를 수정할 경우, 해당 객체와 협력하는 모든 객체가 영향받는다
즉, 인터페이스는 최대한 변화에 안정적으로 만들어야 한다

그를 위해선, 인터페이스가 구현과 관련된 세부 사항을 포함하지 않아야 한다

3. 구현 관점(Implementation Perspective)

public class Barista {
	public Coffee makeCoffee(String coffeeName) {
		// 실제로 동작하는 코드를 구현한다
		return new Coffee(coffeeName);
	}
}

객체들이 책임을 수행하는 데 필요한, ‘동작하는 코드’를 작성하는데 초점을 맞추는 관점이다
즉, 객체의 실제 코드를 바라보는 관점이다

클래스의 내부 구현의 변경은 ‘원칙적으로는’ 외부 객체에 영향을 미쳐선 안된다
(현실적으론 100% 파급효과 없는 변경이 불가능한 경우도 있다)

클래스의 메서드와 속성은 내부 구현에 속하고, 외부 인터페이스에 속하지 않는다
즉, 메서드와 속성은 철저하게 클래스 내부로 캡슐화되어야 한다

4. 중요한 것은 인터페이스와 구현의 분리이다

개념 관점과 명세 관점 사이의 관계는 그렇게 중요하지 않은 경우도 많다
하지만, 명세 관점과 구현 관점을 분리하는 것은 매우 중요하다

명세 관점(인터페이스)이 설계를 주도하게 하라
다음 경우들은 절대 발생하면 안되는 안티 패턴들이다

  1. 구현이 인터페이스 밖으로 노출되는 캡슐화 위반
  2. 인터페이스와 구현의 명확하지 않은 분리
