개요

우테코 프리코스 미션으로 "나만의 프레임워크 만들기"를 시도했는데, 제네릭을 적극적으로 도입하며 구현하는 과정에서 공변, 무공변, 반공변이라는 개념을 만났다.

일단 도입해서 구현은 성공적으로 마무리 지었지만, 제네릭을 완벽히 이해했다고 자신만만해하던 내가 부끄러워 다시 정리하며 제대로 공부해보고자 한다.

공변, 무공변, 반공변 뿐 아니라, 제네릭의 기초부터 심화까지 모두 살펴보도록 하자.

타입 파라미터란?

// 여기서 T를 '타입 파라미터'라고 부른다!
class Hello<T> {
	fun hi(t: T) {
		println(t)
	}
}

제네릭을 본격적으로 배우기 전, 앞으로 가장 많이 마주칠 단어의 뜻을 알아보고 가자.

제네릭의 타입을 지정하는 파라미터를 타입 파라미터라고 부른다.
대문자 1개를 사용하는 것이 관례이며, 타입 파라미터를 지닌 클래스를 제네릭 클래스라고 한다.

제네릭의 장점

1. 제네릭을 사용하지 않을 때의 문제점

1-1. 객체의 타입을 고정하는 경우
// Fish에 대해서는 잘 동작한다
val fishes = FishList()
val fish: Fish = fishes.first()

// 하지만 필요한 모든 타입에 대해서 같은 기능을 구현해야 한다
val cats = CatList()
val cat: Cat = cats.first()

Fish에 대한 리스트가 필요해서 FishList를 만들었다.

Fish에 대해서는 아주 잘 동작하지만, 만약 똑같은 기능이 Cat에도 필요하다면 어떨까?
FishList는 오직 Fish를 위해서만 존재하므로, 필요한 기능은 똑같더라도 별도의 객체인 CatList를 또 만들어야 할 것이다.

1-2. Any를 사용하는 경우
// Any를 사용할 경우
val fishes = AnyList()
val cats = AnyList()

// 모두 캐스팅해서 사용해야 한다
val fish: Fish = fishes.first() as Fish
val cat: Cat = cats.first() as Cat

// 심지어 이런 실수도 컴파일 단계에서 파악할 수 없다
fishes.add(cat)

여러 객체에 대해 같은 기능을 재활용하고 싶어서 AnyList를 만들었다.

위와 같이 AnyList라는 클래스 하나를 fishes, cats처럼 여러 상황에 활용 가능하다.

단, 다음과 같은 문제가 있다.

  1. 타입을 캐스팅해서 사용해야 한다
    • 리스트에서 값을 꺼낼 때 항상 fishes.first() as Fish처럼 타입을 캐스팅해서 사용해야 한다.
    • 번거로울 뿐 아니라, 해당 인스턴스의 타입이 부적절할 수 있다는 위험을 항상 감수해야 한다.
  2. 잘못된 타입을 사용하더라도, 컴파일 단계에서 알 수 없다
    • Fish와 Cat은 모두 Any로 추상화할 수 있다.
    • 그렇기 때문에, fishes에 cat을 추가한다고 해서 컴파일러는 아무 경고나 조치를 취하지 않는다.
    • 추후에 fishes.first() as Fish 코드가 실행될 때에서야 문제를 파악할 수 있을 것이다.

2. 제네릭을 사용해 해결하자

val fishes = List<Fish>()
val cats = List<Cat>()

val fish: Fish = fishes.first()
val cat: Cat = cats.first()

// 다음과 같은 잘못된 코드는 컴파일러가 잡아준다
fishes.add(cat)

제네릭을 도입하면, 위에서 언급한 문제를 모두 해결하면서도 객체를 유연하게 만들 수 있다.

  1. 객체의 유연성
    • 하나의 List<T> 객체를 fishes, cats 등 여러 상황에 활용할 수 있다.
  2. 타입 캐스팅
    • fishes는 List<Fish>이고, cats는 List<Cat>이다.
    • 각각 상황에 맞는 타입이 규정되어 있기 때문에, 값을 꺼낼 때도 캐스팅할 필요 없고, 잘못된 값을 넣는 실수는 컴파일러가 바로 잡아준다.

상속관계와 제네릭

1. 제네릭을 사용하지 않고 구현해보자

class Fish : Animal { ... }
class Cat : Animal { ... }

사실 Cat과 Fish는 모두 Animal의 구현체들이었다.
그렇다면 제네릭 없이도 아래처럼 해결할 수 있지 않을까?

val fishes = AnimalList()
val cats = AnimalList()

// 앗 Any를 사용할 때랑 똑같네...
val fish: Fish = fishes.first() as Fish
val cat: Cat = cats.first() as Cat
fishes.add(cat) // 실수가 발생해도 컴파일러가 막지 못한다

// 그래도 해당 객체를 Animal만 사용할 수 있게 강제할 수 있다
val number: Int = 5
fishes.add(number) // 컴파일러가 막아준다!

AnyList때 보단 낫지만, 여전히 비슷한 문제가 존재한다.

하지만, 해당 객체를 Animal과 그 하위 타입만 사용하도록 제한할 수 있게 되었다.
제네릭으로는 이런 걸 못하지 않을까?

2. 제네릭으로 해결해보자

// T는 Animal이거나 그 하위 타입이어야 한다
class List<T : Animal> { ... }

val fishes = List<Fish>()
val cats = List<Cat>()

// 컴파일러가 다 잡아준다
fishes.add(cat)
fishes.add(5)

당연히 된다.
이를 제네릭 제약이라고 부른다.
(제네릭 제약에 대해서는 뒤에서 자세하게 알아보자)

타입 파라미터를 <T : 타입>처럼 선언하면, 제네릭 타입 T를 타입과 그 하위 타입만으로 제한할 수 있다.

interface Animal {
    fun run()
}

class List<T : Animal> {
    private val animals = mutableListOf<T>()
    
    fun runEveryAnimals() {
        for (t: T in animals) {
            // T이지만 Animal의 메서드에 접근 가능하다!
            t.run()
        }
    }
}

또한, 위와 같은 경우 T는 항상 Animal 혹은 그 하위 타입이니, T가 Animal의 메서드와 속성을 사용하는 것도 가능하다.

제네릭과 무공변, 공변, 반공변

1. 일반적인 상속 관계

val cat: Cat = Cat()

// 상위 타입인 Animal 변수에 Cat 인스턴스를 대입할 수 있다
val animal: Animal = cat

// 상속 관계가 없으니 대입할 수 없다
val animal: Animal = 5 // Animal에 Int를 대입할 수 없다

객체 간 상속관계가 있다면, 위와 같이 하위 타입 인스턴스는 상위 타입으로 취급할 수 있다.
제네릭에서는 이런 상속 관계를 어떻게 처리할까?

2. 무공변(invariance)

(불공변이라고도 부른다)

2-1. 무공변이란?
class List<T> { ... }

val cats: List<T> = List()
val animals: List<Animal> = cats // 컴파일 에러가 발생한다

Cat과 Animal 간 상속 관계가 있더라도, 위와 같이 List<Cat>과 List<Animal>은 완전히 서로 다른 타입으로 취급된다.
이를 무공변하다라고 한다.

또한, Kotlin의 제네릭은 기본적으로 무공변으로 동작한다

2-2. 왜 무공변할까?
Cat[] cats = new Cat[5];

// Cat[]이 Animal[]에 문제 없이 잘 대입된다
Animal[] animals = cats;

Kotlin의 제네릭이 무공변을 선택한 이유를 알기 위해선, 공변한 것의 문제를 먼저 이해해야 한다.

이를 위해 Java 배열 예시를 살펴보자.
Java 배열은 Animal[] 변수에 Cat[] 인스턴스를 대입할 수 있다.

Animal과 Cat의 상속 관계가 Animal[]과 Cat[]에도 반영되는 이런 특징을 공변(co-variant)하다 라고 한다.

Cat[] cats = new Cat[5];
Animal[] animals = cats;

// 컴파일 상으론 문제가 없지만, 런타임에 실제로 대입할 때 문제가 발생한다
animals[0] = new Fish();

공변한 배열은 위와 같은 문제를 지닌다

컴파일러 상으로는 Animal 배열에 Fish를 삽입하는 것이므로 통과되지만, 실제 런타임 시에는 Cat 배열에 Fish를 삽입하는 것이 되기 때문이다

  • 실제 대입 시 ArrayStoreException이 발생한다
  • 즉, 문제가 컴파일 시에 잡히지 않고 런타임 시점에 잡힌다
List<Cat> cats = List.of(cat1, cat2, cat3);
List<Animal> animals = cats; // 컴파일 에러가 발생한다

이런 문제 때문에, Java의 제네릭 역시 무공변하다

즉, 위와 같은 코드에서 컴파일 에러가 발생한다

3. 공변(co-variant)

3-1. 공변해도 괜찮은 상황
class List<T : Animal> {
    private val elements = mutableListOf<T>()

    fun addAll(other: List<T>) {
        for (element: T in other.elements) {
            elements.add(element)
        }
    }
}

// 이 코드가 문제가 될까?
val cats: List<Cat> = List()
val animals: List<Animal> = List()

animals.addAll(cats) // 문제가 없음에도 컴파일 에러가 발생한다

위와 같이 List에 또 다른 List<T>를 파라미터로 받는 addAll 메서드가 존재한다고 가정해보자.
과연 animals.addAll(cats) 코드가 문제가 될까?

  • Cat은 Animal의 하위 타입이므로, List<Animal>에 Cat 원소들을 삽입한다고 해서 아무 문제도 발생하지 않을 것이다.
  • 하지만 제네릭은 무공변하기 때문에, 위 코드에서 컴파일 에러가 발생하게 된다.

제네릭을 공변하게 사용할 순 없을까?

3-2. 공변하게 만들어보자
class List<T : Animal> {
    fun addAll(other: List<out T>) {
        // ...
    }
}

val cats: List<Cat> = List()
val animals: List<Animal> = List()
animals.addAll(cats) // 컴파일 에러가 발생하지 않는다

방법은 간단하다.
타입 파라미터에 out 키워드를 붙여주는 것으로 공변하게 만들 수 있다.

  • 이렇게 공변하게 만드는 것을 ‘변성을 준다’라고도 표현한다.
    (변성을 준다는 것은, ‘공변을 주는 것’과 ‘반공변을 주는 것’을 포함하는 개념이다)

out은 변성을 주는 키워드이므로, 이런 키워드를 variance annotation이라고도 부른다.

3-3. out의 의미
class List<T : Animal> {
    private val elements = mutableListOf<T>()

    fun addAll(other: List<out T>) {
        // 데이터를 꺼내는 것은 괜찮다
        val data: T = other.first()

        // 데이터를 넣는 것은 컴파일 에러가 발생한다
        for (element: T in elements) {
            other.elements.add(element)
        }
    }

    fun first(): T {
        return elements.first()
    }
}

out이란 것은, 해당 제네릭에서 데이터를 꺼내는 것만 가능하다는 의미이다.
이를 다른 말로, 해당 제네릭은 생산자 역할만 할 수 있다고도 한다.

왜 out을 붙이면 소비자 역할을 하지 못하게 막을까?

class List<T : Animal> {
	private val elements = mutableListOf<T>()
		
    fun addAll(other: List<out T>) {
        for (element: T in elements) {
            other.elements.add(element)
        }
    }
}

val cats: List<Cat> = List()
val animals: List<Animal> = List()

animals.addAll(cats) // List<Cat>에 List<Animal>의 원소들이 삽입된다!

소비자 역할이 가능하다면 어떤 일이 벌어질지 생각해보자.

위와 같이 하위 타입인 Cat 리스트에 Animal 원소가 삽입될 수 있게 된다.
즉, 타입 안정성이 깨지게 되어 런타임 에러가 발생할 것이다.

이런 이유 때문에 out을 붙이면 소비자 역할만 가능하도록 제한한다.

4. 반공변(contravariance)

4-1. 반공변이란?
val animals: List<Animal> = List()
val cats: List<Cat> = animals

타입의 상속 관계를 반대로 적용했다 생각하면 된다.
(또한, 공변의 반대 개념이다)

위와 같이 상위 타입을 하위 타입으로 취급할 수 있는 것을 반공변하다라고 표현한다.

4-1. 반공변해도 괜찮은 상황
class List<T : Animal> {
    private val elements = mutableListOf<T>()

    fun addAllTo(other: List<T>) {
        for (element in elements) {
            other.elements.add(element)
        }
    }
}

val cats: List<Cat> = List()
val animals: List<Animal> = List()

cats.addAllTo(animals) // 문제가 없음에도 컴파일 에러가 발생한다

위의 경우, List<Cat>의 원소를 List<Animal>에 삽입하는 것이므로, 아무 문제도 발생하지 않을 것이다.

하지만 Kotlin의 제네릭은 무공변하므로, List<Cat>의 addAllTo에 List<Cat>이 아닌 다른 타입을 전달할 수 없다.

4-2. 반공변하게 만들자

class List<T : Animal> {
    private val elements = mutableListOf<T>()

    fun addAllTo(other: List<in T>) {
        for (element in elements) {
            other.elements.add(element)
        }
    }
}

val cats: List<Cat> = List()
val animals: List<Animal> = List()

cats.addAllTo(animals) // 잘 동작한다!

out 키워드와 반대로, in 키워드를 사용하면 반공변하게 만들 수 있다

이렇게 in 키워드가 붙을 경우, 해당 제네릭 인스턴스는 소비자 역할만 할 수 있다.

해당 제네릭 인스턴스는 소비자 역할만 하므로, 동일 타입 혹은 더 상위 타입이야 한다.

선언 지점 변성과 사용 지점 변성

1. 선언 지점 변성(Declaration-site Variance)이란?

// 클래스 선언 시점에 변성을 지정했다
class List<out T> { /* ... */ }

클래스 혹은 인터페이스를 선언하는 시점에 out이나 in 키워드를 붙여 변성을 지정하는 방식이다.
즉, 제네릭 클래스 자체를 공변하게 만드는 방식이다.

Java에서는 불가능하고, Kotlin의 제네릭만이 지니고 있는 특징이다.

2. 사용 지점 변성(Use-site Variance)이란?

class List<T> { /* ... */ }

// 변수 사용 시점에 변성을 지정했다
val animals: List<out Animal> = List()

클래스 혹은 인터페이스 선언 시점에는 변성이 지정되지 않았지만, 특정 함수나 변수에서 사용할 때 변성을 부여하는 방식이다.

Java의 와일드카드(<? extends …>, <? super …>)가 사용 지점 변성 방식에 해당한다.

  • 참고로, <out T>가 <? extends T>와 대응되고, <in T>가 <? super T>와 대응된다.

3. 선언 지점 변성을 사용하려면?

3-1. 생산만 하는 클래스는 공변하게 만들 수 있다
// UnmodifiableList는 생산만 한다
class UnmodifiableList<out T> {
    private val elements = listOf<T>()
    
    fun first(): T {
        return elements.first()
    }
    
    fun all(): List<T> {
        return elements
    }
}

// UnmodifiableList<Animal>이 Cat을 생산할 수 있다!
val cats = UnmodifiableList<Cat>(listOf(cat1, cat2, cat3))
val animals: UnmodifiableList<Animal> = cats // <Animal>에 <Cat>을 대입 가능하다
val first: Animal = animals.first() // 실제로는 Cat 인스턴스를 생산한다

어떤 제네릭 클래스(혹은 인터페이스)가 오직 생산만 한다면, 그 클래스는 공변해도 문제가 없을 것이다.

이 경우, 클래스의 타입 파라미터 선언에 out 키워드를 붙여서 클래스 자체를 공변하게 만들 수 있다.

3-2. 소비만 하는 클래스는 반공변하게 만들 수 있다
// Printer는 소비만 한다
class Printer<in T> {
    fun print(value: T) {
        println("value = $value")
    }
}

// Printer<Animal>이 Cat을 소비할 수 있다!
val cat: Cat = Cat()
val animalPrinter: Printer<Animal> = Printer()
val catPrinter: Printer<Cat> = animalPrinter // <Cat>에 <Animal>을 대입 가능하다

catPrinter.print(cat) // 실제 인스턴스는 Printer<Animal>이지만 Cat을 소비할 수 있다

반대로 오직 소비만 하는 제네릭 클래스(혹은 인터페이스)가 있다면, 그 클래스는 반공변해도 문제가 없을 것이다.

똑같이 클래스의 타입 파라미터 선언에 in 키워드를 붙여서 클래스 자체를 반공변하게 만들 수 있다.

4. UnsafeVariance

class UnmodifiableList<out T>(
    private val elements: List<T>
) {
    // T 파라미터를 받을 수 없어야 하지만, 애노태이션을 통해 허용한다
    fun contains(element: @UnsafeVariance T): Boolean {
        // 어차피 단순 비교만 수행하므로, 다른 타입이 들어오더라도 안전하다
        return elements.contains(element)
    }
}

// 정말 타입 안전한 상황이라면, 공변한 제네릭 클래스가 소비도 가능하도록 허용할 수 있다
val cats: UnmodifiableList<Cat> = UnmodifiableList(listOf(cat1, cat2, cat3))
val animals: UnmodifiableList<Animal> = cats

animals.contains(cat1) // UnmodifiableList가 무언가를 소비하고 있다

생산자 역할을 하는 클래스지만, 위의 contains 메서드처럼 다른 타입이 들어와도 문제 없이 처리할 수 있는 경우도 있다.
즉, 소비할 때 타입 안전한 경우가 존재한다.

이럴 때는 파라미터에 @UnsafeVariance를 붙여 소비가 가능하도록 허용할 수 있다.

  • 당연히, 이 경우 해당 로직이 타입 안전함을 개발자가 보장해야 한다.

제네릭 제약(Generic Constraints)

1. 제네릭 제약이란?

class Container<T : Animal>(
    private val value: T
)

// Cat과 Animal은 되지만, Int를 넣으려 하면 컴파일 에러가 발생한다!
val cat: Cat = Cat()
val animal: Animal = Animal()
val number: Int = 5

val catContainer: Container<Cat> = Container(cat)
val animalContainer: Container<Animal> = Container(animal)
val numberContainer: Container<Int> = Container(number) // 컴파일 에러 발생

제네릭 타입에 특정 타입과 그 하위 타입들만 사용할 수 있도록 제한하는 것을 말한다.

상속 문법과 같이, <타입_파라미터 : 타입> 형식으로 선언할 수 있다.

2. 제네릭 제약 여러 개 두기

// Comparable을 구현한 Animal 및 하위 타입으로 제한한다
class AnimalSorter<T> where T : Animal, T : Comparable<T> {
    fun sort(vararg animals: T): List<T> {
        return animals.sorted()
    }
}

// 함수에도 적용할 수 있다
class AnimalSorter {
    fun <T> sort(vararg animals: T): List<T> where T : Animal, T : Comparable<T> {
        return animals.sorted()
    }
}

제네릭 타입에 대해 한 번에 여러 제약조건을 걸고 싶을 수도 있다.

그럴 때는 위와 같이 where 키워드를 사용하고 제약조건들을 쉼표(,)로 구분해주면 된다.

3. 제네릭 제약으로 null 막기

// 아무 제약조건도 지정하지 않으면, Any?처럼 모든 타입이 올 수 있게 된다
class List<T> { }

val cats: List<Cat?> = List()

// 타입 제한은 없되 null을 불허하고 싶다면 Any로 제한해주자
class List<T : Any> { }

val cats: List<Cat?> = List() // 컴파일 에러가 발생한다

제네릭 타입에 아무 제약도 걸지 않으면, Any? 타입에 대입될 수 있는 모든 타입을 사용할 수 있게 된다.
즉, null을 허용하게 된다.

만일 타입에 제한을 두고싶진 않지만 null을 허용하면 안될 경우엔, <T : Any>처럼 제약해주자.

타입 소거

1. 타입 소거란?

fun Any.isIntList(): Boolean {
	// 타입 소거로 인해 List<Int>인지 비교 자체가 불가능하다
	return this is List<Int>
}

Kotlin 역시 JVM 위에서 동작하기 때문에, Java 제네릭의 타입 소거가 똑같이 적용된다.
즉, 런타임 때는 제네릭의 타입 정보가 사라진다.

때문에, 위와 같이 런타임 때 제네릭 타입(<Int>)에 접근할 수 없어 컴파일 에러가 발생한다.

2. Star Projection

// List인지 알아내는 것은 가능하다
fun Any.isList(): Boolean {
	return this is List<*>
}

하지만, 소거되는 것은 제네릭 타입 뿐이니, 클래스/인터페이스 자체의 타입 정보는 가져올 수 있다.

이럴 때 제네릭 타입은 *로 명시하면 되는데, 이를 Star Projection이라고 한다.

  • Star Projection은 어떤 타입이든 상관없다는 것을 의미한다.
// 안에 어떤 데이터가 있는지 모르니 Any?로 가져온다
fun List<*>.first(): Any? {
	return this[0]
}

// 데이터를 소비하게 만들 수는 없다
fun MutableList<*>.put(value: Any?) {
	return this.add(value) // 컴파일 에러가 발생한다
}

이 때 제네릭 타입이 무엇인지 모르니, 데이터를 꺼낼 땐 Any?로 취급한다.

어떤 데이터를 사용하는지 모르니, 데이터를 소비하게 만들 수는 없다.

fun Collection<String>.isMutable(): Boolean {
    return this is MutableList<String>
}

단, Kotlin 컴파일러는 타입 추론 기능을 제공하므로, 위와 같은 코드는 컴파일 에러가 발생하지 않는다.

3. inline reified로 타입 정보 얻기

// T에 대한 정보를 알 수 없으니 컴파일 에러가 발생한다
fun <T> List<*>.hasInstanceOf(): Boolean {
	return this.any { it is T }
} 

// 컴파일 에러가 발생하지 않는다
inline fun <reified T> List<*>.hasInstanceOf(): Boolean {
	return this.any { it is T }
}

inline과 reified 키워드를 같이 사용하면, 함수가 제네릭 타입을 알 수 있도록 만든다.

각 키워드는 다음과 같은 역할을 한다.

  1. inline
    • 컴파일 될 때, 함수의 코드를 호출한 위치에 그대로 복사해 붙여넣도록 만든다.
    • 즉, 실제 컴파일된 코드에서는 함수를 호출하는 형태로 동작하지 않고, 복사된 코드를 그대로 실행하게 된다.
  2. reified
    • inline을 통해 함수를 붙여넣을 때, 제네릭 타입 T를 호출할 때 사용된 진짜 타입 클래스로 바꿔치기하게 만든다.
    • 즉, 제네릭 타입(T)이, 런타임에 접근 가능한 실제 클래스로 변환되어 코드에 작성된다.
// 이렇게 정의한 함수가 있을 때, 컴파일은 아래처럼 이루어진다
inline fun <reified T> List<*>.hasInstanceOf(): Boolean {
		return this.any { it is T }
}

// 1. 컴파일 전
val list = listOf(1, "Hi", true)
val result = list.hasInstanceOf<Int>()

// 2. 컴파일 후(만일 reified를 사용하지 않았다면)
val list = listOf(1, "Hi", true)
val result = list.any { it is T } // 런타임 때 T에 대한 정보는 없어지니 컴파일이 불가능하다

// 3. 컴파일 후(inline과 reified를 같이 사용한 경우)
val list = listOf(1, "Hi", true)
val result = list.any { it is Int } // 제네릭 타입에 대한 정보가 실제 클래스로 치환된다

inline과 reified를 사용하면, 위와 같은 과정을 거쳐 컴파일되므로 제네릭 타입의 타입 정보를 알아낼 수 있게 된다.

제네릭과 쉐도잉

class Printer<in T> {
    // 이 함수에 선언된 T는 클래스에 선언된 T를 쉐도잉한다
    fun <T> print(value: T) {
        println("value = $value")
    }
}

// 지역 변수가 전역 변수를 쉐도잉하는 것과 동일하다
val hello = "Hello"

fun main() {
    val hello = "World!"
    println(hello) // "World!"가 출력된다
}

타입 파라미터 역시 쉐도잉이 적용된다.

이를 인지하고, 가급적 타입 파라미터 이름을 서로 다르게 해 쉐도잉되지 않도록 만들자.
