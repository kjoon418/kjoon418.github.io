0. 개요

우아한테크코스 8기 프리코스의 마지막 미션인 오픈 미션을 진행하며, 나만의 서버 프레임워크를 만들어 보자고 마음먹었다.

프레임워크는 다양한 환경에 유연하게 대응할 수 있어야 한다고 생각해, HTTP 뿐 아니라 WSS, STMP 등 다양한 통신 프로토콜에 확장 가능하도록 인터페이스를 추상화하려고 했다.

하지만 정작 통신 프로토콜에 대한 식견이 없어, 인터페이스를 HTTP 기반으로 설계할 수 밖에 없었다...
그렇기에 대부분 통신 프로토콜들이 공유하고 있는 요소는 무엇이 있는지, 이를 어떻게 추상화할 수 있는지 (추상화할 수는 있는지) 공부하고 기록하고자 한다.

1. OSI 7계층

프로토콜의 공통점을 찾기 위해서는, 내가 추상화하고 싶은 프로토콜이 어느 계층에 해당하는지부터 알고 있어야 한다.

당신이 서버 개발자라면, 당연히 가장 중요한 계층은 응용 계층(Application Layer)이 될 것이다.
우리가 다룰 데이터는 (일반적으로) 응용 계층의 프로토콜이 전달해 주는 데이터이기 때문이다.

2. 응용 계층의 핵심 역할

응용 계층의 역할은 여럿 있지만, 서버 개발자 입장에서 크게 느껴지는 역할들은 다음과 같다.

  1. 무엇을 해야 하는지 정의한다.
    • 보내는 데이터에 어떤 행동을 해야 하는지를 같이 정의한다.
    • HTTP의 경우 HTTP Method(GET, POST, PUT 등)이 이에 해당한다.
  2. 데이터의 형식을 정의한다.
    • 두 애플리케이션이 서로 알아들을 수 있도록, 데이터의 구문과 형식을 정의한다.
    • HTTP의 경우 Content-Type 헤더가 이에 해당한다.
  3. 서비스나 리소스를 식별한다.
    • 4계층이 '포트 번호'로 서버 내의 애플리케이션을 식별한 것 처럼, 7계층은 애플리케이션의 특정 서비스나 리소스를 식별한다.
    • HTTP의 경우 Domain과 Path가 이에 해당한다.

즉, 이 세 가지 요소를 잘 이해한다면, 여러 프로토콜에 대응할 수 있는 하나의 추상화된 클래스를 만들 수 있게 될 것이다.

3. 데이터 포장 규칙

모든 프로토콜은 각각 PDU(Protocol Data Unit)을 지닌다. PDU는 데이터를 포장하는 규칙을 정의하는 것으로, 우리에게 익숙한 헤더-페이로드 구조가 이에 속한다.

정말 간단한 프로토콜(Stream 등)이나 Telnet과 같은 몇 예외를 제외하면, 7계층 프로토콜 대부분은 헤더-페이로드 구조를 사용한다.
나의 목적은 서버 애플리케이션을 위해 프로토콜을 추상화하는 것이므로, 과감하게 모든 프로토콜이 헤더-페이로드 구조를 지닌다고 가정해보자.
(Stream, Telnet의 데이터 역시 헤더-페이로드 구조로 매핑할 수 있다고 기대한다)

4. 그래서 어떻게 추상화하지?

interface RequestData<T> {
	// 메타데이터(헤더)
    val headers: Map<String, List<String>>

	// 페이로드(본문)
    val payload: T
    
    // 컨텍스트(데이터의 목적 - HTTP의 Method, URI 등)
    val requestContext: RequestContext
}

enum class RequestContext {
    READ, WRITE, UPDATE, DELETE,
    CONNECT, SEND, SUBSCRIBE,
    AUTHORIZATION, ACKNOWLEDGE
}

이런 느낌으로 추상화할 수 있겠다.
다만, 요청의 컨텍스트(맥락)를 추상화할 수 있을지는 의문이 남는다.

당장 STOMP 기반의 웹소캣만 봐도 HTTP와 이질적이다.
HTTP는 GET, POST, DELETE 등을 사용하는 것에 반해, STOMP는 CONNECT, SEND, SUBSCRIBE 등으로 프레임의 목적을 표현한다.
과연 이렇게 서로 다른 프로토콜들을 하나의 타입으로 추상화할 수 있을까?

일단 위와 같이 구현하면 동작은 하겠지만, 한 enum이 너무 많은 데이터를 품고 있는 것이 아닐까 하는 찝찝함이 남는다.

5. 마치며

썩 만족스럽진 않지만, 어찌저찌 굴러가도록 추상화하는 것에는 성공했다. 비록 RequestContext가 모든 프로토콜을 수용하기 위해 난잡해질 수는 있지만, 프레임워크 내부에서 사용하기엔 충분할 것 같다.

아직은 부족한 것이 많아, 어느 정도 공부한다고 해서 날카로운 답을 제시하기엔 어려움이 있다고 느껴진다. 기회가 된다면 HTTP 뿐 아니라 WSS, STMP 등의 프로토콜도 깊이 있게 학습하고 다시 고민해봐야겠다.
