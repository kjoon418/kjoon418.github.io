개요

어느덧 초록스터디 2주차 과제까지 완료했다.
기존엔 REST API만 개발해서 MVC 패턴을 사용할 일이 많이 없었는데, 이번 기회에 MVC 패턴을 사용해보며 고민하는 시간을 가졌다.
아직도 각 계층이 정확히 어떤 역할을 해야 하는지는 미숙하지만, 조금씩 공부해나가며 발전해나가겠다.

새로 배운 것

Controller의 책임은 어디까지?

public class Controller {

	private final InputView view = new InputView();
    private final Model model = new Model();

	public void controllerLogic() {
        String input = view.getInput(); // View로부터 값을 입력받는다
        model.useInput(input); // View에서 입력받은 값을 Model에 전달한다
    }
    
}

Controller는 기본적으로 Model과 View를 연결해주는 다리 역할을 맡는다.
즉, Model과 View가 서로를 몰라도 되도록 Controller가 중간에서 전체 로직을 관리하게 된다.
또한, 도메인 객체들의 조합을 통해 프로그램의 작동 순서나 방식을 제어하는 역할을 한다.
입출력과 관련된 로직은 View가 갖게 하고, 비즈니스 로직은 Model이 갖도록 하자!

View는 I/O 역할에 충실하자

public class OutputView {

	// Domain을 직접 의존하고 있는 잘못된 메서드
	public void printUserStatus(User user) {
    	String output = String.format("User[name = %s, age = %d]", user.getName(), user.getAge());
    	System.out.println(output);
    }
    
    // Domain을 의존하지 않도록 수정한 메서드
    public void printUserStatus(String name, int age) {
    	String output = String.format("User[name = %s, age = %d", name, age);
        
        System.out.println(output);
    }
}

View는 단순히 데이터를 입출력하는 역할만을 해야 한다.
즉, View 내부에서 데이터를 가공하면 안되며, Domain을 직접적으로 의존하는 것도 지양하도록 하자.

객체의 책임은 어디까지?

public class Car {
	
    private static final int CEILING_OF_RANDOM = 10;
    private static final int LOWER_LIMIT_OF_GO_FORWARD = 4;
    
    private static final Random random = new Random();
    
    private String name;
    private int moveDistance = 1;
    
    public Car(String name) {
    	this.name = name;
    }

	// 난수가 일정 이상이 나올 때만 전진한다.
	public void mightGoForward() {
    	if (isGoForwardCapable()) {
        	this.moveDistance++;
        }
    }
    
    private boolean isGoForwardCapable() {
    	return getRandomNumber() >= LOWER_LIMIT_OF_GO_FORWARD;
    }
    
    private int getRandomNumber() {
    	return random.nextInt(CEILING_OF_RANDOM);
    }
    
    // ...
    
}

위 예시 코드의 Car 객체는 자동차를 표현하는 객체이다.
그러나, 자동차를 표현할 뿐 아니라 별개의 책임을 추가로 가지고 있는 부적절한 객체이기도 하다.

Car는 현재 1. 무작위 값을 생성한다, 2. 이동 가능 여부를 판단한다라는 책임 역시 같이 가지고 있다.
위 책임이 "자동차"라는 객체가 가지고 있어야 하는 책임인걸까?

Car 객체는 '자동차 자체'를 표현하는 역할에 집중해야 한다.
자동차가 무작위 값을 생성하고, 그에 따라 이동 가능 여부를 판단하는 것은 어색하다.
그러므로 난수 생성 및 이동 가능 여부 검증은 외부의 클래스에게 맡기고, Car는 이동에 관련된 기능만 가지고 있어야 한다.

가독성을 위해 상수를 사용하자

public class Car {

	// ...

	// 상수를 사용하지 않은 버전
    private int getRandomNumber() {
    	return random.nextInt(10);
    }
	
    // 상수를 사용한 버전
    private static final int CEILING_OF_RANDOM = 10;
    
    private int getRandomNumber() {
    	return random.nextInt(CEILING_OF_RANDOM);
    }
    
}

위에서 살펴본 Car 클래스를 다시 한번 가져와 봤다.
위의 두 getRandomNumber()는 모두 0 ~ 9의 랜덤 int값을 반환하는 역할을 한다.
하지만 당신이 이 코드를 처음 보는 개발자라고 생각하면 메서드를 읽을 때 어떤 느낌을 받을까?
상수를 사용했다면 10이 '랜덤값의 상한선'이라는 의미를 바로 이해할 수 있을테지만, 그렇지 않다면 10이 어떤 의미를 가지고 있는지 추가로 고민해야 할 것이다.

코드를 직접 작성한 개발자 입장에서는 어느 버전이든 이해하기 쉽겠지만, 코드를 작성할 땐 다른 개발자가 읽을 것을 염두에 두고 항상 직관적으로 작성하자!

자가 검증을 활용하자

// 객체 외부에서 검증하는 방식
public class CarService {
	
    public Car getCar(String name) {
    	validateName(name);
        
        return new Car(name);
    }
    
    private void validateName(String name) {
    	if (isIllegalName(name)) {
        	throw new IllegalArgumentException("이름이 부적절합니다");
        }
    }
    
    private boolean isIllegalName(String name) {
    	return name.trim().isEmpty();
    }
    
}
// 객체 스스로가 검증 로직을 지니게 하는 방식
public class Car {

	private String name;
	
    public Car(String name) {
    	validateName(name);
    
    	this.name = name;
    }
    
	private void validateName(String name) {
    	if (isIllegalName(name)) {
        	throw new IllegalArgumentException("이름이 부적절합니다");
        }
    }
    
    private boolean isIllegalName(String name) {
    	return name.trim().isEmpty();
    }

}

위는 Car를 사용하는 외부 클래스에서 Car의 이름에 대한 검증을 수행하는 방식이고, 아래는 Car 자체에서 이름에 대한 검증을 수행하는 방식이다.
각 방법이 장단점이 있으니, 두 방법 모두 인지하고 상황에 맞게 사용하도록 하자!

개인적으로 생각하는 장/단점은 다음과 같다.

외부 클래스에서 검증을 수행하는 방식
  1. 해당 비즈니스 로직에 최적화된 검증을 수행할 수 있다는 장점이 있다.
  2. 단, 한 애플리케이션에서 Car에 대해 통일된 검증을 수행할 것이라는 보장이 사라진다.
    (여러 클래스에서 각기 다른 검증으로 Car를 생성할 경우, 해당 Car들을 사용하는 곳에서 문제가 발생할 수 있을 것이다)
객체 자체가 검증을 수행하는 방식
  1. 본인의 프로퍼티가 유효한지를 검증하는 것이므로, 이 검증 자체가 객체의 책임이라고 볼 수도 있어 자연스럽다.
  2. 전체 애플리케이션이 항상 똑같은 검증을 통해 해당 객체를 사용하게 된다.
    (객체의 생성자가 검증 로직을 수행할 경우, 해당 객체는 모든 인스턴스에 동일한 검증을 수행하게 된다)
  3. 단, 애플리케이션의 특정 로직에서는 별도의 검증이 필요할 경우 문제가 발생할 수 있다.
    (검증을 두 곳에서 수행하니 유지보수가 어려워진다)
  4. 객체가 항상 검증 로직을 수행하므로, 검증 로직에 따라 객체의 유연성이 떨어질 우려가 있다.

랜덤 요소는 테스트가 까다롭다

public class Car {
	
    private static final int CEILING_OF_RANDOM = 10;
    private static final int LOWER_LIMIT_OF_GO_FORWARD = 4;
    
    private static final Random random = new Random();
    
    private String name;
    private int moveDistance = 1;
    
    public Car(String name) {
    	this.name = name;
    }

	// 난수가 일정 이상이 나올 때만 전진한다.
	public void mightGoForward() {
    	if (isGoForwardCapable()) {
        	this.moveDistance++;
        }
    }
    
    private boolean isGoForwardCapable() {
    	return getRandomNumber() >= LOWER_LIMIT_OF_GO_FORWARD;
    }
    
    private int getRandomNumber() {
    	return random.nextInt(CEILING_OF_RANDOM);
    }
    
    // ...
    
}

위에서 이미 살펴본 Car 객체를 또 또 가져왔다!
위의 Car 객체는 내부적으로 난수 값을 받아 moveDistance를 1 증가시키는 로직을 지니고 있다.
이처럼 내부적으로 랜덤 요소를 지니고 있는 객체는 테스트를 작성하기 상당히 어렵다.
(위 코드에서 난수가 4 이상이면 moveDistance가 증가한다는 것을 어떻게 외부에서 테스트할 것인가?)

이를 해결하기 위해선, 내부적으로 난수를 생성해 로직을 수행하는 역할을 Car 외부 클래스가 수행해야 한다.
그럼에도 해당 클래스의 난수 로직 테스트는 불가하겠지만, 최소한 Car에 대한 테스트는 수행할 수 있게 개선될것이다.

사실 이번 과제를 수행하면서, 난수에 의존하는 로직 자체를 지양해야겠다는 생각이 들었다.
비즈니스적으로 필수적이지 않다면 난수 말고 다른 방법을 찾아보도록 하자!
