객체의 정의
1. 객체란 식별 가능한 개체 또는 사물이다.
2. 객체는 자동차처럼 만질 수 있는 구체적인 사물일 수도 있고, 시간처럼 추상적인 개념일 수도 있다.
3. 객체는 구별 가능한 식별자(Identity), 특징적인 행동(Behavior), 변경 가능한 상태(State)를 가진다.
4. 소프트웨어 안에서 객체는 저장된 상태와 실행 가능한 코드를 통해 구현된다

상태

1. 상태는 왜 필요한가?

객체가 주변 환경과의 상호작용에 어떻게 반응하는지는, 그 시점까지 객체에 어떤 일이 발생했느냐에 좌우된다

  • 자판기의 버튼을 눌렀을 때 음료가 나오는지 여부는, 이전에 충분한 금액을 넣어 두었는지에 좌우된다
  • 자동차의 엑셀을 눌렀을 때 앞으로 갈지 여부는, 이전에 자동차의 시동을 켜 두었는지에 좌우된다

하지만 과거에 발생한 행동의 이력을 모두 검사하고 현재 행동의 결과를 판단하기는 매우 복잡하다
따라서, 행동의 결과를 단순하게 기술하기 위해 상태라는 개념이 도입됐다

  • 자판기에서 음료가 나오는지 여부는, 자판기에 투입된 금액의 상태를 보고 알아낼 수 있다
  • 자동차가 앞으로 갈지 여부는, 자동차의 시동 상태를 보고 알아낼 수 있다

2. 프로퍼티 & 프로퍼티 값

객체의 상태를 구성하는 모든 특징을 통틀어서, 객체의 프로퍼티(Property)라고 한다

  • 키, 이름, 성별, 가족은 사람 객체의 프로퍼티이다

일반적으로 프로퍼티는 변경되지 않고 고정되므로, 정적이다
하지만 프로퍼티 값(Property value)은 시간이 흐름에 따라 변경되므로, 동적이다

  • 사람의 키가 얼마인지는 시간에 따라 변한다

3. 링크 vs 속성

링크란?

  • 객체와 객체 사이의 의미 있는 연결을 링크(Link)라고 한다
  • 사람 객체의 가족 프로퍼티는 또 다른 사람 객체를 가리킨다
    즉, 가족이 있는 사람 객체는 또 다른 사람 객체와 링크를 지니고 있다
  • 객체와 객체 사이에는 링크가 존재해야지만 요청을 보내고 받을 수 있다
    즉, 객체는 링크를 통해서만 메시지를 주고받을 수 있다
  • 일반적으로 한 객체가 다른 객체의 식별자를 알고 있는 것으로 링크를 표현한다

속성이란?

  • 다른 객체를 가리키는 링크와 달리, 객체를 구성하는 단순한 값을 속성(Attribute)이라고 한다
  • 키, 이름, 성별은 사람 객체의 속성이다

4. 정리

  1. 상태는 특정 시점에 객체가 가지고 있는 정보의 집합이다
    • 객체의 구조적 특징을 표현한다
  2. 객체의 상태는 객체에 존재하는 정적인 프로퍼티와, 동적인 프로퍼티 값으로 구성된다
    • 객체의 상태를 구성하는 모든 특징을 통틀어서, 객체의 프로퍼티라고 한다
  3. 객체의 프로퍼티는 단순한 값(속성)과, 다른 객체를 참조하는 링크로 구분할 수 있다
    • 프로퍼티의 값이 단순한 값이면 속성이고, 다른 객체라면 링크로 구분한다
    • 객체의 프로퍼티는 (속성 + 링크)의 조합으로 표현할 수 있다

행동

행동이란 외부의 요청 또는 수신된 메시지에 응답하기 위해 동작하고 반응하는 활동이다
행동의 결과로, 객체는 자신의 상태를 변경하거나 다른 객체에게 메시지를 전달할 수 있다
객체는 행동을 통해 다른 객체와의 협력에 참여하므로, 행동은 외부에 가시적이어야 한다

1. 행동은 왜 필요한가?

객체는 자율적인 존재이다
즉, 객체지향 세계에서 객체는 다른 객체의 상태에 접근할 수 없다

그렇기 때문에, 간접적으로 다른 객체의 상태를 변경하거나 조회할 수 있는 방법이 필요하다
이를 위해 행동이라는 개념이 등장한다

객체는 스스로의 행동에 의해서만 상태가 변경되는 것을 보장함으로써, 스스로의 자율성을 유지한다

2. 상태와 행동의 관계

객체의 상태는 저절로 변경되지 않는다
객체의 상태는 오직, 객체의 자발적인 행동에 의해서만 변경된다

객체의 행동이 객체의 상태를 변경시킨다는 것은, 행동이 부수 효과(Side effect)를 초래한다는 것을 의미한다
이 부수 효과의 개념을 이용하면, 객체의 행동을 상태 변경의 관점에서 쉽게 기술할 수 있다

  • 사람이 음료수를 마시면, 사람의 몸무게를 늘리고 음료의 양을 줄이는 부수 효과를 야기한다
  • 사람이 걸어가면, 사람의 위치를 변화시키는 부수 효과를 초래한다

행동은 객체의 상태를 변경시키지만, 행동의 결과는 객체의 상태에 의존적이다

  • 사람이 음료수를 마셔서 몸무게가 얼마가 될지는, 기존의 몸무게 값에 의존한다
  • 사람이 키가 자라서 키가 얼마가 될지는, 기존의 키 값에 의존한다

따라서 상태와 행동 사이에는 다음과 같은 관계가 존재한다고 볼 수 있다

  1. 객체의 행동은 상태에 영향을 받는다(의존한다)
  2. 객체의 행동은 상태를 변경시킨다

즉, 상태라는 개념을 이용하면 행동을 다음 두 가지 관점에서 서술할 수 있다는 것을 의미한다

  1. 상호작용이 현재의 상태에 어떤 방식으로 의존하는가
  2. 상호작용이 어떻게 현재의 상태를 변경시키는가

그렇다면, 엘리스가 40cm의 문을 통과하는 행동은 아래와 같이 서술할 수 있다

  • 엘리스의 키가 40cm 이하라면 문을 통과할 수 있다
  • 문을 통과한 후에 엘리스의 위치는 아름다운 정원으로 바뀌어야 한다

3. 협력과 행동

객체는 자신의 책임을 완수하기 위해 다른 객체와 적극적으로 상호작용한다
이 때, 객체가 다른 객체와 협력하는 유일한 방법은 ‘다른 객체에게 요청을 보내는 것’이다

객체는 다른 객체와 메시지를 통해서 소통하고, 메시지에 따라 적절히 행동하며 자신의 상태를 변경한다
이 때, 자신의 상태 뿐 아니라 다른 객체의 상태 변경도 유발할 수 있다

  • 사람이 음료수를 마시면, 자신의 몸무게가 늘어나는 동시에 음료의 양이 줄어든다

정리하자면, 객체의 행동으로 인해 발생하는 결과는 두 가지 관점에서 설명할 수 있다
(객체의 행동은 이 두 가지 관점의 부수효과를 명확하게 서술해야 한다)

  1. 객체 자신의 상태 변경
  2. 행동 내에서 협력하는 다른 객체에 대한 메시지 전송

4. 상태 캡슐화

객체의 상태를 행동 집합 뒤로 캡슐화하는 것은, 객체의 자율성을 높이고 협력을 단순하고 유연하게 만든다
상태를 외부로 노출시키지 않은 객체는 스스로 판단하고 결정하는 자율적인 객체가 되기 때문이다

현실 세계의 객체는 능동적인 객체(사람)와 수동적인 객체(음료수)가 존재한다
하지만, 객체지향의 세계에서는 모든 객체가 자신의 상태를 스스로 관리하는 자율적인 존재가 된다

만약 현실이라면 음료를 마셔 음료의 상태(수량)를 변경시키는 주체는 사람이 될 것이다
하지만, 객체지향 세계에서는 음료 스스로가 본인의 상태(수량)를 변경시킨다
(사람은 음료에게, 본인이 음료를 마셨다는 메시지를 전달할 뿐이다)

  • 사람이 음료를 마시는 행동은 스스로의 몸무게(상태)를 변화시킨다
    이 과정에서, 본인이 마신 만큼 수량을 줄여달라는 메시지를 음료수에게 전달한다
  • 하지만 실제로 음료의 수량(상태)를 어떻게 얼마나 변경할지는, 메시지를 수신한 음료가 결정한다
    심지어는, 수량을 아예 줄이지 않을 수도 있다
    (사람은 음료의 양이 줄어들 것이라 믿고 메시지를 전달할 뿐이다)

즉, 메시지를 보내는 객체는, 메시지 송신 객체의 상태 변경에 대해서 전혀 알지 못한다
이것이 바로 상태 캡슐화다

  • 객체는 상태를 캡슐 안에 감춰두고, 외부로 노출하지 않는다
  • 객체가 외부에 노출하는 것은 오직 행동뿐이고, 외부에서 객체에 접근하는 방법 역시 오직 행동뿐이다

객체의 행동을 유발하는 것 자체는, 외부로부터 전달된 메시지이다
하지만, 객체의 상태를 변경할지 여부는 객체 스스로가 결정하는 것이다

  • 심지어 메시지를 전달하는 객체는, 송신 객체의 상태가 변경된다는 사실조차 알지 못한다

식별자(Object와 Value의 차이)

모든 객체(Object)는 식별자를 가진다
반대로, 객체가 아닌 단순한 값(Value)은 식별자를 가지지 않는다

이 점이, 객체(Object)와 단순한 값(Value)을 구분하는 가장 큰 차이이다

1. 식별자란?

객체란 식별 가능한 경계를 지닌 모든 사물을 의미한다

객체가 식별 가능하다는 것은, 모든 객체에 객체를 서로 구별할 수 있는 특정한 프로퍼티가 존재한다는 의미이다

이 프로퍼티를 식별자(Identifier)라고 한다

2. 값: 상태와 동등성

값(Value)은 숫자, 문자열 등과 같이 변하지 않는 양을 모델링한다
흔히 값의 상태는 변하지 않으므로, 불변 상태(Immutable state)를 가진다고 표현한다

값은 식별자 대신 상태를 통해 같은지 다른지 식별한다

  • 우리는 값이 1인 숫자(값)가 여러 개 있으면, 해당 숫자들이 동일하다고 판단한다
    즉, 값의 상태를 보고 인스턴스가 동일한지 판단한다

이처럼 상태를 이용해 두 값이 같은지 판단할 수 있는 성질을 동등성(Equality)이라고 한다

  • 값은 상태가 변하지 않기 떄문에, 상태를 이용해 동등성을 판단할 수 있다
    (한 시점에 동등하다고 판단하면, 값이 변하지 않으니 이후로도 쭉 같다고 판단할 수 있다)

3. 객체: 식별자와 동일성

객체(Object)는 시간에 따라 변경되는 상태를 포함하며, 행동을 통해 상태를 변경한다
그러므로, 객체는 가변 상태(Mutable state)를 가진다고 표현한다

객체의 같고 다름은 오직 식별자(Identifer)로 판단한다
모든 상태 값이 같은 여러 객체가 있더라도, 두 객체는 별개의 객체라고 판단한다

  • 이름이 Kim이고 키가 180인 사람이 두 명 있다 하더라도, 우리는 그 두 사람을 서로 다른 사람으로 판단한다
  • 반대로 객체의 상태가 다르더라도, 식별자 값이 같으면 두 객체를 동일하다 판단한다
    (어린 시절의 나와 지금의 나는 키가 다르지만, 그럼에도 동일한 사람이다)

이처럼 식별자를 기반으로 객체의 같고 다름을 판단할 수 있는 성질을 동일성(Identical)이라고 한다
객체는 상태가 변하기 때문에, 상태를 기반으로 같고 다름을 판단할 수 없다
(한 시점에 동등하더라도, 시간이 지나면 서로 다른 상태를 가질 수 있기 때문이다)

4. 객체지향 언어의 값과 객체

객체지향 프로그래밍 언어에서는 값과 객체가 모두 클래스(Class) 개념으로 구현되기 때문에, 문맥에 따라 그 의미가 혼란스러워진다

  • 정수: Integer라는 클래스로부터 생성된 객체
  • 사람: Person이라는 클래스로부터 생성된 객체

이런 오해를 줄이기 위해, 객체와 값을 지칭하는 별도의 용어를 사용하기도 한다

  1. 참조 객체(Reference obejct), 엔티티(Entity)
    • 식별자를 지닌 전통적인 객체를 가리키는 용어다
  2. 값 객체(Value object)
    • 식별자를 가지지 않는 값을 가리키는 용어다

행동이 상태를 결정한다

1. 상태를 중심으로 설계할 경우의 문제점

  1. 캡슐화 저해
    • 상태에 초첨을 맞출 경우, 객체의 상태가 공용 인터페이스에 그대로 노출되기 쉽다
  2. 객체의 고립
    • 상태를 먼저 고려할 경우, 협력이라는 문맥에서 벗어난 채 객체를 설계하게 된다
    • 자연스럽게, 협력에 적합하지 못한 객체가 만들어진다
  3. 재사용성의 저하
    • 다양한 협력에 참여할 수 있는 능력이 곧 재사용성이다
    • 협력에 적합하지 못한 객체는 당연히 재사용성도 저하된다

2. 행동에 초점을 맞추자

객체는 다른 객체와 협력하기 위해 존재하고, 객체가 협력에 참여하는 유일한 방법은 행동이다
따라서, 우리는 협력의 문맥에 맞는 행동을 수행하는 객체를 만들어내야 한다

객체지향 설계는 다음과 같은 순서로 이루어져야 한다
(이를 책임-주도 설계(Responsibility-Driven Design, RDD)라 부른다)

  1. 애플리케이션에 필요한 협력을 생각한다
  2. 협력에 참여하는데 필요한 행동을 생각한다
  3. 행동을 수행할 객체를 선택한다
  4. 행동에 필요한 정보가 무엇인지 고려한다
    (즉, 객체에 필요한 상태가 무엇인지를 결정한다)

객체지향은 ‘현실 세계의 모방’이 아니다

소프트웨어 안에 구축되는 객체지향 세계는 현실을 그대로 모방하지 않는다
현실의 모습을 참조할 뿐, 궁극적으로는 현실과 전혀 다른 세계를 새롭게 창조하게 된다

1. 의인화

현실 속의 객체와 소프트웨어 객체 사이의 가장 큰 차이점은 ‘능동성’이다
현실 속에서는 수동적인 존재가, 소프트웨어 객체로 구현될 때는 능동적으로 변한다

  • 현실 세계의 음료 객체는 사람에 의해 마셔지고 양이 줄어들지만, 소프트웨어 세계의 음료 객체는 본인의 상태(양)를 스스로 관리한다

이와 같이, 소프트웨어 객체가 현실의 객체보다 더 많은 일을 할 수 있는 특징을 의인화(Anthropomorphism)라고 부른다

2. 은유

소프트웨어 객체와 현실 세계의 객체는 다르지만, 그렇다고 전혀 상관없는 것은 아니다
현실 세계와 객체지향 세계 사이의 관계는 은유(Metaphor)에 가깝다

현실 속의 전화기는 스스로 전화를 걸 수 없고, 소프트웨어 세계의 전화기는 스스로 전화를 걸 수 있다
이런 차이점에도, 소프트웨어 객체 이름을 ‘전화기’로 짓는 것 만으로 우리는 해당 객체가 전화를 걸 수 있다는 사실을 쉽게 이해할 수 있다

이는 은유가 객체의 표현적 차이(Representational gap)을 줄여 주기 때문이다

  • 은유 관계에 있는 실제 객체의 이름을 소프트웨어 객체의 이름으로 사용하면, 표현적 차이를 줄여 소프트웨어의 구조를 쉽게 예측할 수 있다

따라서, 은유를 적절히 사용하면 표현적 차이를 줄임으로써 이해하기 쉽고 유지보수가 용이한 소프트웨어를 만들 수 있다
