개요

레벨 1의 두 번째 코딩 미션인 '장기'를 완료했다.
블랙잭 때와 달리, 미션 일정인 2주 내에 완료하지 못하고 3주를 소모해 겨우 완료했다...

그래도 순수 JDBC로 데이터베이스와 연동해보게 되어 재밌었고, 생각보다 JPA 없이 구현하는 것이 괜찮다고 느껴졌다.
실제로 실무에 일하고 있는 리뷰어 중 한 분도 JPA보다 JdbcTemplate을 선호한다고 하니, "ORM이 반드시 좋은 기술인가?"도 비판적으로 생각해봐야겠다.

코딩 내적인 깨달음

코드의 순서가 자연스러운지 고려해라

/**
 * 해당 과일이 할인 중인지 찾는다
 */
boolean isOnSale(Fruit fruit) {
	// 과일을 찾는다
	boolean isOnSale = salesFruits.contains(fruit);
            
    // 판매가 가능한지 검증한다
    if (fruit.cannotSell()) {
    	throw new IllegalStateException("판매할 수 없는 과일입니다.");
    }
    
    return isOnSale;
}

과일이 할인 중인지 찾는 기능이 있다고 가정해보자.
위처럼 작성해도 충분히 동작하는 코드이지만, 개선할 수 없을까?

/**
 * 해당 과일이 할인 중인지 찾는다
 */
boolean isOnSale(Fruit fruit) {
    // 판매가 가능한지 검증한다
    if (fruit.cannotSell()) {
    	throw new IllegalStateException("판매할 수 없는 과일입니다.");
    }
    
	// 과일을 찾는다
	boolean isOnSale = salesFruits.contains(fruit);
    
    return isOnSale;
}

우리는 이 기능을 생각할 때, 판매 가능한지 검증하고, 판매 가능한지 찾는다라는 흐름으로 생각한다.
사소한 개선이지만, 생각의 흐름에 맞게 코드를 배치하는 것은 가독성에 큰 영향을 준다.

instanceof를 지양하고, 역할을 부여해라

/*
 * 특별한 과일(딸기, 망고)을 반환한다.
 */
public List<Fruit> findSpecialFruit() {
	return fruits.stream()
    		.filter(fruit -> fruit instanceof Strawberry || fruit instanceof Mango)
            .toList();
}

요구사항에서 특별한 과일을 딸기와 망고로 정의했다면, 위와 같이 구현할 수 있겠다.

요구사항에서 SweetFruit이라는 규칙이 바뀌면, Strawberry와 Mango를 수정하는게 아니라 findSweetFruits를 수정해야 할 것이다.

instanceof를 꼭 사용해야 하는 걸까?

/*
 * 특별한 과일을 반환한다.
 */
public List<Fruit> findSpecialFruit() {
	return fruits.stream()
    		.filter(Fruit::isSpecial)
            .toList();
}

// ...

public class Strawberry extends Fruit {
	@Override
	public boolean isSpecial() {
    	return true;
    }
}

public class Mango extends Fruit {
	@Override
	public boolean isSpecial() {
    	return true;
    }
}

instanceof를 사용하는 대신, 객체 스스로가 자신의 역할을 알려주는 방식을 사용해보자.
특별한 과일이라는 역할을 Fruit 객체로 위임하면, findSpecialFruit가 구체 타입에 의존하지 않도록 개선할 수 있다.

예외의 메시지도 테스트해라

public class Fruit {
	private final String name;
    
    public Fruit(String name) {
    	if (name.equals("")) {
        	throw new IllegalArgumentException("과일 이름은 비어있을 수 없습니다.");
        }
        if (name.equals("Fruit")) {
        	throw new IllegalArgumentException("과일 이름은 'Fruit'일 수 없습니다.");
        }
        
        this.name = name;
    }
}

과일 객체는 이름이 비어 있거나 "Fruit"면 예외를 던져야 한다.
이를 테스트해보자.

@Test
void 이름이_비어_있으면_예외를_던진다() {
	assertThatThrownBy(() -> new Fruit(""))
    	.isInstanceOf(IllegalArgumentException.class);
}

@Test
void 이름이_Fruit면_예외를_던진다() {
	assertThatThrownBy(() -> new Fruit(""))
    	.isInstanceOf(IllegalArgumentException.class);
}

테스트를 잘 짰다~
모두 통과할 것이다.

라고 생각하면 안된다!
이름이_Fruit면_예외를_던진다는 개발자의 실수로 "Fruit" 대신 ""을 전달하고 있다.
하지만 이름이 비어도 IllegalArgumentException가 발생할 것이니 테스트는 통과해버린다.

이를 거짓 음성이라고 한다.

@Test
void 이름이_비어_있으면_예외를_던진다() {
	assertThatThrownBy(() -> new Fruit(""))
    	.isInstanceOf(IllegalArgumentException.class)
        .hasMessage("과일 이름은 비어있을 수 없습니다.");
}

@Test
void 이름이_Fruit면_예외를_던진다() {
	// 이 테스트는 실패할 것이다
	assertThatThrownBy(() -> new Fruit(""))
    	.isInstanceOf(IllegalArgumentException.class)
        .hasMessage("과일 이름은 'Fruit'일 수 없습니다.");
}

이렇게 메시지까지 검증하는 것으로, 사람의 실수를 방지하고 더 견고한 테스트 코드를 작성하도록 하자.
겸사겸사, 정말 내가 의도한 케이스로 예외가 발생했는지도 검증할 수 있어진다.

테스트 역시 instanceof를 지양하라

@Test
void 반대_방향을_반환한다() {
	// given
	Direction up = new Up();
    
    // when
    Direction reverse = up.reverse();
    
    // then
    assertThat(reverse).isInstanceOf(Down.class);
}

방향을 Direction이라는 인터페이스로 추상화하고, 구현체로 Up, Down을 만들었다.
서로 반대 방향을 반환해야 했는데, 어쩔 수 없이 instanceof를 사용해 테스트 해야 하는걸까?

@Test
void 반대_방향으로_이동시키는_Direction을_반환한다() {
	//given
    Direction up = new Up();
    
    Point originPoint = new Point(5, 5);
    Point upPoint = up.move(originPoint);
    
    // when
    Direction reverse = up.reverse();
    Point reversedPoint = reverse.move(upPoint);
    
    // then
    assertThat(reversedPoint).isEqualTo(originPoint);
}

Direction은 좌표를 움직이는 역할을 하는데, up이 움직인 좌표를 reverse가 다시 움직이면 원래 좌표로 돌아오는 것을 테스트하도록 수정했다.

테스트가 다소 길어졌지만, instanceof 없이도 기능을 검증할 수 있도록 개선할 수 있었다.

최소한의 케이스로 최대 범위를 단언해라

@ParameterizedTest
@ValueSource(ints = {-1, -10, -100, Integer.MIN_VALUE})
void 값이_음수라면_예외를_던진다(int negativeValue) {
	assertThatThrownBy(() -> new Money(negativeValue))
    	.isInstanceOf(IllegalArgumentException.class)
        .hasMessage("금액은 0 이상이어야 합니다");
}

'금액'을 표현할 Money 객체를 만들고, 이에 대한 테스트 코드를 작성했다.
값이 음수라면 예외를 던지는 것을 테스트하기 위해, 위와 같이 -1, -10, -100, Integer.MIN_VALUE 경우를 테스트하도록 작성했다.

@Test
void 값이_음수라면_예외를_던진다() {
	assertThatThrownBy(() -> new Money(-1))
    	.isInstanceOf(IllegalArgumentException.class)
        .hasMessage("금액은 0 이상이어야 합니다");
}

하지만 이 모든 경우를 테스트할 필요가 있을까?
합리적인 추론이 가능하다면, 최소한의 테스트 케이스만으로 최대한의 범위를 단언하는 것이 바람직할 수 있다.

항상 그런 것은 아니니, @ParameterizedTest로 테스트할 때와 경곗값만 테스트할 때의 장단점을 비교해보고, 상황에 맞는 방법을 선택하도록 하자.

상수화가 정말 필요한지 고민해봐라

@Test
void 값이_음수라면_예외를_던진다() {
	assertThatThrownBy(() -> new Money(-1))
    	.isInstanceOf(IllegalArgumentException.class)

바로 위에서 본 이 테스트에서, 예외 메시지 부분을 상수화해보자.

private static final String NEGATIVE_VALUE_MESSAGE = "금액은 0 이상이어야 합니다";

// ...

@Test

정말 보기 편해졌는가?
동일한 예외 메시지가 여러 곳에서 사용된다거나, 메시지가 너무 길다거나 하면 상수화가 필요할 수 있다.

상수화는 필수가 아니다.
상수화를 했을 때 더 보기 편해지는지, 혹은 유지보수가 쉬워지는지 고려한 후 도입하자.

사용하지 않아도 되는 Getter는 뭘까?

(물론 불가능은 없다)

Tell Don't Ask로 쉽게 대체할 수 있다.
만일 Getter를 사용하고 있다면, "Tell Don't Ask로 대체할 수 없는가?"를 가장 먼저 고려해보자.

Tell Don't Ask로 대체할 수 있다면, 대부분 불필요한 Getter라고 볼 수 있다.

코드를 응집도 있게 배치하라

위 코드는 잘 동작한다.
하지만 개선할 순 없을까?

players는 return new Game(gameTitle, players)에서 사용하기 위한 변수인데, 쓸데없이 메서드 첫 줄에서 선언되고 있었다.
코드의 응집도가 나쁘단 느낌이 든다면, 변수가 실제로 필요할 때 선언되고 있는지 검토해보도록 하자.

try (PreparedStatement statement = connection.prepareStatement(updateIntersection)) {
	Intersection to = move.to();
	Intersection from = move.from();

	statement.setInt(1, to.getRow());
	statement.setInt(2, to.getFile());
	statement.setInt(3, gameId);
	statement.setInt(4, from.getRow());
	statement.setInt(5, from.getFile());

	statement.executeUpdate();
}

물론, 코드의 맥락을 위해, 사용될 곳과 먼 곳에서 선언하는 경우도 있을 수 있다.

위 예시는 장기 미션에서 사용한 실제 코드인데, 값을 꺼내오는 부분(move.to, move.from)과 PreparedStatement에 값을 입력하는 부분을 나눠놓기 위해, from이 실제 사용되는 곳과 선언되는 곳을 떨어트려 놓았다.

RuntimeException은 아무 맥락도 제공하지 않는다.

public class Fruits {
    private final List<Fruit> fruits;
    
    public Fruits(List<Fruit> fruits) {
    	if (fruits.isEmpty()) {
        	throw new IllegalArgumentException("과일이 필요합니다.");
        }
        
        this.fruits = List.copyOf(fruits);
    }
    
    public Fruit findAnyFruit() {
    	return fruits.stream()
        		.findAny()
                // 논리적으로 발생할 수 없는 예외
                .orElseThrow(() -> new RuntimeException("과일을 찾을 수 없습니다."));
	}
}

Fruits는 필드로 지닌 fruits가 비어 있지 않음을 보장한다.
따라서, findAnyFruit()의 orElseThrow 절은 논리적으로 실행되지 않을 예외이다.

저 예외가 던져졌다는 것은 논리 어딘가에 결함이 있다는 뜻이니, 웹 서비스로 치면 4XX 대신 5XX 상태코드를 던져야 할 것이다.

발생할 일 없는 예외이니 RuntimeException을 던지는 것으로 충분할까?

    public Fruit findAnyFruit() {
    	return fruits.stream()
        		.findAny()
                // 논리적으로 발생할 수 없는 예외
                .orElseThrow(() -> new UnexpectedException("과일을 찾을 수 없습니다."));
	}

해당 코드를 처음 읽는 개발자 입장에서 생각해보자.
예외의 타입이 RuntimeException인 이유를 추론할 수 없다.
RuntimeException은 아무 맥락도 제공하지 않기 때문이다.

UnexpectedException처럼, 논리적으로 발생할 수 없는 예외임을 명시해주도록 하자.
(참고로 Java가 제공하는 UnexpectedException은 체크 예외이므로, 직접 언체크 예외인 UnexpectedException을 구현하는 것이 나을 것이다)

UnexpectedException이라는 이름이 정답인 것은 아니다.
다른 개발자 입장에서 맥락을 한 눈에 파악할 수 있는 바람직한 이름을 고민해보자.

불변 객체의 상태는 항상 온전할 수 있다

public class Fruits {
	private OnSaleFruits onSaleFruits;
    private Fruit lastFruit;
    private FruitsState state;
    
    // ... 생성자 생략 ...
    
    public void addFruit(Fruit fruit) {
    	lastFruit = fruit;
        state = state.nextState(fruit);
        onSaleFruits = onSaleFruits.addNewFruit(fruit);
    }
}

모든 상태가 가변인 Fruits가 있다.
과일을 하나 더하는 addFruit 메서드를 구성했는데, 잘 동작할 것 같다.

정말 문제가 없을까?

    public void addFruit(Fruit fruit) {
    	lastFruit = fruit;
        state = state.nextState(fruit); // 여기서 예외가 터지면?
        onSaleFruits = onSaleFruits.addNewFruit(fruit);
    }

state.nextState를 호출하는 과정에서 예외가 발생했다면 어떻게 될까?
lastAddedFruit 상태는 변경되었지만, onSaleFruits 상태는 변경되지 않을 것이다.
가변 객체는, 이와 같이 상태의 무결성이 무너질 위험이 존재한다.

예외가 발생하면 그대로 애플리케이션을 종료할 것이라면 괜찮지만, 외부에서 예외를 잡고 Fruits 인스턴스를 계속 사용한다면 큰 문제로 이어질 수 있다.

어떻게 해결하면 좋을까?

public class Fruits {
	private final OnSaleFruits onSaleFruits;
    private final Fruit lastFruit;
    private final FruitsState state;
    
    // ... 생성자 생략 ...
    
    public Fruits addFruit(Fruit fruit) {
    	Fruit nextLastFruit = fruit;
        FruitsState nextState = state.nextState(fruit);
        OnSaleFruits nextOnSaleFruits = onSaleFruits.addNewFruit(fruit);
        
        return new Fruits(
        		nextOnSaleFruits,
        		nextLastFruit,
                nextState
        );
    }
}

Fruits를 불변 객체로 만들면 이 문제를 해결할 수 있다.
마치 데이터베이스의 트랜잭션에서 문제가 생기면 모두 롤백하고 문제가 없으면 모두 커밋하듯이, 모든 상태가 원자적으로 변경된다.

또한, 생성자에서만 상태를 검증해도 모든 경우의 수를 안전하게 검증할 수 있으니, 검증 로직을 간결하게 구성할 수 있고, 이는 유지보수에 큰 도움을 준다.

코딩 외적인 깨달음

리뷰어에게 컨텍스트를 제공해라

리뷰어는 내가 구현한 클래스의 역할이 뭔지 모르는 상태로 시작한다.
또한, 내가 사용한 도메인 용어(ex_ 장기의 '진'을 Wing으로 표현함)가 무엇을 뜻하는지도 모르는 상태로 시작한다.
(물론, 실무에서의 리뷰어는 도메인 용어를 알고 있을 것이다)

이런 상황에서 '내가 궁금한 것'만 던져놓고 리뷰를 바라는 것은 무례한 행동이 될 수 있다.
내 코드를 처음 보는 리뷰어의 입장이 되어, 어떤 정보가 필요할지 고민해보자.

해보고 나서 질문해라

리뷰어가 어떤 방향을 제시해줬을 때, 당장 이해가 가지 않더라도, 우선 구현해보고 도전해보는 것 자체에 의의가 있다.
그 과정에서 내가 예상했던 이점과 불편함이 실제로 그러하였는지, 혹은 예상과 달랐는지를 학습할 수 있기 때문이다.

이런 관점에서, 어떤 피드백을 받았다면 이것을 실제로 도입해본 후, 마음에 들지 않는다면 '어째서 단점이 더 큰지'를 정리해보자.
이를 가지고 리뷰어를 설득하는 것이 더 효과적인 대화법일 수 있다.

마치며

이번 미션 역시 많은 어려움을 겪었고, 이를 이겨내며 많이 성장했다.
특히, 리뷰어와 어떻게 소통하는게 좋을지 고민해보며, 코드 외적으로도 성장한 것이 만족스럽다.

배우면 배울수록 부족한 부분이 더 많이 보인다.
덕분에 겸손해질 수 있고, 다른 사람의 피드백을 쉽게 수용하게 바뀌어 가는 것 같다.
