의도는 “메시징”이다. 훌륭하고 성장 가능한 시스템을 만들기 위한 핵심은 모듈 내부의 속성과 행동이 어떤가보다는 모듈이 어떻게 커뮤니케이션하는가에 달려있다.
- 앨런 케이

책임과 추상화

당신은 바리스타에게 커피를 만들어달라고 요청하고 싶다
어떻게 요청하면 좋을까?

1. 너무 구체적인 책임

다음처럼 구체적으로 명령하면 어떻게 될까?

  1. 커피콩을 갈아라
  2. 에스프레소 머신으로 커피를 내려라
  3. 커피를 제공해라

결과적으로 바리스타가 “커피를 만들어라”라는 책임을 수행하긴 하지만, 어떻게 수행할지를 명확하게 명령했다
→ 바리스타가 “책임을 어떻게 수행할지 결정할 자유”를 침해당하게 된다

어떤 바리스타는 캡슐 머신으로 커피를 만들고 싶을 수도 있고, 이미 갈려있는 커피콩을 사용하고 싶을 수도 있다
하지만 우리는 “커피콩을 갈고, 에스프레소 머신으로 커피를 내려라”라고 명령하고 있기 때문에, 바리스타가 지니고 있던 선택의 자유를 훼손하게 된다

이는 바리스타가 자율적으로 책임을 수행할 수 없게 만든다
즉, 객체의 자율성이 훼손된다

2. 너무 추상적인 책임

다음처럼 추상적으로 명령하면 어떻게 될까?

  1. 만들어라

이 책임은 너무 모호하기 때문에, 바리스타 입장에서는 무엇을 만들라는지 알 수가 없다
즉, 해당 객체가 협력에 참여하는 의도를 설명하지 못한다

3. 적절한 책임이란?

추상적이고 포괄적인 책임은 협력을 유연하게 해 재사용성을 증진시킨다
하지만, 과하게 추상적일 경우, 해당 객체가 협력에 참여하는 의도를 명확하게 설명하지 못하게 된다

즉, 적절한 책임이란, 협력에 참여하는 의도가 명확하면서 객체의 자율성을 보장하는 정도의 추상화여야 한다
어떤 책임이 가장 적절한지는 문맥에 따라 달라지기 때문에, 현재의 문맥을 고려해 적절한 책임을 선택하는 안목을 기르도록 하자

4. ‘어떻게(How)’가 아니라 ‘무엇(What)’을

자율적인 책임은 객체가 어떻게(How) 해야 하는지를 설명하는 대신, 무엇을(What) 해야 하는지 설명한다

‘커피를 만든다’라는 책임은 바리스타가 협력을 위해 무엇(What)을 할지는 명확히 결정하는 동시에, 어떻게(How) 해야 하는지는 간섭하지 않는다

메시지와 메서드

메시지는 객체들이 서로 협력하기 위해 사용할 수 있는 유일한 의사소통 수단이다
메서드는 객체가 메시지를 처리하기 위해 선택할 수 있는 ‘방법’이다

1. 메시지 전송의 구성요소

메시지는 ‘메시지 이름’과 ‘인자’로 구성된다

  1. 메시지 이름
    • ‘커피를 만들어라’라는 부분이 메시지 이름이 된다
  2. 인자(Argument)
    • 메시지를 전송할 때 추가적인 정보가 필요할 경우 사용한다
    • 예를 들면, ‘커피의 종류’, ‘커피의 개수’ 등이 있을 수 있다

메시지 전송은 ‘수신자’와 ‘메시지’로 구성된다
즉, ‘수신자’와 ‘메시지 이름’과 ‘인자’로 구성된다

  • 이전 예시에서는 ‘바리스타’가 수신자가 된다

메시지 전송을 Java 식으로 표현하면 다음과 같다

  • 수신자.메시지이름(인자, 인자, ...)
    ex) barista.makeCoffee(type, amount)

2. 메시지와 메서드의 관계

메서드는 메시지를 처리하기 위해 내부적으로 선택하는 ‘방법’이다
즉, 어떻게(How) 메시지를 처리할지 결정하는 것이 메서드이다

  • ‘커피를 만들어라’라는 메시지를 처리하기 위한 ‘에스프레소 머신을 사용한다’라는 방법이 바로 메서드이다

어떤 객체에게 메서지를 전달하면, 해당 메시지에 대응되는 특정 메서드가 실행된다
즉, 메시지는 무엇(What)을 처리할지만을 나타내고, 메서드는 어떻게(How) 수행할 것인지를 명시한다

이전에 말했듯, 메시지를 어떻게 처리할지는 다른 객체가 몰라야 한다
즉, 메서드는 객체 내부에 존재하고, 외부에 공개되지 않는다

3. 메서드와 다형성

메시지와 메서드의 관계를 이해하고 나면, 다형성도 쉽게 이해할 수 있다
서로 다른 객체가 동일한 메시지를 서로 다른 메서드로 처리하는 메커니즘이 바로 다형성이다

우리는 다형성 덕분에 객체의 대체 가능성을 얻을 수 있고, 이를 통해 협력의 유연성을 얻을 수 있어 재사용성이 높은 협력을 설계할 수 있다

4. 송신자와 수신자를 약하게 연결하라

우리는 ‘커피를 만들어라’라는 메시지만 전달할 수 있다면, 수신자의 구체적인 타입에 대해 몰라도 괜찮다
즉, 송신자는 수신자가 메시지를 이해할 수 있다는 사실만 알고 있는 상태에서 협력에 참여한다

송신자가 수신자에 대해 최소한의 정보만 알고 있어도 협력이 가능하다는 것은, 다음과 같은 장점을 누리게 해준다

  1. 협력이 유연해진다

    • 송신자에게는 ‘메시지를 이해하는 수신자’만 필요할 뿐이다
      때문에, 수신자가 다른 타입의 객체로 대체되더라도 송신자는 알지 못하게 된다
    • 즉, 송신자에 대한 파급효과 없이 유연하게 협력을 변경할 수 있다

  2. 협력이 수행되는 방식을 확장할 수 있다

    • 송신자에게 영향을 미치지 않고 수신자를 교체할 수 있으므로, 협력의 세부적인 수행 방식을 쉽게 수정할 수 있다
    • 협력을 확장하고 싶다면, 새로운 유형의 객체를 협력에 끼워 맞추는 방식으로 간단하게 확장할 수 있다

  3. 협력이 수행되는 방식을 재사용할 수 있다

    • 협력에 영향을 미치지 않으면서도 다양한 객체를 교체할 수 있다
      이것은, 다양한 문맥에서 협력을 재사용할 수 있다는 의미이다
    • 당신이 바리스타에게 커피를 요청하는 상황에서도, 친구에게 커피를 요청하는 상황에서도 모두 이 협력을 재사용할 수 있다
    • 이 장점은 다형성으로부터 온다
      또한, 다형성이 가능한 이유는 송신자와 수신자가 오직 메시지라는 얇은 연결고리로만 이어져 있기 때문이라는 것을 기억하자

메시지와 책임 주도 설계

1. 책임 주도 설계 속 메시지의 역할

다음과 같은 흐름을 통해, 결과적으로 메시지가 수신자의 책임을 결정한다

  1. 본인의 책임을 완수하기 위해 다른 객체의 도움이 필요한 객체가 발견된다
  2. 해당 객체가 도움을 요청하기 위해 어떤 메시지가 필요한지 결정한다
  3. 메시지를 결정한 후, 해당 메시지를 수신하기 적합한 객체를 선택한다

위에서 메시지를 수신하기로 한 객체는, 송신자가 메시지를 보내며 기대하는 바를 충족시켜야 한다
즉, 수신자는 송신자가 기대한 대로 메시지를 처리할 책임을 갖게 된다

2. What/Who 사이클

책임 주도 설계는, 어떤 행위가 필요한지를 먼저 결정한 후 해당 행위를 수행할 객체를 결정한다
즉, “어떤 행위(What)를 수행할지”를 결정한 후에 “누가(Who) 그 행위를 수행할 것인지”를 결정한다

이 사이클을 What/Who 사이클이라고 부르며, 여기서의 어떤 행위(What)가 바로 메시지이다

이렇게 객체에 수신 가능한 메시지들이 쌓이고, 그것이 객체의 인터페이스를 구성한다
즉, 객체의 인터페이스는 메시지를 통해 발견된다

3. 묻지 말고 시켜라

우리는 위에서 “메시지를 먼저 결정하고 객체가 메시지를 따르게 하는” 설계 방식을 사용해야 함을 알게 되었다

이렇게 만들어진 인터페이스는 묻지 말고 시켜라(Tell, Don’t Ask) 스타일을 지니게 된다
(이 스타일을 디미터의 법칙(Law of Demeter)이라고도 한다)

우리는 메시지를 먼저 결정한 후 메시지에 적합한 객체를 선택하기 때문에, 송신자는 수신자가 어떤 객체인지 모르게 된다
즉, 송신자는 수신자의 내부 상태를 모르게 되고, 이는 송신자와 수신자 사이의 결합을 느슨하게 만들어준다

‘묻는다’라는 것은, 다른 객체의 상태를 물어보는 것을 의미한다
다른 객체의 상태를 묻는다는 것은, 송신자가 수신자의 상태에 관심을 가진다는 뜻이다

객체가 다른 객체의 상태를 궁금해하지 않아도 되도록, 송신자는 단지 필요한 메시지를 전송하기만 하라
메시지의 처리 방법은 수신자가 스스로 결정해야 한다

결과적으로 ‘묻지 말고 시켜라’ 스타일은 객체를 자율적으로 만들고 캡슐화를 보장하므로, 결합도를 낮게 유지시켜 설계를 유연하게 한다

객체 인터페이스

1. 인터페이스의 특성

  1. 인터페이스의 사용법만 익히면, 내부 구현을 몰라도 사용할 수 있다

    • 우리는 스마트폰 앱의 내부 구현법을 몰라도 앱을 사용하고 있다

  2. 내부 구현을 변경하더라도 인터페이스를 변경하지 않았다면, 사용자에게 아무 영향도 미치지 않는다

    • 우리는 스마트폰 앱의 내부 구현이 변경되더라도 동일하게 사용할 수 있다

  3. 대상이 변경되더라도 동일한 인터페이스를 제공한다면, 문제 없이 상호작용할 수 있다

    • 다른 앱을 사용하더라도 사용법은 똑같다

2. 인터페이스의 분류

앞에서는 모든 인터페이스가 외부에 열려 있는 것 처럼 설명했지만, 실제 인터페이스는 다음과 같이 나뉜다

  1. 외부에서 접근 가능한 인터페이스(구분을 위해 공용 인터페이스라고 부른다)

  2. 내부에서만 접근 가능한 감춰진 인터페이스

객체지향에서는 모든 요청이 메시지를 통해 이루어지기 때문에, 자기 자신에 대한 요청 역시 메시지를 통해야 한다

이 때 자기 자신에게 메시지를 보내기 위해 감춰진 인터페이스를 사용한다

3. 공용 인터페이스

공용 인터페이스는 서로 다른 객체간의 협력을 위한 접점이다

우리는 What/Who 사이클을 사용하므로, 먼저 메시지를 결정하고 해당 메시지를 수행할 객체를 나중에 결정한다
그렇기 때문에, 자연스럽게 메시지가 수신자의 인터페이스를 결정하게 된다

즉, 인터페이스는 객체가 수신할 수 있는 메시지의 목록으로 채워진다
다르게 말하면, 객체가 어떤 책임을 수행할 수 있는지가 인터페이스의 형태를 결정하게 된다

인터페이스와 구현의 분리

송신자와 수신자가 느슨한 인터페이스에 대해서만 결합되게 만들어라
구체적인 구현 부분에 결합하게 만들지 말라

1. 최소 인터페이스 원칙

외부에서 사용할 필요가 없는 인터페이스는 최대한 노출하지 말라는 원칙이다
인터페이스를 최소로 노출하는 것은 곧, 객체의 내부 동작에 대해 가능한 한 적은 정보만 노출하게 된다

이는 객체의 내부를 수정하더라도 외부에 미치는 영향을 최소화하게 만든다

2. 구현(Implementation)이란?

구현이란, 객체의 내부 구조와 작동 방식을 가리킨다
즉, 객체를 구성하지만 공용 인터페이스에 포함되지 않는 모든 것이 구현에 해당한다

객체의 외부와 내부를 분리하라는 것은, 결국 객체의 공용 인터페이스와 구현을 분리하라는 말이 된다

3. 인터페이스의 구현과 분리 원칙

훌륭한 객체란, 구현을 모르고 인터페이스만 알아도 쉽게 상호작용할 수 있는 객체다
즉, 훌륭한 객체를 만들기 위해선 외부의 인터페이스와 내부의 구현을 명확히 분리해야 한다는 것을 의미한다

소프트웨어는 항상 변경되기 때문에, 우리는 어떤 변경에 외부 객체가 최소한으로 영향받게 만들어야 한다
즉, 변경에 대한 안전 지대(구현)와 위험 지대(인터페이스)를 명확히 분리하는 것이 유지보수에 용이하다

구현을 변경에 대한 안전 지대로 만드는 것은, 객체가 메시지를 처리하는 메서드를 외부에 상관 없이 만들 수 있게 하므로, 자율적인 객체를 만드는 데에도 도움을 준다

4. 캡슐화 & 정보 은닉

인터페이스와 구현을 분리하기 위해서는, 일반적으로 구현을 외부로부터 감추는 캡슐화 기법을 사용한다
이런 측면에서, 캡슐화를 정보 은닉(Information hiding)이라고도 부른다

객체지향에서 캡슐화는 다음 두 가지 관점으로 사용된다

  1. 상태와 행위의 캡슐화

    • 이전에 설명한 것 처럼, 객체를 자율적인 존재로 만들기 위해 상태와 행위를 내부에 보관하는 캡슐화를 의미한다
    • 상태와 행위를 묶어서 보관하고, 외부에서 반드시 접근해야 하는 행위만 골라서 공용 인터페이스를 통해 노출한다

  2. 사적인 비밀의 캡슐화

    • 변경이 빈번하게 일어나는 불안정한 부분을 인터페이스 뒤로 숨기는 캡슐화를 의미한다
    • 일반적으로, ‘불안정한 부분’은 구현과 관련된 세부 사항을 의미한다
    • 이 캡슐화는, 객체의 사적인 부분을 외부의 간섭 없이 변경할 수 있게 만듦으로써 자율적인 객체를 만들 수 있게 한다

책임의 자율성이 협력의 품질을 결정한다

자율적인 책임은 놀라울 정도로 강력하다
자율적인 책임은 협력을 이해하기 쉽게 하고, 객체의 외부와 내부를 명확히 구분하고, 변경의 파급효과를 제한하고, 협력을 유연하게 만들고, 객체의 역할을 이해하기 쉽게 만든다

1. 자율적인 책임은 협력을 단순하게 만든다

우리는 이전에 바리스타에게 무엇을 원했는가?

  • ‘커피콩을 갈고’, ‘에스프레소 머신으로 커피를 내리고’, ‘커피를 제공해라’라고 하지 않았다
  • 우리는 그저 ‘커피를 만들어라’라고 요청했을 뿐이다

위에서 알 수 있듯, 자율적인 책임은 의도를 명확하게 표현함으로써 협력을 단순하고 이해하기 쉽게 만든다

2. 자율적인 책임은 객체의 외부와 내부를 명확하게 분리한다

이전에 말했듯, ‘커피를 만들어라’라는 책임을 수행하는 바리스타는, 커피를 만드는 방식을 자율적으로 선택할 수 있다

외부에서는 ‘커피를 만들어라’라는 책임만 완수할 수 있다면 어떤 방법을 선택할지 상관 없기 때문이다

즉, 책임을 어떻게 수행할지 결정하는 권한이 바리스타에게 있다

3. 자율적인 책임은 내부 수정이 외부에 영향을 미치지 않는다

당신은 바리스타가 ‘커피를 만들어라’라는 책임을 수행하는 방법에는 관심도 없을 뿐더러, 알 수 있는 방법조차 없다

만약 바리스타가 ‘커피콩을 갈고 에스프레소 머신으로 커피를 내려서 제공해라’라는 책임을 수행한다면 어땠을까?

바리스타가 책임을 수행하는 방법을 조금만 변경하더라도 당신과 바리스타 사이의 협력이 무너지게 된다
즉, 바리스타의 수정에 당신이 영향 받게 되는 것이다

자율적인 책임은 변경의 파급효과가 객체 내부로 캡슐화되어, 객체 간의 결합도가 낮아진다

4. 자율적인 책임은 협력에 유연성을 제공한다

당신 입장에서 ‘커피를 만들어라’라는 책임만 수행할 수 있다면, 바리스타 뿐 아니라 어느 객체가 요청을 수신하던지 상관할 필요 없다

당신의 친구가 ‘커피를 만들어라’라는 책임을 수행할 수 있다면, 커피를 만드는 객체가 친구가 될 수도 있는 것이다

반면 ‘커피콩을 갈고 에스프레소 머신으로 커피를 내려서 제공해라’라는 구체적인 책임이었다면, 협력에 참여할 수 있는 객체는 ‘커피콩을 갈고 에스프레소 머신으로 내릴 수 있는’ 객체로 한정된다

즉, 책임이 자율적일수록 설계가 유연해지고 재사용성이 높아진다

5. 자율적인 책임은 객체의 역할을 이해하기 쉽게 만든다

‘커피를 만들어라’라는 책임은, 협력에서 바리스타가 어떤 역할을 하는지 명확하게 전달한다

만일 ‘커피콩을 갈고’, ‘에스프레소 머신으로 커피를 내리고’, ‘커피를 제공해라’라는 책임이었다면, 바리스타가 어떤 역할을 수행하는건지 이해하기 어려울 것이다
