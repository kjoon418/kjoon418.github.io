역할, 책임, 협력

한 카페가 있다 가정해보자.
이 카페에는 주문을 처리하는 캐셔, 커피를 만드는 바리스타, 커피를 주문하는 손님이 있다.

카페 예시를 통해서 객체지향에서의 역할과 책임, 협력에 대해 알아보자

1. 협력

협력은 객체 사이의 요청과 응답으로 구성된다

  • 요청을 받은 객체는 주어진 책임을 다하면서 필요한 서비스를 제공한다
    즉, 요청에 응답한다

객체들은 요청과 응답을 통해 협력하며, 하나의 거대한 문제를 같이 해결한다

  • 각각의 객체는 요청을 성실히 이행해서 적절한 응답을 제공함으로써, 전체의 복잡한 문제를 해결하게 된다

2. 역할과 책임

객체는 다른 객체와 협력하는 과정 속에서 특정한 역할(Role)을 부여받는다

  • 역할이란, 협력에 참여하는 특정 객체가 협력 안에서 차지하는 책임이나 임무를 의미한다
  • 즉, 역할이라는 단어는 의미적으로 책임을 내포한다

카페 예시의 경우, 각 사람의 책임은 다음과 같다

  1. 손님 - 커피를 주문하고, 완성된 커피를 받아간다
  2. 캐셔 - 주문 내용을 바리스타에게 전달하고, 커피가 준비됐음을 손님에게 알린다
  3. 바리스타 - 커피를 제조한다

3. 객체의 특징

  1. 여러 객체가 동일한 역할을 수행할 수 있다

    • 주문을 받는 캐셔가 여럿일 수도 있고, 커피를 만드는 바리스타가 여럿일 수도 있다
      캐셔가 누구든 주문만 잘 받으면 되고, 바리스타가 누구든 커피만 잘 만들면 문제없다
    • 즉, 같은 역할을 수행하는 객체가 몇 개인지는 중요하지 않다
      요청자 입장에서는 해당 객체가 책임을 성실히 이행할 수 있는지만 중요하다

  2. 역할이 같다면, 객체들은 서로 대체 가능(Substitutable)하다

    • 손님 입장에서는 여러 캐셔가 있더라도 아무한테나 가서 커피를 주문하면 된다
      모든 캐셔는 손님의 커피 주문을 처리할 수 있기 때문이다
    • 어느 캐셔가 그만두더라도, 같은 일을 할 수 있는 다른 캐셔가 있다면 손님 입장에서는 아무 문제도 일어나지 않는다
    • 즉, 같은 역할을 수행할 수 있는 객체가 여럿 있다면, 요청자 입장에서는 어느 객체를 사용하던 상관 없다

  3. 책임을 수행하는 방법은 객체의 자율이다

    • 바리스타가 여럿 있다면 각각의 바리스타가 커피를 만드는 방법은 모두 다를 수 있다
      하지만, 캐셔 입장에서는 어느 바리스타에게 커피 제작을 요청하던 상관 없다
    • 여러 객체가 같은 역할을 수행하더라도, 각각 객체마다 서로 다른 방식으로 요청을 처리할 수 있다
      이 능력을 다형성(Polymorphism)이라고 한다

  4. 한 객체가 동시에 여러 역할을 수행할 수 있다

    • 한 사람이 캐셔 역할과 바리스타 역할을 동시에 수행해도 문제되지 않는다
      손님 입장에서는 자신이 주문한 커피가 제대로 제공되는지만 중요하다
    • 이처럼, 한 객체가 동시에 여러 역할을 수행할 수도 있다
      요청자 입장에서는 해당 객체가 본인이 책임을 제대로 이행하는지만 중요하다

바람직한 객체란?

1. 협력적인 객체

모든 객체는 충분히 ‘협력적’이어야 한다
즉, 다른 객체의 요청에 충실히 응답할 수 있어야 하고, 다른 객체에게 적극적으로 도움을 요청해야 한다

외부 도움 없이 모든 것을 스스로 처리하는 전지전능한 객체(God object)는 내부적인 복잡도가 너무 높아지기 마련이다

2. 자율적인 객체

모든 객체는 충분히 ‘자율적’이어야 한다
즉, 다른 객체의 요청을 어떻게(how) 처리할지 스스로 판단하고 행동해야 한다

위에서 말한 ‘협력적인 객체’는 다른 객체의 명령에 따라 행동하는 수동적인 객체가 아니다
외부의 요청에 적극적으로 응답하되, 요청을 어떻게 처리할지는 스스로가 결정해야 한다

즉, 요청을 받은 객체는 요청을 처리하되 최대한 스스로의 판단에 따라 결정하고 행동해야 한다

  • 어떤 손님도 캐셔에게 주문을 어떻게 처리하라고 명령하지 않는다
    손님은 캐셔가 어떻게 주문을 받아야 하는지 몰라도 괜찮다
  • 어떤 캐셔도 바리스타에게 커피를 어떻게 만들라고 명령하지 않는다
    캐셔는 바리스타가 커피를 어떻게 만들어야 하는지 몰라도 괜찮다

3. 상태 & 행동

자율적인 객체가 되기 위해서는, 상태(State)와 행동(Behavior)을 함께 지녀야 한다
객체가 협력에 참여하기 위해 어떤 행동을 해야 할 때, 그 행동에 있어 필요한 것이 상태이다

바리스타가 커피 제조법을 모른다는 것은 말이 되지 않는다
즉, 객체는 어떤 행동을 하기 위해 필요한 상태를 스스로 지니고 있어야 한다

상태는 객체가 스스로 생각하고 판단하는 자율적인 존재가 되기 위해 반드시 필요하다

객체지향에서의 협력

1. 협력과 메시지

손님은 캐셔에게 커피를 요청하고, 캐셔는 바리스타에게 커피 제조를 요청한다
실세계에서는 사람 간에 여러 방법을 통해 요청하고 응답할 수 있지만, 객체지향의 세계에서는 오직 한 가지 의사소통 수단만이 존재한다
이를 메시지라고 한다

여러 객체는 서로 메시지를 전송하고 수신하며 협력한다
즉, 객체지향의 세계에서 협력은 메시지를 전송하는 객체와, 메시지를 수신하는 객체의 관계로 구성된다

메시지를 전송하는 객체는 송신자(Sender)라고 부르고, 메시지를 수신하는 객체는 수신자(Receiver)라고 부른다

2. 메서드

위에서 말했듯, 객체는 다른 객체들과 협력하기 위해 메시지를 전송하고 수신한다
이 때, 객체가 수신한 메시지를 처리하는 방법을 메서드(Method)라고 부른다

메서드는 주로 클래스 안에 포함된 함수 혹은 프로시저를 통해 구현된다
따라서, 어느 객체에게 메시지를 전송하면, 결과적으로 메시지에 대응되는 특정 메서드가 실행된다

3. 메시지와 메서드의 분리

객체지향 프로그래밍 언어에서는, 메시지를 수신한 객체가 실행 시간에 메서드를 선택할 수 있다
이는 프로시저 호출에 대한 실행 코드를 컴파일 시간에 결정하는 절차지향 언어와의 차별점이다

즉, 메시지와 메서드의 분리가 가능하다

메시지와 메서드의 분리는, 객체의 협력에 참여하는 객체들 간의 자율성을 증진시킨다

  • 바리스타의 경우를 생각해 보자
    바리스타는 커피 제조(메시지) 요청을 받지만, 커피를 어떻게 제조할지(메서드)는 스스로 결정한다
  • 이와 같이, 메시지(외부의 요청이 무엇인지 식별)와 메서드(요청을 처리하는 구체적인 방법)를 구분하는 것은 객체의 자율성을 높이는 핵심 메커니즘이다

객체지향의 핵심은 클래스가 아니다

클래스는 객체를 만드는 데 사용하는 구현 메커니즘일 뿐이다
즉, 객체지향에서 가장 중요한 것은 클래스가 아니라 객체다
(클래스라는 매커니즘 없이도 객체를 구현하는 자바스크립트를 생각해보라)

훌륭한 객체지향 설계자가 되기 위해선, 코드를 담는 클래스의 관점에서 벗어나 메시지를 주고받는 객체의 관점으로 사고를 전환하는 것이다

정적인 클래스를 어떻게 구현할지 생각하지 말고, 동적으로 메시지를 주고받는 객체들을 어떻게 구현할지 고민해 보자
즉, 클래스의 구조나 메서드에 집중하지 말고, 객체의 역할/책임/협력에 집중하라

요약(객체지향의 본질)

  1. 객체지향이란, 시스템을 상호작용하는 자율적인 객체들의 공동체로 바라보고, 객체를 이용해 시스템을 분할하는 방법이다
  2. 자율적인 객체란 상태와 행위를 함께 지니며, 스스로 자기 자신을 책임지는 객체이다
  3. 객체는 시스템의 행위를 구현하기 위해 다른 객체와 협력한다
    각 객체는 협력 내에서 정해진 역할을 수행한다
    역할은 관련된 책임의 집합이다
  4. 객체는 다른 객체와 협력하기 위해 메시지를 전송한다
    메시지를 수신한 객체는, 메시지를 처리하는 데 적합한 메서드를 자율적으로 선택한다
